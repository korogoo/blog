> 
> 다만 실제로 실무를 보고 다양한 코드를 보면서, 적절한 타협점을 계속 찾아가는 것 같아요. 아무래도 여러 사람이 협업해서 코드를 작성하고 리뷰를 하다 보니, 회사에서 협업할때에는 정교한 다형성보다는 해당 코드가 지는 책임 그리고 해당 코드의 작관성에 대해 더 고민하게 되더라고요.
> 
> 예를 들어 협업을 하면서 코드 확인이 어려워서, 여러 단계의 상속 관계나 지나치게 세부적인 클래스 쪼개기는 지양하게 되었습니다.(기능 확인을 위해 지나치게 많은 클래스를 확인해야 하고, 책임이 분산되어 복잡도가 증가)  
대신 팀에서 다형성을 활용한 예시라면, 공통 모듈에 여러 인터페이스들을 만들어둬서, 공통 기능(예: 암호화, 파일 생성 등)에 대해 사용하는 쪽에서는 인터페이스만 참조하도록 하고 구현체는 필요 및 상황에 따라 여러 개를 만들어 주입해주는 경우도 보았습니다. 이러한 다형성의 적용은 정말 유용하게 잘 쓰고 있는듯 해요. (아무래도 책임이 명확하고, 사용하는 측에서도 편리하니까요)

> `협업하기 좋은 코드` 혹은 `직관적인 코드`는 사람마다 기준이 다를수밖에 없고, 저 역시 제 기준이 정답이라고 생각하지는 않습니다.  
그래서 더 중요한 건, 코로구의 기준을 어떻게 정할지라고 생각해요. 앞으로 페어들과 미션 진행하면서 기준을 잡아가고, 다만 유연하게 기준을 바꿀 수 있는 마음가짐도 함께 가지고 가면 좋겠습니다. 그러면 레벨2 시점쯤에는 지금 하시는 고민에 대해 어느정도 정리가 되어있지 않을까 기대되네요. 💯

## 가독성이란?

> 가독성은 ==코드를 이해하는 데 드는 인지 비용==이다  
> 
> 파일을 몇 개나 열어봐야 하는가, 추적이 몇 단계나 필요한가

---

### 정의

John Ousterhout — *A Philosophy of Software Design* (2018)

> "Complexity is anything related to the structure of a software system that makes it **hard to understand and modify** the system."

복잡성의 핵심 증상 중 하나는 개발자가 코드 하나를 파악하기 위해 알아야 하는 정보의 양이다

클래스 하나를 이해하기 위해 다른 클래스 5개를 먼저 이해해야 한다면, 그게 바로 높은 인지 부하다

---

### 내가 느끼는 가독성 저하 신호

✨ **상속 계층이 3단계 이상 들어간다**

`SangSetup → GeneralSangSetup → 구현체4개` 같은 구조는

기물 초기화 로직 하나를 파악하기 위해 3개의 파일을 순서대로 이해해야 한다

<br/>

✨ **한 기능을 파악하기 위해 3~4개의 객체가 협력 중임을 알아야 한다**

단순한 기능인데 클래스 의존 그래프를 머릿속에 그려야 하면 힘들다

<br/>

✨ **처음 보는 디자인 패턴이 쓰인다**

팀 전체의 지식 수준을 고려하지 않은 패턴은 협업 비용을 높인다

💬 리뷰어 카프카(include42)도 이렇게 말했다:

> "여러 단계의 상속 관계나 지나치게 세부적인 클래스 쪼개기는 지양하게 되었습니다. 기능 확인을 위해 지나치게 많은 클래스를 확인해야 하고, 책임이 분산되어 복잡도가 증가하기 때문입니다."

---

### 가독성의 기준

> 이 코드를 처음 보는 사람이 얼마나 빨리 이해할 수 있는가?

| 신호                  | 판단       |
| ------------------- | -------- |
| 상속 3단계 이상           | ⚠️ 검토 필요 |
| 협력 객체 3~4개 이상 이해 필요 | ⚠️ 검토 필요 |
| 파일 1~2개로 파악 가능      | 좋다       |
| 메서드 이름만으로 의도 파악 가능  | 좋다       |

## 확장성과 다형성

> 확장성은 미덕이 아니다  
> 
> ==충분히 가변적인 곳에 적용한 다형성만이 의미 있다==

---

### OCP 원칙

Robert C. Martin — *Clean Coder Blog* (2014)

> "You should be able to extend the behavior of a system without having to modify that system."

확장에는 열려있고, 수정에는 닫혀있어야 한다는 원칙이다

새 기물 `Dragon`을 추가할 때 기존 코드를 건드려야 한다면, OCP가 필요한 상황이다

---

### YAGNI 원칙

Ron Jeffries — *Extreme Programming* (2001)

> "Always implement things when you actually need them, never when you just foresee that you will need them."

지금 필요하지 않은 것은 만들지 않는다

OCP는 훌륭한 원칙이지만, YAGNI와 함께 생각해야 한다

---

### 내가 만든 구분

💬 카프카(include42)의 코멘트이다

> "공통 기능(예: 암호화, 파일 생성 등)에 대해 사용하는 쪽에서는 인터페이스만 참조하도록 하고, 
> 
> 구현체는 필요 및 상황에 따라 여러 개를 만들어 주입해주는 경우도 보았습니다. 
> 
> 이러한 다형성의 적용은 정말 유용하게 잘 쓰고 있는 듯 해요."

<br/>

이 사례와 내 SangSetup, Turn 구조의 차이를 생각해봤을 때, 

충분히 가변적인 곳에 적용한 다형성은 과하지 않다는 결론을 내렸다

---

### Rule of Three 리팩터링 타이밍

Martin Fowler — *Refactoring* (Don Roberts 원 제안)

> "The first time you do something, you just do it. The second time you do something similar, you wince at the duplication, but you do the duplicate thing anyway. **The third time you do something similar, you refactor.**"
> 
> 처음 뭔가를 할 때는 그냥 합니다. 두 번째로 비슷한 일을 할 때는 중복되는 코드 때문에 움찔하지만, 어쨌든 중복된 코드를 그대로 둡니다. **세 번째로 비슷한 일을 할 때는 리팩토링을 합니다.**


<br/>

추상화 타이밍은 두 번째가 아니라 세 번째라는 재미있는 기준이었다

추상화 타이밍이 너무 어려우면 이런식으로 단순하게 생각하는 것도 방법인 것 같다

### 실전 판단 흐름

```
새 구조를 설계한다
        │
        ▼
애플리케이션 코드인가, 변경 비용이 큰 영역인가?
        │
   ┌────┴──────────────┐
앱 코드              DB/외부 API/인프라
   │                      │
   ▼                      ▼

   │
   ▼

   │
   ▼
그때 리팩터링
```

### 예외) 추상화를 미리 고려할 때

다음 두 조건 중 하나에 해당하면 다르게 판단한다

<br/>

✨ **이후에 반드시 도입될 기능이라는 확신이 있을 때**

확신의 근거: 팀 로드맵, 계약된 요구사항, 업무 특성상 반복되는 패턴

<br/>

✨ **초기 구조를 잘못 잡으면 변경 비용이 너무 큰 영역일 때**

모든 레이어의 리팩터링 비용이 같지 않다

레이어별 리팩터링 비용을 고려하여 추상화를 도입한다

| 레이어                  | 변경 비용                       | 기본 전략         |
| -------------------- | --------------------------- | ------------- |
| 애플리케이션 코드 (도메인, 서비스) | 낮음 - IDE 리팩터링, 테스트로 확인 가능   | 단순하게 시작       |
| DB 스키마               | 높음 - 마이그레이션, 데이터 변환, 운영 리스크 | 처음부터 보수적으로 설계 |
| 외부 API 계약            | 높음 - 하위 호환성, 클라이언트 영향       | 변경 여지를 미리 확보  |
| 인프라 구성               | 높음 - 배포, 장애 위험              | 검증 후 변경       |

### 실전 체크리스트

❓ **나중에 필요할 것 같아서 추상화를 도입하려 하는가?**

YAGNI 원칙을 생각하며 실제 요구가 생겼을 때 리팩터링한다  

애플리케이션 코드는 리팩터링 비용이 낮다

<br/>

❓ **지금 만드는 게 DB 스키마, 외부 API 계약, 인프라 구성인가?**

변경 비용이 높다

여기서는 처음부터 보수적으로 설계한다

<br/>

❓ **같은 패턴이 몇 번째 등장했는가?**

세 번째라면 추상화 타이밍이다

<br/>

❓ **상속 계층이 3단계를 넘거나, 협력 객체가 3~4개 이상인가?**

단순화를 검토한다

값 주입이나 enum으로 해결되지 않는지 먼저 본다

<br/>

❓ **책임이 선명하고 읽기 좋은 구조인가?**

이것 자체가 나중에 바꾸기 쉬운 구조의 전제 조건이다
