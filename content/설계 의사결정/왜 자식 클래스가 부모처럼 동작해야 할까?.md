## 발단

`EmptyPiece`가 `Piece` 인터페이스를 구현하면서 `asFullPiece()`를 호출하면 예외를 던지는 구조를 만들었다

나와 비슷하게 코드를 작성한 크루들이 리뷰어에게 지적을 받았다

예를 들어, 리뷰어에게 "호출하면 안 된다는 제약이 여전히 남아있는 것 아닌가" 라는 피드백을 받았다

또 `isPo()`로 타입별로 다르게 처리하는 코드에서도 "LSP 관점에서 문제가 생길 수 있다"는 지적을 받았다

<br/>

LSP 는 뭐고, 인터페이스에서 왜 그 개념이 중요한지 궁금해졌다

## LSP(리스코프 치환 원칙)

> ==상위 타입의 객체를 하위 타입으로 대체해도 프로그램이 올바르게 동작해야 한다==

---

### 개념

Barbara Liskov가 1987년에 제시한 원칙이다


💬 
T 타입의 객체 o1에 대해,

S 타입의 객체 o2가 있어서

T로 정의된 모든 프로그램 P에서

o1 대신 o2를 사용해도 P의 동작이 변하지 않는다면

S는 T의 서브타입이다


<br/>

쉽게 말하면

> `Piece piece = new EmptyPiece()` 가 `Piece piece = new Cannon()` 과 **같은 기대**로 사용될 수 있어야 한다

---

### 위반 예시: 예외를 던지는 구현

⚠️ **EmptyPiece가 Piece처럼 동작하지 않는다**

```java
public class EmptyPiece implements Piece {

    @Override
    public List<Position> getMovablePositions(Position from, Board board) {
        throw new UnsupportedOperationException("빈 기물은 이동할 수 없습니다");
        // "호출하면 안 된다"는 제약이 숨어있다
    }
}
```

`Piece`를 사용하는 쪽은 `getMovablePositions()`가 정상 동작한다고 기대한다

`EmptyPiece`로 대체하는 순간 예외가 터진다 → LSP 위반

---

### 위반 예시: 타입 분기로 다른 처리

⚠️ **isPo()로 분기하는 순간 상위 타입으로 대체 불가능**

```java
if (piece.isCannon()) {
    // Cannon 전용 처리
} else {
    // 나머지 처리
}
```

---

### 계약 관점

LSP는 상속 관계에서의 계약을 요구한다

- **사전 조건**: 자식 클래스는 부모보다 약하거나 같아야 한다 (더 많은 입력을 받을 수 있다)
- **사후 조건**: 자식 클래스는 부모보다 강하거나 같아야 한다 (더 많은 보장을 제공한다)
- **불변 조건**: 부모 클래스의 불변 조건은 자식 클래스에서도 유지돼야 한다

## LSP를 지키는 설계

> LSP를 지키는 핵심은 ==계층 구조가 "행위의 유사성"에 기반하는 것==이다  
> 
> 코드 재사용이 아닌 행위의 일관성을 위해 상속한다

---

### 패턴: Null Object 패턴으로 구현 처리

빈 기물도 Piece처럼 동작하게 수정해본다

```java
public class EmptyPiece implements Piece {

    @Override
    public List<Position> getMovablePositions(Position from, Board board) {
        return List.of(); // 빈 기물은 이동 가능한 위치가 없다 — 예외 없음
    }

    @Override
    public int getScore() {
        return 0; // 빈 기물은 점수가 없다
    }

    @Override
    public boolean isOwnedBy(Side side) {
        return false; // 빈 기물은 누구의 것도 아니다
    }
}
```

`Piece`를 사용하는 쪽이 null 체크 없이 안전하게 쓸 수 있다

---

### 패턴: 상속보다 인터페이스 분리

서로 다른 계약을 하나의 인터페이스로 묶으면 LSP가 깨진다

⚠️ **차는 포의 규칙이 필요 없다**

```java
public interface CannonRule {
    boolean canJumpOver(List<Piece> path);
}

public class Chariot extends StraightMovePiece implements CannonRule {
    @Override
    public boolean canJumpOver(List<Piece> path) {
        throw new UnsupportedOperationException(); // 차는 이 메서드가 의미 없다
    }
}
```

✨ **포에게만 필요한 규칙은 포만 구현한다**

```java
public class Cannon extends StraightMovePiece implements JumpRule {
    @Override
    public boolean canJumpOver(List<Piece> path) {
        return path.size() == 1;
    }
}
// Chariot은 JumpRule 구현 불필요
```

---

### 상속을 쓸 때 LSP 체크

```
부모 클래스의 모든 메서드를
자식 클래스로 대체해도 동작이 같은가?
         │
    ┌────┴────┐
   YES        NO
    │          │
    ▼          ▼
LSP 준수   X 상속이 잘못된 것
           인터페이스 분리 or 구조 변경 고려
```

---

### 상속 vs 인터페이스

| 상황                 | 선택      |
| ------------------ | ------- |
| is-a 관계 + 행위가 일관됨  | 상속      |
| ~할 수 있다(can-do) 관계 | 인터페이스   |
| 공통 코드 재사용이 목적      | 컴포지션 고려 |

## 내 기준

### 핵심 질문

❓ **자식 클래스를 부모 타입으로 사용했을 때, 호출하는 쪽의 기대가 깨지는가?**

기대가 깨진다면 LSP 위반이고, 상속 구조를 검토해본다


---

### LSP 위반 신호

| 신호                                           | 의미        |
| -------------------------------------------- | --------- |
| 자식 클래스 메서드에서 `UnsupportedOperationException` | 상위 계약 위반  |
| "이 메서드는 호출하면 안 된다"는 주석                       | LSP 위반 구조 |
| `instanceof`로 자식 타입을 확인 후 분기                 | 다형성 실패    |
| 자식 클래스가 부모의 사전 조건을 강화                        | LSP 위반    |

---

### 실전 체크리스트

❓ **자식 클래스에 `UnsupportedOperationException`이 있는가?**

상속 구조가 잘못된 것이다

인터페이스를 분리하거나 계층을 재설계한다

<br/>

❓ **"이 메서드는 이 클래스에선 호출하지 않는다"는 전제가 있는가?**

그 전제 자체가 LSP 위반의 신호다

<br/>

❓ **부모 타입으로 대체했을 때 if/instanceof 분기가 필요한가?**

다형성이 제대로 동작하지 않는다는 신호다
