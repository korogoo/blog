## 발단

Spring Boot 2.6 이후부터 Bean 순환참조가 기본 금지됐다는 것을 알게 됐다

그러다 "인터페이스끼리도 순환참조가 가능한가?"라는 질문이 생겼다

구현체 간의 순환참조는 Spring이 막아주지만, 인터페이스 타입으로 선언했을 때는 어떻게 되는지 궁금했다

---

### 생겼던 질문

- 인터페이스끼리 서로 참조하면 컴파일 에러가 나는가?
- 인터페이스 순환참조와 클래스(Bean) 순환참조는 무엇이 다른가?
- Spring은 어느 시점에 순환참조를 감지하는가?
- 인터페이스 순환참조가 생겼다면 설계에 어떤 문제가 있는 것인가?

---

### 왜 중요한가?

> 순환참조는 컴파일러가 막아주지 않는 경우가 많다  
> ==설계 수준에서 의존 방향을 단방향으로 유지해야 한다==

인터페이스 순환이 있다는 것은 두 개념이 서로 강하게 결합되어 있다는 신호다

의존 방향을 정리하거나, 중간에 새로운 추상화를 도입하는 것이 해결책이다


---

---

## 인터페이스끼리의 순환참조

> 인터페이스끼리의 순환참조는 컴파일 수준에서는 가능하다  
> 
> ==하지만 의미 있는 설계인지는 다른 문제다==

---

### 순환참조란?

A가 B를 의존하고, B가 A를 의존하는 구조다

```
A → B → A (순환)
```

---

### 인터페이스끼리는 가능한가?

```java
public interface A {
    B getB();
}

public interface B {
    A getA();
}
```

컴파일 에러가 나지 않는다

인터페이스는 메서드 시그니처만 선언하기 때문에 서로를 타입으로 참조해도 JVM이 문제없이 로딩한다

인터페이스는 Spring이 직접 Bean으로 만들지 않기 때문에 컴파일에서 문제가 되지 않는다

⚠️  **하지만, 구현체가 만들어질 때 순환이 생기는 것이 문제다**

---

### 클래스 순환참조와의 차이

```java
@Service
class ServiceA {
    @Autowired ServiceB serviceB;
}

@Service
class ServiceB {
    @Autowired ServiceA serviceA;
}
```

Spring이 Bean을 생성할 때 A를 만들려면 B가 필요하고,  

B를 만들려면 A가 필요한 교착 상태가 발생한다

Spring Boot 2.6 이후부터는 기본적으로 순환참조를 금지한다

---

### 의미 있는 설계인가?

인터페이스끼리 순환참조가 생겼다면, 두 인터페이스가 강하게 결합되어 있다는 신호다

❓ **두 개념이 정말 서로를 알아야 하는가?**

❓ **한쪽이 다른 쪽에 일방적으로 의존하도록 방향을 정할 수 없는가?**

❓ **중간에 새로운 추상화를 도입해서 순환을 끊을 수 없는가?**

---

### 핵심

인터페이스끼리의 순환참조는 컴파일러가 막지 않는다

하지만 순환이 생겼다는 것 자체가 설계를 다시 볼 신호다

의존 방향이 한쪽으로 흐르도록 설계를 정리하는 것이 맞다


---

## 내 기준

### 순환참조 감지 시점

| 종류               | 감지 시점                         |
| ---------------- | ----------------------------- |
| 인터페이스 순환참조       | 컴파일 통과, 런타임도 문제없음             |
| 클래스(Bean) 순환참조   | Spring 컨텍스트 로딩 시 (런타임 오류)     |
| Spring Boot 2.6+ | 기본적으로 Bean 순환참조를 시작 시 감지하고 거부 |

---

### 인터페이스 순환 발생 시 해결 방법

✨ **의존 방향을 한쪽으로 정한다**

```
A ←→ B  (순환)
```

```
A → B  (단방향)
```

A가 B를 알고, B는 A를 모르게 한다

<br/>

✨ **중간 추상화를 도입한다**

```
A → C ← B
```

두 개념이 공통으로 의존할 수 있는 새로운 인터페이스 C를 만든다

---

### 실전 체크리스트

❓ **인터페이스 두 개가 서로를 타입으로 참조하고 있는가?**

컴파일은 되지만, 이 두 개념이 정말 서로를 알아야 하는지 다시 생각한다

<br/>

❓ **Spring Bean 순환참조 오류가 나는가?**

`application.properties`에 `spring.main.allow-circular-references=true`로 임시 우회할 수 있지만, 

근본 원인(설계 문제)을 해결하는 것이 맞다

<br/>

❓ **순환을 끊기 어렵다면?**

두 클래스가 하나의 책임을 나눠 갖고 있는 것일 수 있다

하나로 합치거나, 제3의 클래스로 공통 로직을 분리한다
