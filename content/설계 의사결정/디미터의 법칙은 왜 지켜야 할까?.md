## 발단

다른 크루의 리뷰를 구경하다가 `board.getPieces().get(position).getSide().getColor()` 같이 연속으로 점을 찍는 코드 발견했다

리뷰어는 해당 코드에 대해서 점을 하나만 찍도록 개선하라는 코멘트를 남겼다

그리고 우테코 요구사항에도 "한 줄에 점을 하나만 찍는다." 라는 규칙이 있다

이 규칙을 왜 지켜야 하는지 궁금해졌다

## 디미터의 법칙이란?

> 디미터의 법칙: ==내가 직접 아는 객체의 메서드만 호출한다==  
> 
> 한 줄에 점을 하나만 찍는다로 기억하면 쉽다

---

### 개념

디미터의 법칙(Law of Demeter, LoD): 객체는 자신과 **직접 연결된** 객체에만 메시지를 보낸다


메서드 M에서 호출해도 되는 대상:
  1. M이 속한 클래스 자신 (this)
  2. M의 파라미터로 받은 객체
  3. M 안에서 직접 생성한 객체
  4. 클래스의 인스턴스 변수


---

### 위반 예시

⚠️ **기차 충돌 코드 (Train Wreck라고도 한다)**

```java
String color = board.getPieces().get(position).getSide().getColor();
//                    └─ Board 내부               └─ Piece 내부 └─ Side 내부
//          Board → Piece → Side → Color 까지 줄줄이 의존
```

이 코드는 `Board`의 내부 구조(`Map<Position, Piece>`)를 알고,

`Piece`의 내부 구조(`Side`)를 알고,

`Side`의 내부 구조(`Color`)를 알아야 한다

`Side`에 `Color`가 없어지면 이 코드도 바꿔야 한다

---

### 준수 예시

👍 **Board에게 이 위치의 색이 뭔지 바로 묻는다**

```java
String color = board.getColorAt(position);
```

```java
// Board 안에서 처리
public String getColorAt(Position position) {
    return pieces.get(position).getColor();
}
```

호출하는 쪽은 Board 내부 구조를 전혀 몰라도 된다

---

### 왜 중요한가?

✨ **결합도를 낮춘다**

`board.getPieces().get(position).getSide().getColor()`는  
Board, Piece, Side의 내부 구조 모두에 결합되어 있다

하나만 바뀌어도 이 코드가 깨진다

<br/>

✨ **변경 범위를 줄인다**

Board 내부가 바뀌어도 Board 밖에는 영향이 없어야 한다

<br/>

✨ **캡슐화를 강제한다**

getter로 내부를 꺼내지 않고, 객체에게 일을 시키게 된다 (Tell, Don't Ask)

## 위반 사례와 해결

> 점이 여러 개 찍히는 곳을 찾으면 ==결합이 숨어있는 곳==이 보인다

---

### 패턴별 해결

 ⚠️ **체이닝으로 내부 탐색**

```java
int score = game.getBoard().getPieces().stream()
    .mapToInt(p -> p.getSide().getScore())
    .sum();
```

✨  **Board에게 일을 시킨다**
```java
int score = game.calculateScore();

// Game 안에서
public int calculateScore() {
    return board.sumScore();
}

// Board 안에서
public int sumScore() {
    return pieces.values().stream()
        .mapToInt(Piece::getScore)
        .sum();
}
```

---

⚠️ **getter 체이닝으로 조건 확인**

```java
if (game.getBoard().getPieces().get(pos).getSide() == Side.HAN) { ... }
```

✨ **Board에게 물어본다**
```java
if (game.isHanAt(pos)) { ... }
```

---

⚠️ **stream()을 외부로 노출**

```java
// 내부 컬렉션의 stream을 꺼내줌 → 호출자가 내부를 마음대로 처리
public Stream<Piece> getPieceStream() {
    return pieces.stream();
}

// 호출부
board.getPieceStream()
    .filter(p -> p.getSide() == side)
    .count();
```

✨ **필요한 결과를 Board 안에서 계산**
```java
public long countBySide(Side side) {
    return pieces.values().stream()
        .filter(p -> p.getSide() == side)
        .count();
}
```

---

### 주의: 디미터의 법칙 예외

**점이 두 개여도 문제없는 경우**가 있다

```java
// 빌더 패턴 (같은 객체를 반환하는 체이닝)
Game.builder()
    .name("장기")
    .status(Status.RUNNING)
    .build();

// 스트림 (중간 연산 체이닝)
pieces.stream()
    .filter(...)
    .map(...)
    .collect(toList());
```

객체 구조를 **탐색**하는 것이 문제이지, **같은 타입을 반환하는 체이닝**은 다른 개념이다

## 내 기준

### 핵심 질문

❓ 한 줄에서 탐색하는 객체가 몇 단계인가?

 👍 1단계: `board.move()` 
 
⚠️ 2단계: `board.getPiece(pos).getScore()` 

👎 3단계 이상: `a.getB().getC().doSomething()`

---

### 판단 기준표

👍 인스턴스 변수의 메서드 `this.field.method()`

👍 파라미터의 메서드 `param.method()`

👍 직접 생성 객체 `new Object().method()`

👍 같은 타입 체이닝 `stream().filter().map()...`

👍 빌더 체이닝 `builder.set().set().build()`

⚠️ B 내부에 의존 `a.getB().method()`

👎 기차 충돌 `a.getB().getC().method()`

---

### 해결 전략

✨ **중간 객체에 메서드를 위임한다**

`a.getB().doSomething()` -> `a.doSomethingViaB()`

<br/>

✨ **일급 컬렉션에 로직을 옮긴다**

`list.stream().filter(...).count()` -> `pieces.countBySide(side)`
   
<br/>

✨ **Tell, Don't Ask**

값을 꺼내서 판단하지 말고, 객체에게 판단을 시킨다

---

### 실전 체크리스트

❓ **한 표현식에 점이 2개 이상인가?**

탐색인지 체이닝인지 구분한다

<br/>

❓ **getter로 꺼낸 값으로 다시 getter를 호출하는가?**

중간 객체에 메서드를 추가해 위임한다

<br/>

❓ **`stream()`을 외부로 반환하는가?**

컬렉션 내부에서 처리하고 결과만 반환한다 (→ [[02. 일급 컬렉션이란?]])
