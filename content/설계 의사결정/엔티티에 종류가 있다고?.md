## 발단

예전에 크루가 DB 엔티티랑 도메인 엔티티는 다른 개념이라고 언급했다.

엔티티가 뭔지? 엔티티는 JPA 엔티티랑 다른건지? 궁금해졌다


---

---

## Entity 란? 그리고 종류는?

> 엔티티는 ==식별자를 가진, 고유하게 구별 가능한 개념==이다  
> 
> 어떤 계층에서 다루느냐에 따라 DB 엔티티 / 도메인 엔티티 / JPA 엔티티로 나뉜다

---

### DB 엔티티

> 데이터베이스에 저장되는 테이블과 행(Row)의 단위

```sql
CREATE TABLE member (
    id       BIGINT AUTO_INCREMENT PRIMARY KEY,
    email    VARCHAR(100) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

- 관심사: **영속성** - 데이터를 어떻게 저장하고 조회할 것인가
- 행동(메서드)이 없다. 컬럼과 관계만 있다

---

### 도메인 엔티티

> 비즈니스 규칙과 행동을 담은 객체. 식별자로 구별한다

```java
public class Member {
    private final MemberId id;
    private Email email;
    private Password password;

    public void changeEmail(Email newEmail) {
        // 비즈니스 규칙: 인증된 이메일만 허용
        if (!newEmail.isVerified()) {
            throw new InvalidEmailException();
        }
        this.email = newEmail;
    }
}
```

- 관심사: **행동** - 이 개념이 무엇을 할 수 있는가
- DB 구조를 몰라도 된다. 테이블이 어떻게 생겼는지 알 필요 없다

---

### JPA 엔티티

> ORM이 도메인 객체를 DB 테이블에 매핑하기 위해 사용하는 클래스

```java
@Entity
@Table(name = "member")
public class MemberJpaEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String password;

    @Column(nullable = false)
    private LocalDateTime createdAt;
}
```

- 관심사: **매핑** - DB 구조와 자바 객체를 어떻게 연결할 것인가
- 도메인 엔티티도, DB 엔티티도 아니다. 둘 사이의 변환 역할이다


---

---

## 그냥 다 같은 Entity로 생각하면 안되나?

> 분리하지 않으면 ==DB 구조의 변화가 비즈니스 로직을 깨트린다==  
> 
> 그리고 비즈니스 규칙이 JPA 어노테이션에 묻혀 사라진다

---

### 분리하지 않으면 생기는 문제

> 하나의 클래스가 모든 걸 다 한다

```java
@Entity
@Table(name = "member")
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    public void changeEmail(String newEmail) {
        // 비즈니스 규칙이 JPA 엔티티 안에 들어있다
        if (!newEmail.contains("@")) throw new RuntimeException();
        this.email = newEmail;
    }
}
```

✨ **테이블 구조가 바뀌면 비즈니스 로직도 흔들린다**  

`email` 컬럼을 `email_address`로 rename하면, 

비즈니스 메서드가 있는 클래스를 직접 건드려야 한다

<br/>

✨ **JPA 제약이 도메인 설계를 침범한다**  

`@Entity`는 기본 생성자를 요구한다. 

도메인 관점에서 불완전한 객체를 만들어선 안 되는데, JPA 스펙 때문에 억지로 허용하게 된다

<br/>

✨ **테스트가 무거워진다**  

도메인 로직 하나 테스트하려고 `@DataJpaTest`나 DB 설정이 필요해진다

---

### 분리했을 때의 구조

✨ **도메인 엔티티는 순수하게 유지한다**

```java
public class Member {

    private final MemberId id;
    private Email email;

    public void changeEmail(Email newEmail) {
        if (!newEmail.isVerified()) {
	        throw new InvalidEmailException();
		}
        this.email = newEmail;
    }
}
```

<br/>

✨ **JPA 엔티티는 매핑만 한다**
```java
@Entity
@Table(name = "member")
public class MemberJpaEntity {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;
}
```

<br/>

✨ **매퍼가 변환을 담당한다**
```java
public class MemberMapper {

    public Member toDomain(MemberJpaEntity entity) {
        return new Member(new MemberId(entity.getId()), new Email(entity.getEmail()));
    }

    public MemberJpaEntity toJpaEntity(Member member) {
        MemberJpaEntity entity = new MemberJpaEntity();
        entity.setEmail(member.getEmail().getValue());
        return entity;
    }
}
```

---

### 분리가 만들어내는 이점

✨ **변경 격리**

DB 스키마가 바뀌어도 도메인 코드는 건드리지 않아도 된다

도메인 규칙이 바뀌어도 DB 테이블 마이그레이션이 불필요하다

<br/>

✨ **순수한 도메인 테스트**

```java
@Test
void 미인증_이메일로_변경하면_예외() {
    Member member = new Member(...);
    assertThatThrownBy(() -> member.changeEmail(unverifiedEmail))
        .isInstanceOf(InvalidEmailException.class);
}
```

DB 없이 도메인 로직만 테스트할 수 있다


<br/>

✨ **JPA 교체 가능성**

도메인이 JPA를 모르기 때문에, MyBatis나 다른 ORM으로 바꿔도 도메인은 그대로다

## 프로젝트에서 어떻게 쓸까?

> 세 종류의 엔티티를 항상 분리해야 한다는 것이 아니라  
> 
> ==규모와 복잡도에 맞는 전략을 선택하는 것==이 핵심이다

---

### 통합 (작은 프로젝트)

> JPA 엔티티 = 도메인 엔티티로 사용

```java
@Entity
@Table(name = "member")
public class Member {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    // 간단한 도메인 로직도 여기에
    public boolean hasSameEmail(String other) {
        return this.email.equals(other);
    }
}
```

**선택 기준**
- 비즈니스 로직이 단순하다
- 팀이 작고, 빠른 개발이 우선이다
- 도메인 레이어를 따로 테스트할 이유가 없다

⚠️ **주의할 점**  

나중에 로직이 복잡해지면 분리 비용이 커진다

처음부터 도메인 메서드를 최소화해두면 이후 분리가 쉬워진다

---

### 분리 (복잡한 도메인)

> 도메인 엔티티 / JPA 엔티티 / 매퍼를 각각 둔다

```
src/
├── domain/
│   └── member/
│       ├── Member.java          ← 도메인 엔티티
│       ├── MemberId.java
│       ├── Email.java
│       └── MemberRepository.java (인터페이스)
│
└── infrastructure/
    └── member/
        ├── MemberJpaEntity.java ← JPA 엔티티
        ├── MemberJpaRepository.java
        └── MemberMapper.java    ← 변환 담당
```

**선택 기준**
- 비즈니스 규칙이 복잡하고 자주 바뀐다
- 도메인 로직을 DB 없이 단위 테스트해야 한다
- 팀이 크고, 도메인 레이어와 인프라 레이어를 다른 사람이 담당한다

---

### 매퍼 작성 가이드

분리 전략을 쓸 때 매퍼의 위치와 책임이 중요하다

```java
@Component
public class MemberMapper {

    // JPA 엔티티 → 도메인 엔티티
    public Member toDomain(MemberJpaEntity entity) {
        return Member.restore(
            new MemberId(entity.getId()),
            new Email(entity.getEmail()),
            entity.getCreatedAt()
        );
    }

    // 도메인 엔티티 → JPA 엔티티
    public MemberJpaEntity toJpaEntity(Member member) {
        MemberJpaEntity entity = new MemberJpaEntity();
        entity.setEmail(member.getEmail().getValue());
        entity.setCreatedAt(member.getCreatedAt());
        return entity;
    }
}
```

매퍼는 인프라 레이어에 둔다

도메인이 매퍼를 알면 안 된다

도메인 엔티티 생성 시 `restore()` 같은 팩토리 메서드를 분리해두면 생성자와 재구성을 구분할 수 있다

## 내 기준

### 엔티티 정의 분리 기준

```
새 프로젝트를 시작한다
       │
       ▼
도메인 규칙이 복잡하거나 자주 바뀔 것 같은가?
       │
  ┌────┴────┐
 YES        NO
  │          │
  ▼          ▼
분리 전략    도메인 메서드 없이 JPA 엔티티 통합 사용
```

---

### 실전 기준표

| 상황 | 선택 |
|---|---|
| 미션/토이 프로젝트, 로직 단순 | 통합 (JPA 엔티티 = 도메인 엔티티) |
| 도메인 로직 단위 테스트가 필요 | 분리 |
| DB 없이 도메인을 설명할 수 있어야 한다 | 분리 |
| JPA 기본 생성자가 도메인 불변식을 깨트린다 | 분리 |
| 빠른 프로토타이핑, 이후 리팩터링 예정 | 통합으로 시작 → 복잡해지면 분리 |

---

### 기억할 것

> 분리는 목적이 아니라 수단이다  
> 
> 도메인을 DB로부터 보호해야 할 이유가 생겼을 때 분리한다
