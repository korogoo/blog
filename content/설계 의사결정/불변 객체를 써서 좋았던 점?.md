## 가변

> 객체 생성 후에도 ==내부 상태(필드 값)를 바꿀 수 있는 것==

---

### 개념

Java에서 대부분의 객체는 기본적으로 가변이다

`setter`를 열어두거나, 필드를 `public`으로 두거나, 컬렉션을 그대로 반환하면 가변이 된다

```java
public class Piece {  

    private Side side;  
  
    // setter가 있으면 가변 객체  
    public void setSide(Side side) {  
        this.side = side;  
    }
}
```
```java
Piece piece = new Piece(Side.HAN);  
piece.setSide(Side.CHO); // 상태 변경 가능
```

---

### 왜 쓰는가?

✨ **직관적이고 자연스럽다**

현실 세계의 많은 것은 변한다 (유저 정보, 장바구니, 게임 캐릭터 체력 등)

<br/>


✨ **메모리 효율**

객체를 매번 새로 만들지 않아도 된다

상태 변경이 잦은 도메인에 적합하다

<br/>


✨ **JPA/ORM 필수**

Hibernate는 기본적으로 가변 엔티티를 요구한다 (기본 생성자 + setter)

프레임워크(Spring, JPA) 친화적이다


<br/>

✨ **Builder 패턴**

복잡한 객체를 단계적으로 조립할 때 내부적으로 가변 상태를 활용한다

---

### 단점도 있지 않을까?

> ==어디서 바뀌었는지 모른다==가 가장 큰 단점이라고 생각한다

<br/>


✨ **공유 상태 문제**

```java
Piece piece = new Piece(Side.HAN);

// 기물을 넘겼더니 외부에서 Side를 바꿔버림
movePiece(piece);
System.out.println(piece.getSide()); // CHO — 예상 못한 변경
```

<br/>


✨ **멀티스레드 위험**

두 스레드가 동시에 접근하면 데이터가 깨진다

synchronized, Lock 없이는 안전 보장이 안 된다


<br/>

✨ **추적 어려움**

`piece.setSide("HAN")` 가 코드 어디서 호출됐는지 추적하기 어렵다

디버깅 시 "언제 이 값이 바뀌었지?" 를 역추적해야 한다


<br/>

✨ **테스트 복잡도**

테스트 실행 순서에 따라 결과가 달라질 수 있다

```java
// 테스트에서 같은 객체를 공유한다고 가정
GameState state = new GameState();

@Test
void 점수가_10이어야_한다() {
    state.addScore(10);
    assertThat(state.getScore()).isEqualTo(10); // 단독 실행 시 통과
}

@Test
void 점수가_0이어야_한다() {
    assertThat(state.getScore()).isEqualTo(0); // 앞 테스트가 먼저 실행되면 실패
}
```

> @BeforeEach 등에서 상태 초기화 코드를 매번 써야 함

---

### 언제 쓰면 좋을지 나만의 기준을 만들어보자


나는 아래 사항이 모두 충족되면 가변을 사용한다

예를 들면, 객체의 무결성을 포기하는 대신에 성능을 챙기는 것이다

<br/>


✨ **변경이 도메인의 핵심인가?**

예를 들면 주문 상태는 `PENDING` -> `PAID` -> `SHIPPED` 로 변경되는게 핵심이다


<br/>

✨ **변경 시점을 추적할 수 있는가?**

이벤트 로그, 상태 머신 등에서 확인 가능한가?

<br/>


✨ **성능이 더 우선순위인가?**

대량 배치 처리 같은 상황에서는 가변을 고려해본다

<br/>


⚠️ ==단, 메서드 내에서 상태가 잘못 변하는 경우에 대한 처리를 한다==

```java
public class Order { 

	private OrderStatus status; 
	
	public void pay() { 
		if (this.status != OrderStatus.PENDING) {
			throw new IllegalStateException("결제는 PENDING 상태에서만 가능"); 
		}
		this.status = OrderStatus.PAID; 
	}
```
> 근데 이 방법도 결국 멀티 쓰레드에선 pay 가 동시에 호출될 수 있기 때문에 안전하지 않다

## 불변

> 객체 생성 후 ==내부 상태가 절대 변경되지 않는 것==  
> 
> 변경이 필요하면 ==새 객체를 만들어 반환한다==

---

### 개념

Java에서 대표적인 불변 클래스: `String`, `Integer`, `Long`, `LocalDate`, `LocalDateTime`

```java
public String toUpperCase(Locale locale) {  
    return ...
}
```
```java
String a = "hello";
String b = a.toUpperCase(); // a는 그대로, b가 새 객체
// a == "hello", b == "HELLO"
```

---

### 불변 클래스 만드는 조건

```java
public final class Row {  // ① final 클래스 — 상속 차단
    private final int index;   // ② private final 필드

    public Row(int index) {
        this.index = index;
    }

    // ③ setter 없음
    // ④ 변경이 필요하면 새 객체 반환
    public Row add(Row other) {
        return new Row(this.index + other.index);
    }
}
```

| 조건                 | 이유                        |
| ------------------ | ------------------------- |
| `final class`      | 하위 클래스가 가변으로 오버라이드하는 것 방지 |
| `private final` 필드 | 외부 접근 + 재할당 모두 차단         |
| setter 없음          | 변경 경로 자체를 없앰              |
| 가변 필드는 방어적 복사      | 참조를 공유하면 외부에서 변경 가능       |

---

### 왜 쓰는가?

> 이 객체는 절대 안 바뀐다는 보장이 코드 전체를 단순하게 만든다


<br/>


✨ **공유해도 안전**

누가 들고 있어도 절대 바뀌지 않으니 복사할 필요가 없다

<br/>


✨ **멀티스레드 안전**

동기화 없이 공유 가능하다

<br/>


✨ **버그 감소**

언제 바뀌었는지 추적할 필요 자체가 없다

<br/>


✨ **HashMap 키로 안전**

필드 값으로 계산되는 `hashCode`가 바뀌어서 저장 당시 버킷을 다시 못 찾게 된다

불변이면 필드가 절대 안 바뀌니 `hashCode`도 보장된다

<br/>


✨ **테스트 단순**

상태 초기화 불필요하고, 순서도 무관하다

---

### 단점도 있지 않을까?

✨ **객체 생성 비용**

변경마다 새 객체 생성
대부분의 경우 JVM GC가 잘 처리하므로 실제 문제가 되는 경우는 드물다

단, 극단적인 대량 루프에서는 성능 측정 후 판단한다

<br/>


✨ **가변이 강제되는 환경**

JPA Entity는 불변 적용이 어렵다

> Hibernate는 ==빈 객체를 먼저 만들고 나중에 값을 setter로 채우는 방식==으로 동작하기 때문에, Entity는 구조적으로 가변일 수밖에 없다

```java
// 1. 기본 생성자로 빈 객체 먼저 만든다
User user = new User();

// 2. 그 다음 DB 컬럼 값을 setter로 하나씩 채운다
user.setId(1L);
user.setName("홍길동");
```

> 또한, Hibernate는 지연 로딩을 위해 프록시 객체도 Entity 클래스를 상속해서 만드는데,  
`final class`면 상속 자체가 막혀버린다

```java
public final class User { // 불변을 위해 final 선언하면

// Hibernate가 내부에서 만드는 프록시 (ByteBuddy 라이브러리로 런타임에 생성)
public class User$HibernateProxy extends User { // ← User를 상속할 수 없다

```

따라서 Entity 안에서 값으로 취급해도 되는 필드를 VO 로 관리하는 방법을 고려한다

```java
@Entity
public class User { // Entity 자체는 가변 — 어쩔 수 없음

    @Id
    private Long id;

    @Embedded
    private Email email; // VO — 이 부분만큼은 불변으로 관리
}
```


<br/>

✨ **설계 비용**

불변 객체는 생성 시점에 모든 값이 확정되어 있어야 한다

처음부터 불변으로 설계해야 하므로 사전 고민이 필요하다

### 불변 객체에서 실수했던 것

> 불변 객체의 필드가 가변인 경우를 조심해야 한다

![[불변객체_실수_리뷰_코멘트_1.png]]

불변객체 `Baord`에 대한 리뷰를 받았다

평소 카프카는 의미 없는 질문을 하지 않기에, 분명 내 코드에 문제가 있다고 생각하고 꼼꼼히 살펴봤다


![[불변객체_실수_피드백_2.png]]


<br/>

내가 빼먹은 건 ==생성시점의 방어적 복사==!

외부에서 `Map` 를 만들어 `Baord` 생성자에 인자로 넣어주게 될텐데,
객체 생성 시점에 방어적 복사를 하지 않는다면 외부와 `Baord` 모두 같은 주소의 `Map`을 사용하게 된다

```java
public final class Board {
    private final Map<Position, Piece> pieces; // ← final이지만 맵 내용은 바꿀 수 있음!

    public Board(Map<Position, Piece> pieces) {
        this.pieces = pieces; // ← 외부 리스트 참조 공유 — 위험
    }

    public Map<Position, Piece> getPieces() {
        return pieces; // ← 외부에서 .put() .remove() 가능
    }
}
```

## 동등성 vs 동일성

> VO가 뭔진 아직 모르겠으나 아무튼 VO를 이해하기 위한 필수 전제  
> 
> Java에서 "같다"는 말은 두 가지 의미가 있다

---

### 개념

| 구분             | 의미                          | Java 연산자/메서드 |
| -------------- | --------------------------- | ------------ |
| 동일성 (Identity) | ==같은 객체==인가? (메모리 주소가 같은가?) | `==`         |
| 동등성 (Equality) | ==같은 값==인가? (의미적으로 동등한가?)   | `equals()`   |

---

### 코드로 이해하기

VO 는 다음과 같이 동작한다

```java
Piece p1 = new Piece(HAN, CHA);
Piece p2 = new Piece(HAN, CHA);

System.out.println(p1 == p2);       // false — 다른 객체 (주소 다름)
System.out.println(p1.equals(p2));  // true  — 값이 같음
```

---

### Object의 기본 동작은 동일성이다

`equals()`를 오버라이드하지 않으면 **기본적으로 `==`(동일성) 과 동일하게 동작한다**

```java
public class Piece {

    private final Side side;
    private final Type type;

    // equals 오버라이드 안 함
}

Piece p1 = new Piece(HAN, CHA);
Piece p2 = new Piece(HAN, CHA);

System.out.println(p1.equals(p2)); // false ← 다른 객체니까
System.out.println(p1 == p2);      // false
```

> 값이 같아도 다르다고 판단한다

---

### 동등성은 어떻게 보장할 수 있을까?

✨ **equals + hashCode 규약**

> `equals()`를 오버라이드하면 ==반드시 hashCode()도 오버라이드==해야 한다

일단 결론부터 말하면, 위 규약을 지키지 않을 경우 `Map` 이나 `Set` 에서 동등성이 보장되지 않는다

그럼 `Map`/`Set` 을 안 쓰면 `equals` 만 해도 되냐?

사실 맞는 말이다.

하지만, 보통 `나중에 Map/Set 을 안 쓸 것이다`를 보장하기 어렵기 때문에 

`equals` 오버라이드할 때 `hashCode`도 같이 하는 게 관례이다

<br/>

✨ **Map/Set 의 동작 방식**

만약 위 규약을 제대로 지키면 아래처럼 동작한다

```
p1 추가:
	1단계: hashCode = X → 버킷[X]에 넣자
	버킷[X] 비어있음 → 저장 
	
p2 추가: 
	1단계: hashCode = X → 버킷[X] 확인
	버킷[X]에 뭔가 있음 → 2단계 진입 
	2단계: p1.equals(p2) = true → 중복! 저장 안 함
```

`HashMap`, `HashSet`은 `hashCode()`로 버킷을 찾고, `equals()`로 최종 비교한다

<br/>


✨ **equals 만 구현하면?**

`hashCode()`를 오버라이드 하지 않으면 같은 값의 객체가 Set에 각각 저장되는 버그가 발생한다

```java
Piece p1 = new Piece(HAN, CHA);
Piece p2 = new Piece(HAN, CHA);

System.out.println(p1.equals(p2)); // true (equals override)

Set<Piece> set = new HashSet<>();
set.add(p1);
set.add(p2);
System.out.println(set.size()); // 2 (중복 제거 안 됨)
```


<br/>

✨ **제대로 구현해보면**

아래는 오버라이드의 예시이다

```java
public class Piece {

    private final Side side;
    private final Type type;

    @Override  
	public boolean equals(Object obj) {  
	    if (obj == this) {  
	        return true;  
	    }    
	    if (obj == null || obj.getClass() != this.getClass()) {  
	        return false;  
	    }    
	    var that = (Piece) obj;  
	    return Objects.equals(this.side, that.side) && Objects.equals(this.type, that.type);  
	}

    @Override
    public int hashCode() {  
	    return Objects.hash(side, type);  
	}
}
```

---

### 나는 언제 동등성을 구현할 것인가?

#### 동일성으로 구현하는 경우

✨ **상태 값이 같아도 다른 객체로 판단하는 경우**

같은 엔티티를 가리키는가? (JPA Entity는 보통 ID로 동일성 판단)

<br/>


#### 동등성으로 구현하는 경우

✨ **상태 값이 같으면 같은 객체로 판단하는 경우**

ex) Piece 의 Side와 Type이 같으면 같은 종류의 기물이다

---

### Java 16+ Record의 경우

`record`는 `equals()`와 `hashCode()`를 **자동으로** 모든 필드 기준으로 생성해준다

```java
record Piece(Side side, Type type) {}

Piece p1 = new Piece(HAN, CHA);
Piece p2 = new Piece(HAN, CHA);
System.out.println(p1.equals(p2)); // true (자동)
```

## 방어적 복사

> 불변 객체가 ==가변 객체를 필드로 가질 때==,  
> 
> 외부에서 그 가변 객체를 통해 내부 상태를 바꾸지 못하도록 ==복사본을 만드는 기법==

---

### 왜 필요한가?

`final` 필드라도, 그 필드가 가변 객체(`List`, `Map` 등)를 참조하면 ==참조 자체는 변경 불가지만 참조된 객체의 내용은 바꿀 수 있다==

```java
public final class Board {

    private final Map<Position, Piece> pieces;

    public Board(Map<Position, Piece> pieces) {
        this.pieces = pieces;  // ← 위험: 외부 리스트 참조 공유
    }

    public Map<Position, Piece> getPieces() {
        return pieces;        // ← 위험: 내부 참조 노출
    }
}
```

```java
// 이렇게 되면:
Map<Position, Piece> pieces = new HashMap<>(Map.of(position, piece));
Board board = new Board(pieces);

pieces.put(position, piece);  // Board 내부도 바뀜
board.getPieces().put(position, piece); // getter로도 내부 변경 가능
```

<br/>

✨ **방어적 복사를 적용하면 해결할 수 있다**

```java
public final class Board {

    private final Map<Position, Piece> pieces;

    public Board(Map<Position, Piece> pieces) {
        this.pieces = Map.copyOf(pieces); // 생성자에서
    }

    public Map<Position, Piece> getPieces() {
        return Map.copyOf(pieces); // getter 에서
    }
}
```
```java
Map<Position, Piece> pieces = new HashMap<>();  
Board board = new Board(pieces);  

pieces.put(departure, piece); // 영향 없음
```

---

### 생성 방어적 복사에서 검증 먼저? 방어적 복사 먼저?

생성자에서 유효성 검사를 할 때, ==반드시 복사 → 검사== 순서로 해야 한다

```java
// 잘못된 순서
public Board(Map<Position, Piece> pieces) {
    validate(pieces);
    this.pieces = Map.copyOf(pieces); // 검사 후 복사 사이에 값이 바뀔 수 있음
}

// 올바른 순서
public Board(Map<Position, Piece> pieces) {
    this.pieces = Map.copyOf(pieces);
    validate(this.pieces);
}
```

<br/>

✨ **TOCTOU란**

> Time-Of-Check Time-Of-Use

검사한 시점과 사용하는 시점 사이에 값이 바뀌는 것

```java
// 잘못된 순서
public Board(Map<Position, Piece> pieces) {
    validate(pieces);               // 검사
    this.pieces = Map.copyOf(pieces); // 복사 (저장)
}
```

검사와 복사 사이에 다른 스레드가 끼어들 수 있다.

```
스레드 A: validate(pieces) 통과
    ← 스레드 B: pieces.put(position, piece)
                                    
스레드 A: Map.copyOf(pieces) 저장  ← 이미 오염된 Map을 복사
```

검사는 통과 이후에 저장되는 기물은 검사를 못한다

단일 스레드 웹 요청에서는 이 공격이 현실적으로 발생하기 어렵지만, 

멀티스레드 환경을 대비해서 습관적으로 지키는 게 좋다

---

### 얕은 복사 VS 깊은 복사

얕은 복사의 경우, 컬렉션 껍데기만 새로 만들고, 안의 객체는 그대로 참조가 공유된다

```java
Piece piece = new Piece(Side.HAN);
Map<Position, Piece> original = new HashMap<>();
original.put(position, piece);

Map<Position, Piece> copy = Map.copyOf(original); // 얕은 복사
```

```java
piece.setSide(Side.CHO);

original.get(position).getSide(); // CHO 
copy.get(position).getSide(); // CHO (같이 바뀜)
```


깊은 복사의 경우, 컬렉션도, 안의 객체도 전부 새로 만든다.

```java
Map<Position, Piece> deepCopy = new HashMap<>();
for (var entry : original.entrySet()) { 
	deepCopy.put(entry.getKey(), new Piece(entry.getValue().getSide())); // Piece도 새로 생성 
}
```
```java
piece.setSide(Side.CHO);

original.get(a1).getSide(); // CHO
deepCopy.get(a1).getSide(); // HAN (영향 없음)
```

<br/>

✨ **얕은 복사가 더 좋은가? 깊은 복사가 더 좋은가?**

얕은 복사는 로직이 간단하지만, 내부 필드가 가변이라면 무결성이 떨어진다

깊은 복사는 로직이 복잡하지만, 내부 필드가 가변이어도 무결성을 지킬 수 있다

따라서 만약 불변 객체가 갖는 필드도 불변 객체라면, 얕은 복사로도 충분하다

단, ==내부 필드가 가변이라면 깊은 복사를 하거나, 내부 필드를 불변 객체로 만들어준다==

---

### 나는 언제 방어적 복사를 쓸 것인가?

✨ **불변 객체의 인스턴스 변수가 가변 객체인가?**

생성 시점에 복사해서 필드 초기화 하기 (복사 초기화 -> 검사)

만약 내부 필드가 가변이라면 불변으로 바꾸거나, 깊은 복사 하기


<br/>

✨ **getter가 가변 객체를 반환하는가?**

외부에서 해당 객체의 내부 상태를 조작하지 못하도록 복사해서 반환하기

## VO

> Value Object
> 
> 값 자체가 식별자인 객체  
> 
> ID가 아니라 ==모든 필드의 값이 같으면 같은 객체==로 취급한다

---

### 개념

DDD(도메인 주도 설계)에서 나온 개념으로,  도메인에서 값 그 자체를 표현하는 객체다

|       | Entity                         | VO                           |
| ----- | ------------------------------ | ---------------------------- |
| 식별 기준 | ID (고유 식별자)                    | 값 전체                         |
| 가변/불변 | 가변 (상태 변함)                     | 불변                           |
| 예시    | User (userId), Order (orderId) | Money, Address, Email, Color |

---

### 왜 쓰는가?

✨ **원시 타입의 의미 손실 방지 (Primitive Obsession 해결)**

원시 타입(`int`, `String`)은 값만 있고 의미가 없다

```java
// 이게 뭘 의미하는 점수인지? 음수는 가능한가?
int score = 10;

// VO로 감싸면 의미가 생기고 검증이 따라온다
Score score = new Score(-1000); // 생성 시점에 터짐
```


<br/>

✨ **흩어진 유효성 검사를 한 곳으로**

```java
// VO 없이: 점수 검증이 여기저기
if (score < 0) { ... } // Service
if (score < 0) { ... } // Repository
if (score < 0) { ... } // Controller

// VO 있으면: Score 생성자 한 곳에만
Score score = new Score(-1000); // 여기서 바로 터짐
```

도메인 로직이 한 곳에 모이니 중복도 줄고, 고칠 때도 한 곳만 고친다

<br/>


✨ **안전한 공유**

불변이기 때문에 여러 객체가 같은 VO 인스턴스를 참조해도 문제 없다

→ [[02. 불변(Immutability)]]의 "공유해도 안전" 과 같은 맥락이다

---

### 구현 조건

1. 불변 (모든 필드 private final, setter 없음)
2. equals/hashCode — 값 기준으로 오버라이드
3. 유효성 검사 — 생성자에서 처리 (잘못된 VO는 만들어지지 않아야 함)
4. (선택) 가변 필드가 있으면 방어적 복사 → [[#방어적 복사]]

```java
public final class Email {
    private final String value;

    public Email(String value) {
        if (value == null || !value.contains("@"))
            throw new IllegalArgumentException("유효하지 않은 이메일: " + value);
        this.value = value.toLowerCase().trim();
    }

    public String getValue() { return value; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Email)) return false;
        return value.equals(((Email) o).value);
    }

    @Override
    public int hashCode() { return Objects.hash(value); }

    @Override
    public String toString() { return value; }
}
```

---

### 단점도 있지 않을까?


✨ **수정 비용**

만약, 중간에 필드 하나를 추가해야 한다면 파급 범위가 크다

이번에도 `Piece` 에 `PieceType` 필드를 추가했다가 모든 생성자 호출 코드를 다 수정해야 했다

<br/>


✨ **프레임워크와의 마찰**

JPA에서 VO를 사용하려면 `@Embeddable`, `@Embedded` 를 써야 한다

Json 직렬화를 위해 사용하는 Jackson 라이브러는 기본 생성자로 객체를 만들고 getter 로 값을 읽는다

근데 VO 는 기본 생성자가 없어서  `InvalidDefinitionException` 가 발생한다

```java
@JsonCreator
public Email(@JsonProperty("value") String value) {
	this.value = value;
}
```

> 이런식으로 별도 설정을 해주거나, `Record` 쓰면 `Jackson 2.12+` 부터 자동 지원된다

<br/>


✨ **과도한 객체 생성**

요청마다 `new Email(...)`, `new Money(...)` 를 계속 만든다

대부분은 GC가 처리하지만, 성능이 민감한 구간에선 부담이 될 수 있다

---

### VO를 처음 도입하고 나서 실수했던 것

내가 만든 `Position` VO는 `final` 필드에 `equals/hashCode` 도 잘 구현했다고 생각했는데,

Map의 키로 쓰니 예상과 다르게 동작했다

원인은 [[#동등성 vs 동일성]] 에서 설명한 것처럼 ==equals 만 구현하고 hashCode 를 빠트렸기 때문이다==

```java
Position p1 = new Position(1, 'a');
Position p2 = new Position(1, 'a');

Map<Position, Piece> map = new HashMap<>();
map.put(p1, piece);

map.get(p2); // null — equals는 true인데 hashCode가 달라서 못 찾음
```

→ ==VO는 equals와 hashCode를 반드시 같이 오버라이드해야 한다.==

### 나는 언제 VO를 쓸 것인가?

나는 아래 사항이 하나라도 해당되면 VO 도입을 고려한다

<br/>


✨ **같은 유효성 검사 코드가 두 곳 이상 흩어져 있는가?**

검증 코드가 반복된다면 VO로 묶는다


<br/>

✨ **두 파라미터가 항상 같이 다니는가?**

`int row`, `int column` 는 항상 쌍으로 등장하면 `Position` VO 후보

<br/>


✨ **두 객체의 모든 값이 같으면 같은 것인가?**

## Record

> VO를 보일러플레이트 없이 표현하는 불변 데이터 클래스  
> 
> Java 16에서 정식 도입. (Java 14, 15에서 Preview)

---

### 개념

기존에 VO 하나를 만들려면 구현해야 할 코드가 너무 많다

```java
// 기존 방식 — 매번 반복되는 보일러플레이트
public final class Money {
    private final int amount;
    private final String currency;

    public Money(int amount, String currency) {
        this.amount   = amount;
        this.currency = currency;
    }

    public int    amount()   { return amount; }
    public String currency() { return currency; }

    @Override public boolean equals(Object o) { ... }  // 직접 구현
    @Override public int hashCode()           { ... }  // 직접 구현
    @Override public String toString()        { ... }  // 직접 구현
}
```

Record를 쓰면 정말 간단해진다

```java
// Record — 한 줄
record Money(int amount, String currency) {}

Money m = new Money(1000, "KRW");
m.amount();    // 1000
m.currency();  // "KRW"
```

---

### 자동으로 생성되는 것들

| 자동 생성                       | 설명                                       |
| --------------------------- | ---------------------------------------- |
| 생성자 (canonical constructor) | 모든 필드를 받는 생성자                            |
| 접근자 메서드                     | `side()`, `type()` (getter 아님 — 필드명과 동일) |
| `equals()`                  | 모든 필드 값 기준 비교                            |
| `hashCode()`                | 모든 필드 기반                                 |
| `toString()`                | `Piece[side=HAN, type=CHA]` 형태           |

---

### 왜 쓰는가?


✨ **보일러플레이트 제거**

VO를 만들 때마다 반복되는 코드를 지워버릴 수 있다

`equals`, `hashCode`, `toString`, 접근자 메서드를 직접 작성하지 않아도 된다

<br/>


✨ **실수 방지**

`hashCode` 만 빠트리는 실수 → Record는 자동으로 둘 다 생성하니 빠트릴 수 없다

<br/>


✨ **읽기 쉬운 선언**

클래스 이름 한 줄만 봐도 이 객체가 어떤 값을 갖는지 바로 알 수 있다

---

### 생성자가 없는데, 어떻게 유효성을 검사하지?


`compact constructor` 에서 필드 초기화 직후의 메서드를 추가할 수 있다

```java
public record Row(int index) {
    // compact constructor — 파라미터 선언 없이 검사만
    public Row {  
	    validateRange(index);  
	}
}
```

---

### 단점도 있지 않을까?


✨ **상속 불가**

`java.lang.Record`를 암묵적으로 상속하기 때문에 다른 클래스를 `extends` 할 수 없다

```java
// Record를 선언하면
record Money(int amount, String currency) {}

// 컴파일러가 내부적으로 이렇게 바꿈
final class Money extends java.lang.Record { // 이미 부모가 정해짐
    ...
}
```

부모 자리가 `java.lang.Record`로 이미 채워졌으니 다른 클래스를 상속할 수 없다

```java
// = final class Money extends Record, CommonVO → 다중 상속이라 안 됨
record Money(int amount, String currency) extends CommonVO { }
```


<br/>

✨ **JPA Entity로 사용 불가**

기본 생성자가 없고, 불변이라 Hibernate가 프록시 생성 및 상태 변경을 제어하지 못한다


<br/>


✨ **Java 버전 의존성**

Java 11 이하 프로젝트에서는 사용이 불가능해서 일반 `final class`로 구현해야 한다

---

### 나는 언제 Record를 쓸 것인가?

나는 아래 사항이 모두 충족되면 Record를 선택한다

<br/>


✨ **이 객체가 VO 또는 DTO인가?**

데이터 전달이 목적이고, 식별자 없이 값으로만 비교해도 되는 경우에 사용한다

<br/>


✨ **JPA Entity가 아닌가?**

Entity라면 Record 사용 불가능 하다

<br/>


✨ **상속 구조가 필요 없는가?**

상속이 필요하면 일반 class로 설계한다

### 불변을 선택하는 기준

아래 중 하나라도 해당하면 **불변 우선 검토**

| 기준 | 예시 |
|------|------|
| 값 자체가 개념인 경우 | `Money`, `Email`, `Coordinates` |
| 여러 객체/스레드가 공유하는 경우 | 설정값, 공통 코드 |
| 변경 이력이 중요한 경우 | 이벤트 소싱 — 새 상태를 새 객체로 |
| 생성 후 절대 안 바뀌어야 하는 경우 | 주문 생성 시각, 가입 이메일 |
| 팀원이 실수로 바꿀 위험이 있는 경우 | setter 열어두면 여기저기서 건드림 |

### 가변을 유지하는 기준

| 기준             | 예시                              |
| -------------- | ------------------------------- |
| JPA Entity     | Hibernate 요구사항                  |
| 변경이 핵심 도메인 행위  | 주문 상태: PENDING → PAID → SHIPPED |
| 프레임워크가 가변을 요구  | Jackson 역직렬화, Spring Form       |
| 성능 측정 후 불변이 병목 | 단, 드문 경우 이므로 먼저 측정하고 나중에 최적화    |

### VO로 만들 기준

❓ **이 데이터에 고유한 ID가 없어도 되는가?**

❓ **값이 같으면 같은 것으로 취급해도 되는가?**

❓ **같은 파라미터 묶음이 여러 메서드에 반복해서 등장한다**

❓ **유효성 검사가 여러 군데 흩어져 있다 (중복)**

❓ **이 필드가 단순 String/int인데 특정 형식/범위가 있는가?**

❓ **JPA Entity에 너무 많은 책임이 있는가?**
