## 발단

애플 앱스토어에 로그인을 구현할 경우, Apple 소셜 로그인이 필수적으로 요구된다

그래서 인증 방식을 가장 간단한 방법인 세션으로 구현하려고 했다

<br/>

근데 바리바리는 iOS 네이티브 앱이다

세션은 쿠키 기반으로 동작하는데, 브라우저는 쿠키를 자동으로 관리해주는데 네이티브 앱에선 자동 관리가 안 된다

그래서 iOS 측에서 쿠키를 수동으로 파싱하고 저장하고 붙여야 한다

서버도 마찬가지로 Spring Session 기본 동작은 쿠키로 세션 ID를 주고받는다  
헤더로 우회하려면 `HeaderHttpSessionIdResolver`를 따로 설정해야 한다

⚠️ **결국 세션을 쓰려면 앱, 서버 둘 다 세션의 기존 구현을 우회해야 한다**

<br/>

❓ 그럼 애초에 헤더 기반으로 동작하는 인증 방식이 있지 않을까?

## 세션 동작 원리

세션은 서버 메모리에 상태를 저장한다

```
로그인 요청
-> 서버: 메모리에 "sessionId-abc: user123 로그인 중" 저장
-> 응답: Set-Cookie: JSESSIONID=abc

이후 요청
-> 브라우저: Cookie: JSESSIONID=abc 자동 첨부
-> 서버: 메모리 조회 -> 인증 확인
```

브라우저는 이걸 자동으로 해주기 때문에 개발자가 신경 쓸 게 없다

그리고 서버가 상태를 갖기 때문에 세션을 삭제해서 즉시 무효화도 가능하다

<br/>

## 단점도 있지 않을까?

⚠️ **다중 서버일 때 로그인 상태 공유가 안 된다**

세션은 메모리에 로그인 상태를 저장한다는 특징이 있다

서버가 2대 이상이면 A서버 메모리에만 세션이 있기 때문에 B서버로 요청이 가면 모른다

Redis 같은 외부 저장소가 필요해진다

(현재 서버는 단일 서버라서 문제가 되지 않는다)

<br/>


⚠️ **쿠키는 브라우저 전용 설계다**

네이티브 앱은 쿠키를 자동으로 관리하지 않는다

쿠키를 유지하기 위해서는 앱개발자가 쿠키를 직접 파싱하고 붙이는 과정이 필요하다

그렇다고 헤더로 세션 정보를 주고받기에는 앱/서버 개발자 모두 추가 개발이 필요하고,  
세션의 기존 구현을 거슬러서 우회해야 한다

## JWT 구조

JWT는 문자열이다

```
eyJhbGciOiJSUzI1NiIsImtpZCI6IjEyMyJ9   <- Header (알고리즘, kid)
.
eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxNzAwfQ  <- Payload (sub, 만료시간 등)
.
SIGNATURE                                 <- 서명
```

각 부분은 Base64 인코딩이라 디코딩하면 읽을 수 있다

서버가 아무것도 저장하지 않아도 된다

<br/>

## 조작이 가능하지 않을까?

✨ **조작은 가능하지만, 조작 여부를 알 수 있다**

서버의 비밀키로 서명했기 때문에 Payload를 누군가 조작하면 서명이 맞지 않는다

```
검증 흐름
-> 토큰 수신
-> Header + Payload + 서버 비밀키로 서명 재계산
-> 토큰의 서명과 비교 -> 일치하면 신뢰
```

<br/>

✨ **토큰을 헤더로 주고받는 구조다**

```
Authorization: Bearer eyJhbGci...
```

네이티브 앱 입장에서 문자열을 저장하고 헤더에 붙이는 건 자연스럽다

쿠키 수동 처리 같은 우회가 필요 없다

<br/>

## 단점은 없을까?

⚠️ **발급한 토큰을 만료 전에 무효화할 수 없다**

서버가 상태를 갖지 않기 때문에 토큰이 탈취당해도 막을 방법이 없다

만료되기 전까지 그 토큰은 유효하다

## Apple ID Token

Apple 로그인을 구현하려면 Apple이 발급하는 JWT를 다뤄야 한다

```
[1] iOS 앱 -> Apple: 로그인 요청
[2] Apple -> iOS 앱: ID Token 발급
[3] iOS 앱 -> 우리 서버: ID Token 전달
[4] 우리 서버 -> Apple 공개키로 서명 검증
[5] 검증 통과 -> sub, email 추출
```

<br/>

## Payload에 뭐가 들어있나?

```json
{
  "sub": "000123.abc456",
  "email": "user@icloud.com",
  "exp": 1700000000
}
```

✨ **`sub`가 핵심이다**

Apple이 이 사용자에게 영구적으로 부여한 고유 ID다

회원 식별은 이걸로 한다

<br/>

⚠️ **이메일은 첫 로그인 시에만 준다**

재로그인 시에는 email이 없을 수 있다

<br/>

## 서명은 어떻게 검증하나?

Apple의 공개키를 `https://appleid.apple.com/auth/keys` 에서 받아서 검증한다

토큰 Header의 `kid` 값과 매칭되는 공개키로 RS256 서명을 확인한다

### 💬 RS256?

RSA 알고리즘으로 서명하고 SHA-256으로 해싱하는 방식이다

Apple이 비밀키로 서명하고, 누구나 공개키로 검증할 수 있다

<br/>

❓ 이 토큰을 우리 서비스 인증에 그대로 쓰면 안 될까?

## Apple ID Token을 그대로 쓰면 안 되는 이유

Apple ID Token을 우리 서비스 인증에 그대로 쓰면 안 된다

탈취 문제가 아니다

<br/>


⚠️ **우리가 통제할 수 없어서다**

만료 시간을 Apple이 정한다

어떤 서비스에나 제출할 수 있는 범용 증명서다

우리가 무효화할 권한도 없다

<br/>

## 그래서 어떻게 하나?

✨ **Apple ID Token은 신원 확인용으로만 쓰고 버린다**

```
Apple ID Token
-> 서명 검증 (Apple 공개키로)
-> sub, email 추출
-> 버림

-> 우리 JWT 발급
   (만료 시간, 용도 모두 우리가 통제)
```

우리 JWT는 만료 시간을 우리가 정하고, `aud` 클레임으로 바리바리 전용임을 명시할 수 있다

<br/>

❓ 근데 우리 JWT도 탈취당하면 무효화할 수 없다는 문제가 그대로 아닌가?

## Access-Refresh Token 분리

JWT는 만료 전에 무효화할 수 없다

탈취당해도 만료될 때까지 공격자가 쓸 수 있다

<br/>

## 어떻게 피해를 줄이나?

✨ **수명을 짧게 만든다**

Access Token 의 만료 시간을 1시간으로 만들면 탈취당해도 최대 1시간만 유효하다


<br/>


## 그럼 1시간마다 재로그인..?

재로그인 자동화가 가능할까?

가능하다

<br/>

✨ **Refresh Token (30일)을 별도로 발급한다**

```
[정상 흐름]
Access Token 만료
-> Refresh Token으로 새 Access Token 재발급
-> 사용자는 재로그인 없이 유지

[탈취 시나리오]
Access Token 탈취 -> 최대 1시간만 유효 -> 피해 제한
Refresh Token 탈취 -> DB에서 삭제 -> 즉시 무효화 가능
```

Access Token은 짧은 수명으로 리스크를 줄이고

Refresh Token은 DB 에 저장해뒀다가 재로그인 시 활용한다

## 내 기준

## 핵심 흐름

```
세션으로 구현하려 했다
    │
    ▼
iOS 네이티브 앱에서는 쿠키 자동 관리가 없다
앱/서버 양쪽에서 세션 설계를 우회해야 한다
    │
    ▼
JWT는 처음부터 토큰을 헤더로 주고받는 구조다
우회 없이 자연스럽게 붙는다
    │
    ▼
단, JWT는 탈취 시 즉시 무효화가 안 된다
-> Access Token 수명을 짧게 (1시간)
-> Refresh Token을 DB에 저장해 통제권 확보
```

---

## 핵심

> 기술 선택의 기준은 그 기술이 클라이언트 환경과 얼마나 자연스럽게 맞는가다
> 세션이 더 안전하고 단순해도, 네이티브 앱과의 연동에서 그 단순함을 다 까먹는다

---

## 실전 체크리스트

❓ **세션을 쓸지 JWT를 쓸지 고민되는가?**

클라이언트가 브라우저면 세션이 더 단순하다

클라이언트가 iOS/Android 네이티브 앱이면 JWT가 자연스럽다

<br/>

❓ **JWT 탈취 시 무효화가 걱정되는가?**

Access Token 수명을 짧게 가져가면 피해를 제한할 수 있다

Refresh Token을 DB에 저장하면 서버에서 직접 무효화할 수 있다

<br/>

❓ **Apple ID Token을 그대로 인증에 쓰려 하는가?**

Apple ID Token은 신원 확인용이다

만료 시간과 무효화 권한이 Apple에 있어 우리 서비스 인증에 쓰면 안 된다

검증 후 버리고 우리 JWT를 새로 발급해야 한다
