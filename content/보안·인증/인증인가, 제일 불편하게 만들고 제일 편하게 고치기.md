## 이 요청을 보낸 사람이 누군지 어떻게 알지?

## 이름만 입력하면 누구든 믿어야 하나?

처음 만든 예약 서비스는 이름을 입력하면 예약이 됐다

서버 입장에서는 이 요청을 실제로 누가 보냈는지 알 방법이 없었다

```
POST /reservations
{ "name": "고진", "date": "2026-06-01", ... }
```

이름 필드에 아무 값이나 넣으면 그 사람인 척 할 수 있다

---

## 뭐가 문제인가?

⚠️  **다른 사람의 예약을 수정하거나 취소할 수 있다**

이름만 알면 그 사람인 척 요청을 보낼 수 있다

<br/>

⚠️  **매니저가 다른 매장 예약에도 접근할 수 있다**

매니저 권한이 있어도, 자기 매장 예약만 관리해야 한다

---

## 인증과 인가, 뭐가 다른가?

> ==인증(Authentication)==: 이 요청을 보낸 사람이 누구인가  
> ==인가(Authorization)==: 그 사람이 이걸 해도 되는가

로그인 -> 인증  
내 예약만 수정 가능 -> 인가

둘은 순서가 있다. 누구인지 모르면 뭘 할 수 있는지도 판단할 수 없다

---

## 어떻게 해결할 수 있나?

서버가 '이 사람이 누군지' 기억하는 방법이 필요하다

대표적인 두 가지다

| 방식 | 원리 | 특징 |
| ---- | ---- | ---- |
| 세션 | 서버가 로그인 상태를 저장, 클라이언트는 세션 ID만 보냄 | 서버에 상태 저장 |
| 토큰 | 클라이언트가 서명된 토큰을 매 요청마다 첨부 | 서버 무상태 |

이번엔 세션 방식으로 구현했다

## 매번 컨트롤러에서 검증해야 된다고?

## 왜 컨트롤러에서 직접 꺼냈나?

'내 예약 목록 조회하기' 기능에 해당하는 컨트롤러를 수정하려 했다.

찾아보니 서버 메모리 상에 저장된 세션 정보는 컨트롤러 파라미터에 HttpSession 을 두면 가져올 수 있다고 한다


<br/>

이름만 입력하던 예약 서비스에서 세션 기반 인증으로 수정했다

```java
@GetMapping("/reservations")
public ResponseEntity<List<ReservationResponse>> getReservations(HttpSession session) {
    Member member = (Member) session.getAttribute("member");
    if (member == null) {
        throw new UnauthorizedException();
    }
    // 실제 로직
}
```

---

## 뭐가 불편했나?


⚠️  **중복 코드가 쌓인다**


'내 예약 생성하기'를 구현하려고 했더니

또 컨트롤러에서 직접 세션을 꺼내서 검증해야 했다

매번 컨트롤러를 생성할 때마다 인가처리 코드를 적어줘야 하나...?

<br/>

⚠️  **실수로 검증을 빠뜨릴 수 있다**

새 API를 추가할 때 인증 코드를 빠뜨려도 컴파일 에러가 나지 않는다

<br/>

⚠️  **인증 로직이 바뀌면 모든 컨트롤러를 수정해야 한다**

세션 키 이름 하나만 바꿔도 전체를 찾아다녀야 한다

## 예외 응답을 JSON으로 직접 써야 한다고?

## 왜 필터를 선택했나?

컨트롤러마다 반복되는 인증 코드를 없애고 싶었다

전역에서 요청을 가로챌 수 있는 Filter를 도입했다

---

## 어떻게 구현했나?

Filter에서 세션을 꺼내 인증 여부를 확인하고, 실패하면 예외를 던졌다

```java
public class AuthFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    
    if (session == null || session.getAttribute(SESSION_KEY) == null) {  
	    writeErrorResponse(httpResponse, ErrorCode.UNAUTHORIZED_MEMBER);  
	    return;  
	}  
	
	Member member = (Member) session.getAttribute(SESSION_KEY);
	if (httpRequest.getRequestURI().startsWith("/admin") && !member.isAdmin()) { 
		writeErrorResponse(httpResponse, ErrorCode.FORBIDDEN);  
		return;  
	}
        
	chain.doFilter(request, response);
    }
    
    private void writeErrorResponse(HttpServletResponse httpResponse, ErrorCode error) throws IOException {  
	    httpResponse.setStatus(error.getCode().value());  
	    httpResponse.setContentType("application/json");  
	    httpResponse.setCharacterEncoding("UTF-8");  
	    httpResponse.getWriter().write(  
	        OBJECT_MAPPER.writeValueAsString(ErrorResponse.of(error))  
	    );  
	}
}
```

인증 코드는 컨트롤러에서 사라졌고, 전역 처리도 잘 됐다

---

## 뭐가 불편했나?

⚠️ **커스텀 에러 응답 형식을 정형화해뒀는데 재사용할 수 없었다**

왜 @ControllerAdvice가 안 잡혔나?

> Filter는 ==Servlet 컨테이너 레벨==에서 동작한다  
> DispatcherServlet 앞에 있기 때문에 @ControllerAdvice가 예외를 잡지 못한다


`ObjectMapper`로 JSON을 직접 작성해야 했다

```java
httpResponse.setStatus(error.getCode().value());  
httpResponse.setContentType("application/json");  
httpResponse.setCharacterEncoding("UTF-8");  
httpResponse.getWriter().write(  
	OBJECT_MAPPER.writeValueAsString(ErrorResponse.of(error))  
);  
```


<br/>


⚠️  **인증 이후에도 컨트롤러에서 세션을 꺼내야 했다**

필터가 인증은 막아줬지만, 컨트롤러에서 Member 객체가 필요할 때는 여전히 세션을 직접 꺼내야 했다

## 인터셉터로 옮겼는데 세션은 또 꺼내야 한다고?

## 왜 인터셉터로 옮겼나?

Filter의 예외 처리 문제를 해결하고 싶었다

Filter는 DispatcherServlet 앞에서 동작하기 때문에 @ControllerAdvice가 예외를 잡지 못한다

Spring MVC 안에서 동작하는 Interceptor로 옮기면 해결될 것 같았다

---

## 어떻게 구현했나?

`HandlerInterceptor`의 `preHandle`에서 세션을 검증하고, 실패하면 예외를 던졌다

```java
public class AuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        HttpSession session = request.getSession(false);  
  
		if (session == null) {  
		    throw new RoomEscapeException(ErrorCode.UNAUTHORIZED_MEMBER);  
		}  
		Member member = (Member) session.getAttribute(MEMBER_SESSION_KEY);  
		if (member == null) {  
		    throw new RoomEscapeException(ErrorCode.UNAUTHORIZED_MEMBER);  
		}  
		  
		if (request.getRequestURI().startsWith("/admin") && !member.isAdmin()) {  
		    throw new RoomEscapeException(ErrorCode.FORBIDDEN);  
		}  
		  
		return true;
    }
}
```

---

## 뭐가 해결되고 뭐가 남았나?

> Interceptor는 ==DispatcherServlet 안==에서 동작한다  
> @ControllerAdvice가 예외를 정상적으로 잡아준다

✨ **커스텀 에러 응답 포맷을 그대로 재사용할 수 있었다**

<br/>

⚠️  **그런데 세션 추출 문제는 그대로였다**

인터셉터가 인증을 통과시켜줬지만, 컨트롤러에서 Member 객체가 필요할 때는 여전히 직접 꺼내야 했다

```java
@GetMapping("/reservations")
public ResponseEntity<List<ReservationResponse>> getReservations(HttpSession session) {
    Member member = (Member) session.getAttribute("member");
    // ...
}
```

예외 처리 문제는 해결됐지만, 컨트롤러에 세션 추출 코드가 남아있었다

## 컨트롤러 파라미터에 Member가 그냥 오면 안 될까?

## 뭐가 아직 불편했나?

인터셉터가 인증을 막아줬지만, 컨트롤러에는 세션 추출 코드가 여전히 남아있었다

인증이 통과된 이후에는 컨트롤러가 Member 객체를 그냥 받아쓸 수 있으면 좋겠다는 생각이 들었다

---

## 어떻게 해결했나?

`@LoginMember` 커스텀 어노테이션과 `HandlerMethodArgumentResolver`를 도입했다

```java
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface LoginMember {
}
```

```java
public class LoginMemberArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(LoginMember.class);
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ..., NativeWebRequest webRequest, ...) {
	    HttpServletRequest httpRequest = webRequest.getNativeRequest(HttpServletRequest.class);  
	    HttpSession session = httpRequest.getSession(false);  
	    return session.getAttribute(MEMBER_SESSION_KEY);
    }
}
```

컨트롤러 파라미터에 `@LoginMember`를 달면 세션에서 Member를 꺼내 자동으로 주입해준다

```java
@GetMapping("/reservations")
public ResponseEntity<List<ReservationResponse>> getReservations(@LoginMember Member member) {
    // 세션 추출 코드가 사라졌다
}
```

---

## 뭐가 달라졌나?

> 인터셉터가 인증을 막고,  
> 리졸버가 ==Member 주입을 담당==하면서  
> 컨트롤러는 비즈니스 로직만 남게 됐다

<br/>

각 도구의 역할이 분리됐다

| 도구               | 역할                        |
| ---------------- | ------------------------- |
| Interceptor      | 인증 여부 확인, 미인증 요청 차단       |
| ArgumentResolver | 세션 -> Member 변환 후 파라미터 주입 |
| Controller       | 비즈니스 로직만 처리               |

## 고도화 흐름

| 단계 | 방식 | 해결한 것 | 남은 것 |
| ---- | ---- | --------- | ------- |
| 1 | 컨트롤러 직접 검증 | - | 중복 코드, 누락 위험 |
| 2 | + Filter | 전역 처리 | @ControllerAdvice 미적용, 세션 추출 반복 |
| 3 | + Interceptor | 커스텀 예외 처리 | 세션 추출 반복 |
| 4 | + ArgumentResolver | 세션 추출 분리 | - |

---

## 핵심

> Filter와 Interceptor의 차이는 ==동작 위치==다

```
HTTP 요청
    │
    ▼
[Filter]          ← Servlet 컨테이너, @ControllerAdvice 미적용
    │
    ▼
DispatcherServlet
    │
    ▼
[Interceptor]     ← Spring MVC, @ControllerAdvice 적용
    │
    ▼
[ArgumentResolver]
    │
    ▼
Controller
```

## 실전 체크리스트

❓ **Filter를 선택하려 하는가?**

@ControllerAdvice로 예외를 잡을 수 없다

커스텀 에러 응답이 있다면 JSON을 직접 작성해야 한다

<br/>

❓ **Interceptor만 쓰고 있는가?**

컨트롤러에서 세션을 직접 꺼낸다면 ArgumentResolver를 추가할 타이밍이다

<br/>

❓ **ArgumentResolver를 도입했는가?**

`@LoginMember` 같은 커스텀 어노테이션으로 컨트롤러 파라미터를 깔끔하게 만들 수 있다

Spring Security의 `@AuthenticationPrincipal`도 같은 원리다
