## 모바일 앱은 쿠키를 자동으로 저장 안 한다고?

## 웹 브라우저는 뭘 해주고 있었나?

세션 기반 인증은 이렇게 동작한다

```
1. 로그인 요청
2. 서버: 세션 생성 → Set-Cookie: JSESSIONID=abc123
3. 브라우저: 쿠키 자동 저장
4. 다음 요청: Cookie: JSESSIONID=abc123 자동 첨부
5. 서버: 쿠키로 세션 조회 → Member 확인
```

웹 브라우저가 쿠키를 자동으로 저장하고, 자동으로 요청에 붙여줬다

별도 처리 없이도 인증이 유지됐던 이유다

---

## 모바일 앱은 뭐가 다른가?

> 모바일 앱은 ==쿠키를 자동으로 관리하지 않는다==

로그인 응답으로 `Set-Cookie`가 와도 앱이 직접 저장하고 직접 헤더에 추가하지 않으면 다음 요청에 세션 정보가 없다

```
1. 로그인 요청
2. 서버: Set-Cookie: JSESSIONID=abc123
3. 앱: 쿠키 저장 안 됨 (자동 관리 X)
4. 다음 요청: 세션 정보 없음
5. 서버: 세션 없음 → 401 Unauthorized
```

---

## 뭘 해결해야 하나?

쿠키 없이도 인증 상태를 유지할 방법이 필요하다

가장 직관적인 접근은 세션 ID를 쿠키 대신 헤더로 주고받는 것이다

## 세션 ID를 헤더로 넘기면 되지 않을까?

## 왜 헤더를 선택했나?

쿠키를 쓸 수 없다면, 세션 ID를 다른 방법으로 주고받으면 된다

헤더는 모바일 앱이 직접 제어할 수 있다

로그인 응답에 `X-Session-Id` 헤더로 세션 ID를 내려주고, 앱이 저장한 뒤 이후 요청마다 헤더에 담아 보내는 방식을 시도했다

---

## 어떻게 구현했나?

로그인 성공 시 응답 헤더에 세션 ID를 추가했다

```java
@PostMapping("/login")
public ResponseEntity<Void> login(@RequestBody LoginRequest request, HttpSession session) {
    Member member = memberService.login(request);
    session.setAttribute(MEMBER_SESSION_KEY, member);

    return ResponseEntity.ok()
        .header("X-Session-Id", session.getId())
        .build();
}
```

흐름은 이렇다

```
1. 로그인 → 서버: X-Session-Id: abc123 헤더 응답
2. 앱: abc123 저장
3. 다음 요청: X-Session-Id: abc123 헤더 전송
4. 인터셉터: 헤더에서 abc123 꺼내기
5. abc123으로 세션 조회 → Member 확인
```

---

## 어디서 막혔나?

4번까지는 됐다

문제는 5번이었다

```java
String sessionId = request.getHeader("X-Session-Id");
// 이 sessionId로 세션을 어떻게 찾지?
```

> `request.getSession(false)`는 ==현재 요청의 쿠키 기반 세션==만 반환한다  
> 세션 ID로 세션을 직접 조회하는 표준 API가 없다

---

## 헤더 속 세션 ID로 세션을 어떻게 찾지?

## 표준 API로 찾을 수 있나?

`HttpServletRequest`에서 세션 ID로 세션을 조회하는 방법을 찾아봤다

```java
String sessionId = request.getHeader("X-Session-Id");
request.get???  // 자동완성 목록에도 없다
```

> 표준 Servlet API에는 ==`findSessionById()` 같은 메서드가 없다==

`request.getSession(false)`가 반환하는 세션은 현재 요청에 붙은 쿠키 기반 세션 하나뿐이다

---

## 억지로 구현하면?

Tomcat 내부 구현을 직접 건드리면 가능하다

```java
// 비표준 코드
StandardContext context = (StandardContext) ((RequestFacade) request).getContext();
Session tomcatSession = context.getManager().findSession(sessionId);
```

기술적으로는 동작한다

하지만 두 가지 문제가 생긴다

<br/>

⚠️ **서블릿 컨테이너에 종속된다**

Tomcat이 아닌 Jetty나 Undertow로 바꾸면 이 코드는 바로 깨진다

<br/>

⚠️ **내부 API라 언제 바뀔지 모른다**

Tomcat 버전이 올라가면 `RequestFacade`나 `StandardContext`의 구조가 달라질 수 있다

---

## 뭘 깨달았나?

> 세션은 ==쿠키와 함께 설계된 구조==다  
> 쿠키 없이 세션 ID만 따로 다루는 건 표준 밖의 일이다

세션을 억지로 유지하는 대신, 처음부터 헤더 기반으로 설계된 방식이 필요하다

## 토큰을 만들어서 DB에 저장하면 어떨까?

## 뭘 바꿨나?

세션을 포기하고 서버가 직접 토큰을 발급하는 방식으로 전환했다

핵심 아이디어는 간단하다

> 서버가 발급한 토큰을 DB에 저장하고,  
> 클라이언트는 매 요청마다 ==Authorization 헤더==에 토큰을 담아 보낸다

---

## 어떻게 구현했나?

**로그인 시 토큰 발급**

```java
@PostMapping("/login")
public ResponseEntity<Void> login(@RequestBody LoginRequest request) {
    Member member = memberService.login(request);
    String token = UUID.randomUUID().toString();
    tokenRepository.save(token, member.getId());

    return ResponseEntity.ok()
        .header("Authorization", token)
        .build();
}
```

**인터셉터에서 DB 조회**

```java
@Override
public boolean preHandle(HttpServletRequest request, ...) {
    String token = request.getHeader("Authorization");
    if (token == null) {
        throw new RoomEscapeException(ErrorCode.UNAUTHORIZED_MEMBER);
    }
    Member member = tokenRepository.findMemberByToken(token)
        .orElseThrow(() -> new RoomEscapeException(ErrorCode.UNAUTHORIZED_MEMBER));

    if (request.getRequestURI().startsWith("/admin") && !member.isAdmin()) {
        throw new RoomEscapeException(ErrorCode.FORBIDDEN);
    }
    return true;
}
```

---

## memberId를 그대로 헤더에 담으면 안 됐나?

처음엔 memberId를 그대로 헤더에 담는 방법도 생각했다

```
Authorization: 42  ← memberId 직접 노출
```

⚠️ **보안 취약점이 생긴다**

헤더 값만 바꾸면 다른 사람인 척 요청을 보낼 수 있다

```
Authorization: 43  ← 다른 사람의 ID로 변조
```

UUID 토큰은 예측 불가능하고, DB에서만 Member와 연결된다

토큰을 탈취하지 않는 이상 다른 사람인 척 할 수 없다

---

## 뭐가 달라졌나?

| | 세션 + 헤더 시도 | 토큰 DB + 헤더 |
|---|---|---|
| 표준 API | ❌ Tomcat 내부 접근 필요 | ✅ 표준 HTTP 헤더 |
| 서블릿 컨테이너 의존 | ❌ | ✅ 독립적 |
| 모바일 지원 | △ 억지로 가능 | ✅ 자연스럽게 가능 |
| 보안 | △ 세션 ID 예측 어려움 | ✅ UUID 토큰으로 추상화 |

## 내 기준

## 전환 흐름

```
세션 + 쿠키 (웹)
    │ 모바일은 쿠키 자동 저장 안 됨
    ▼
세션 + 헤더 시도
    │ 표준 API에 findSessionById() 없음
    │ Tomcat 내부 API 접근 필요 → 비표준 의존
    ▼
토큰 DB + 헤더
    │ 서버가 직접 발급한 UUID 토큰
    │ DB에 저장, Authorization 헤더로 주고받음
    ▼
웹 + 모바일 모두 지원
```

---

## 핵심

> 세션은 ==쿠키와 함께 설계된 구조==다  
> 헤더 기반 인증이 필요하다면 처음부터 토큰으로 설계하는 게 맞다

<br/>

> 클라이언트에 식별자를 그대로 노출하면 안 된다  
> ==UUID 토큰으로 추상화==해서 예측과 변조를 막는다

---

## 웹 vs 모바일 인증 비교

| | 웹 브라우저 | 모바일 앱 |
|---|---|---|
| 쿠키 자동 관리 | ✅ | ❌ |
| 세션 방식 | ✅ 자연스럽게 동작 | ❌ 별도 처리 필요 |
| 토큰 방식 | ✅ 동작 | ✅ 자연스럽게 동작 |

---

## 실전 체크리스트

❓ **모바일 앱 지원이 필요한가?**

쿠키 기반 세션은 모바일에서 자동으로 동작하지 않는다

처음부터 토큰 방식을 고려한다

<br/>

❓ **세션 ID를 헤더로 넘기려 하는가?**

표준 Servlet API에 세션 ID로 세션을 조회하는 방법이 없다

서블릿 컨테이너 내부 API에 의존하게 된다

토큰 + DB 방식이 더 안전하고 이식성이 높다

<br/>

❓ **토큰에 식별자를 직접 담으려 하는가?**

memberId 같은 예측 가능한 값은 변조 위험이 있다

UUID로 추상화해서 DB에서만 Member와 연결한다
