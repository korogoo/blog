> 프로그램이 실행되려면 메모리에 올라와야 한다. 그런데 어떻게?

---

## 메모리의 기본 구조

- [I] **메모리: 각각 고유한 주소를 가진 바이트(byte)들의 대형 배열**

CPU는 프로그램 카운터(PC)를 이용해 메모리에서 명령어를 가져오고,
명령어 실행 중에 메모리에서 데이터를 읽거나 쓴다

---

## 프로세스 간 메모리 격리: Base & Limit 레지스터

여러 프로세스가 메모리를 공유할 때, 한 프로세스가 다른 프로세스의 메모리를 침범하면 안 된다

- [I] **Base 레지스터: 프로세스가 사용할 수 있는 메모리의 시작 주소**
- [I] **Limit 레지스터: 프로세스가 사용할 수 있는 메모리의 크기**

```
Base = 300040, Limit = 120900

합법적 주소 범위: 300040 ~ 420939
이 범위를 벗어난 주소 접근 → 트랩(오류) 발생
```

CPU 하드웨어가 유저 모드에서 생성되는 모든 주소를 Base/Limit과 비교한다

---

## 주소 바인딩 (Address Binding)

프로그램 코드의 주소가 실제 메모리 주소와 연결되는 과정

소스 코드에서 실행까지, 주소는 세 번 변환된다

```
소스 코드 (symbolic 주소)
     ↓  컴파일러 (Compiler)
오브젝트 파일 (relocatable 주소: "시작점으로부터 14바이트")
     ↓  링커/로더 (Linker/Loader)
실행 파일 (absolute 주소: "실제 메모리 주소 74014")
```

| 단계 | 주소 형태 | 예시 |
|---|---|---|
| 소스 코드 | 심볼릭 | `count`, `main` |
| 오브젝트 파일 | 재배치 가능 | 시작점+14 |
| 실행 중 메모리 | 절대 주소 | 74014 |

바인딩이 일어나는 시점에 따라 **컴파일 시간 / 로드 시간 / 실행 시간** 바인딩으로 구분한다

## 동적 로딩 (Dynamic Loading)

- [!] **프로그램 전체를 한꺼번에 메모리에 올려야 할까?**

- ["] **동적 로딩: 루틴이 실제로 호출될 때만 메모리에 로드한다**

```
프로그램 시작 → main() 로드
main()에서 foo() 호출 → 그때 foo() 로드
foo()에서 bar() 호출 → 그때 bar() 로드
```

거의 사용되지 않는 오류 처리 루틴 같은 경우, 실제로 호출되지 않으면 메모리를 아예 차지하지 않는다

---

## 동적 연결과 공유 라이브러리 (DLL)

| 방식 | 설명 |
|---|---|
| **정적 연결** (Static Linking) | 라이브러리가 실행 파일에 통째로 포함됨 — 파일이 크고, 메모리 낭비 |
| **동적 연결** (Dynamic Linking) | 라이브러리 연결을 실행 시점까지 미룸 — `.dll`, `.so` 파일 |

- [I] **DLL (Dynamically Linked Library) = 공유 라이브러리**: 메모리에 단 하나의 인스턴스만 존재하고, 여러 프로세스가 공유한다

```
프로세스 A ──►┐
              ├──► libc.so (메모리에 1개만 존재)
프로세스 B ──►┘
```

libc를 쓰는 프로세스가 100개여도, libc의 코드는 메모리에 하나만 올라간다
