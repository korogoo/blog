> 32비트 주소 공간에서 페이지 테이블 하나의 크기는 4MB에 달한다

---

## 문제: 페이지 테이블이 너무 크다

32비트 시스템, 페이지 크기 4KB(2^12)라면

```
페이지 번호 비트 수 = 32 - 12 = 20비트
페이지 테이블 엔트리 수 = 2^20 = 1,048,576개
엔트리당 4바이트 → 페이지 테이블 크기 = 4MB
```

프로세스마다 4MB의 페이지 테이블이 필요하다

⚠️ **100개의 프로세스가 동시에 실행되면 페이지 테이블만 400MB**

세 가지 구조화 방법이 있다

---

## 1. 계층적 페이지 테이블 (Hierarchical Paging)

✨ **페이지 테이블 자체를 다시 페이지로 나눠 2단계(또는 그 이상)로 구성한다**

```
논리 주소 (32비트):
[ 외부 페이지 번호 p1 | 내부 페이지 번호 p2 | 오프셋 d ]
      10비트                 10비트            12비트
```

**변환 과정**

```
① 외부 페이지 테이블[p1] → 내부 페이지 테이블의 주소
② 내부 페이지 테이블[p2] → 프레임 번호 f
③ 물리 주소 = f × 페이지크기 + d
```

💬 **실제로 사용하는 부분의 페이지 테이블만 메모리에 올리면 되므로 공간 절약**

그러나 64비트 주소 공간에서는 계층이 너무 깊어진다 (7단계 이상) → 다른 방법 필요

---

## 2. 해시 페이지 테이블 (Hashed Page Table)

✨ **32비트 초과 주소 공간에서 사용 — 가상 페이지 번호를 해시해서 테이블에서 찾는다**

```
가상 페이지 번호 → 해시 함수 → 버킷
버킷에서 체인 탐색으로 매칭되는 프레임 번호 반환
```

```
가상 주소 p ──► hash(p) ──► 버킷 ──► [ p | f | next ] ──► 프레임 f
```

테이블 전체를 탐색하지 않고 해시 버킷만 뒤진다 → 효율적

---

## 3. 역 페이지 테이블 (Inverted Page Table)

✨ **기존 방식의 역발상: 프로세스마다 페이지 테이블을 갖는 대신, 물리 프레임 하나당 항목 하나를 가지는 전역 테이블**

```
기존 방식:  프로세스 수 × 페이지 수 만큼의 항목
역 페이지:  물리 프레임 수만큼의 항목 (훨씬 적음)
```

각 항목에는 `(프로세스 ID, 가상 페이지 번호)` 가 저장된다

**변환 과정**

```
논리 주소 (pid, p, d) 입력
→ 역 페이지 테이블에서 (pid, p) 일치하는 항목 i를 찾음
→ 물리 주소 = i × 페이지크기 + d
```

💬 **시스템 전체에 단 하나의 페이지 테이블 → 메모리 크게 절약**
⚠️ **테이블을 순차 탐색해야 하므로 느리다 — 해시와 함께 사용해 속도 보완**

---

## 세 가지 방법 비교

| 방법 | 장점 | 단점 |
|---|---|---|
| 계층적 | 사용하는 부분만 메모리에 | 64비트에서 계층 너무 깊음 |
| 해시 | 빠른 탐색 | 충돌 처리 오버헤드 |
| 역 페이지 | 메모리 절약 | 탐색 느림, 공유 페이지 구현 복잡 |
