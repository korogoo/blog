
> 웹 서버가 요청마다 새 프로세스를 만든다면 어떻게 될까?

---

## 문제: 요청마다 프로세스를 만들면 너무 비싸다

웹 서버는 동시에 수천 개의 요청을 처리해야 한다

요청마다 새 프로세스를 만들면?

- [!] **프로세스 생성 비용이 크다 — 메모리 복사, 자원 할당, OS 초기화 등**

요청이 끝나면 프로세스를 또 제거해야 한다

서버가 요청을 처리하는 시간보다 프로세스를 만들고 없애는 시간이 더 길어진다

---

## 해결: 멀티스레딩

- ["] **요청마다 새 스레드를 생성한다 — 프로세스보다 훨씬 가볍다**

```
클라이언트 요청 ──►  서버 프로세스
                         │
               ┌─────────┼─────────┐
               ▼         ▼         ▼
            Thread 1  Thread 2  Thread 3
            (요청 처리) (요청 처리) (요청 처리)
```

스레드들은 서버 프로세스의 코드, 데이터, 파일을 공유하면서
각자 독립적으로 요청을 처리한다

---

## 멀티스레딩의 4가지 이점

### 1. 응답성 (Responsiveness)

- ["] **프로세스의 일부가 블로킹되어도 다른 스레드는 계속 실행된다**

UI 프로그램에서 버튼 클릭 후 긴 작업이 시작되어도,
다른 스레드가 화면 갱신을 담당하면 앱이 멈춘 것처럼 보이지 않는다

### 2. 자원 공유 (Resource Sharing)

- ["] **같은 프로세스 안의 스레드들은 메모리와 자원을 자동으로 공유한다**

공유 메모리나 메시지 전달 같은 별도 IPC 없이도 데이터를 주고받을 수 있다

### 3. 경제성 (Economy)

- ["] **스레드 생성 비용은 프로세스 생성 비용보다 훨씬 작다**

컨텍스트 스위치도 프로세스 전환보다 스레드 전환이 오버헤드가 적다

### 4. 확장성 (Scalability)

- ["] **멀티코어 환경에서 스레드들이 각 코어에서 병렬로 실행된다**

프로세스 하나가 여러 코어를 동시에 활용할 수 있다

---

## 정리

| 이점 | 핵심 |
|---|---|
| 응답성 | 블로킹 상황에서도 다른 스레드는 동작 |
| 자원 공유 | 별도 IPC 없이 메모리 공유 |
| 경제성 | 생성/전환 비용이 프로세스보다 작음 |
| 확장성 | 멀티코어를 자연스럽게 활용 |
