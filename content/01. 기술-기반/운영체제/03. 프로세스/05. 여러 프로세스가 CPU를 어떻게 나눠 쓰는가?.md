> CPU는 하나인데 프로세스는 수백 개다

---

## 두 가지 목표

멀티프로그래밍과 타임 쉐어링은 비슷해 보이지만 목적이 다르다

- [I] **멀티프로그래밍(Multiprogramming): 항상 어떤 프로세스가 실행 중이도록 → CPU 활용률 최대화**
- [I] **타임 쉐어링(Time Sharing): CPU를 빠르게 전환하여 사용자가 동시 실행처럼 느끼도록 → 응답성 확보**

---

## 스케줄링 큐

OS는 프로세스를 두 종류의 큐로 관리한다

| 큐 | 설명 |
|---|---|
| **Ready Queue** | CPU를 받을 준비가 된 프로세스들의 대기열 |
| **Wait Queue** | I/O 완료 등 특정 이벤트를 기다리는 프로세스들의 대기열 |

```
프로세스 생성
     │
     ▼
[Ready Queue] ──► CPU 실행
                     │
          ┌──────────┼──────────────┐
          │          │              │
          ▼          ▼              ▼
     인터럽트    I/O 요청        자식 프로세스
     발생       (Wait Queue)    종료 대기
          │          │              │
          └──────────┴──────────────┘
                     │
               [Ready Queue]
```

- [i] **큐는 내부적으로 PCB들의 연결 리스트(linked list)로 구현된다**

---

## 문제: 실행 중인 프로세스를 어떻게 전환하는가?

프로세스 A가 실행 중인데, 인터럽트가 발생하거나 타임 슬라이스가 끝났다

CPU를 다음 프로세스에게 넘겨야 한다

- [!] **단순히 다른 프로세스를 실행하면 A의 상태가 사라진다**

---

## 컨텍스트 스위치 (Context Switch)

- [I] **컨텍스트 스위치: 현재 프로세스의 상태를 PCB에 저장하고, 다음 프로세스의 상태를 PCB에서 복원하는 작업**

```
프로세스 P0 실행 중
     │
     │  인터럽트 발생
     ▼
P0의 상태 → PCB₀에 저장   (state save)
     │
P1의 상태 ← PCB₁에서 복원 (state restore)
     │
     ▼
프로세스 P1 실행 중
     │
     │  인터럽트 발생
     ▼
P1의 상태 → PCB₁에 저장
     │
P0의 상태 ← PCB₀에서 복원
     │
     ▼
프로세스 P0 재개
```

<br/>

- [i] **컨텍스트 스위치 자체는 순수한 오버헤드다**

전환하는 동안 CPU는 유용한 작업을 전혀 하지 않는다

전환 속도는 하드웨어(레지스터 수, 메모리 속도 등)에 의존한다
