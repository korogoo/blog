> 공유 메모리는 빠르지만, 프로그래머가 모든 걸 직접 관리해야 한다

---

## 문제: 공유 메모리 방식의 한계

공유 메모리는 빠르지만 책임이 크다

- [!] **공유 영역에 접근하는 코드를 프로그래머가 직접 작성해야 하고, 동기화도 직접 처리해야 한다**

두 프로세스가 동시에 같은 위치에 쓰면? 데이터가 깨진다

---

## 해결: 메시지 전달

- [I] **메시지 전달(Message Passing): OS가 통신 수단을 제공하고, 프로세스는 `send()`/`receive()`만 호출한다**

프로그래머가 공유 메모리를 직접 다룰 필요가 없다

```c
// 생산자
while (true) {
    produce_item(&next_produced);
    send(next_produced);        // OS에게 전달 요청
}

// 소비자
while (true) {
    receive(&next_consumed);    // OS에게 수신 요청
    consume_item(next_consumed);
}
```

---

## 직접 통신 vs 간접 통신

메시지를 "누구에게" 보내느냐에 따라 방식이 나뉜다

### 직접 통신 (Direct Communication)

수신자/발신자를 명시적으로 지정한다

```c
send(P, message)      // 프로세스 P에게 전송
receive(Q, message)   // 프로세스 Q로부터 수신
```

- [>] 링크가 자동으로 생성됨
- [>] 정확히 두 프로세스 사이에만 링크가 존재
- [>] 두 프로세스 사이에 링크는 정확히 하나

### 간접 통신 (Indirect Communication)

메시지를 **메일박스(mailbox)** 또는 **포트(port)** 를 통해 주고받는다

```c
send(A, message)      // 메일박스 A에 전송
receive(A, message)   // 메일박스 A에서 수신
```

```
프로세스 P ──► [메일박스 A] ◄──► 프로세스 Q
                    ▲
               프로세스 R도 접근 가능
```

- [>] 메일박스를 공유하는 프로세스 사이에만 링크 생성
- [>] 하나의 링크가 여러 프로세스와 연결될 수 있음
- [>] OS가 메일박스 생성/삭제/송수신 기능 제공

---

## Blocking vs Non-blocking

메시지를 보내고 받을 때 "기다릴 것인가"를 선택할 수 있다

| 방식 | 설명 |
|---|---|
| **Blocking send** | 수신자가 받을 때까지 발신자가 대기 |
| **Non-blocking send** | 메시지를 보내고 바로 다음으로 진행 |
| **Blocking receive** | 메시지가 올 때까지 수신자가 대기 |
| **Non-blocking receive** | 메시지가 있으면 받고, 없으면 null 반환 |

- [i] **Blocking send + Blocking receive 조합을 랑데부(rendezvous)라고 부른다**

둘 다 기다리는 구조라 동기화가 자연스럽게 이루어진다
