> CPU를 누가, 언제, 얼마나 쓸지 결정하는 것이 스케줄링이다

---

## CPU-burst와 I/O-burst

프로세스는 실행 중에 두 가지 행동을 반복한다

- ✨ **CPU-burst: CPU를 사용해서 연산을 수행하는 구간**
- ✨ **I/O-burst: I/O 완료를 기다리는 구간**

```
프로세스 실행 흐름:
[CPU burst] → [I/O burst] → [CPU burst] → [I/O burst] → ... → 종료
```

대부분의 프로세스는 짧은 CPU-burst가 매우 많고, 긴 CPU-burst는 드물다

이 특성 덕분에 스케줄링이 의미있다 — CPU가 잠깐 비는 순간을 잘 활용하면 된다

---

## 스케줄러가 하는 일

메모리에 올라와 있는 Ready 상태의 프로세스 중 하나를 골라 CPU를 할당한다

어떻게 고를 것인가? 이것이 **스케줄링 알고리즘**의 문제다

---

## 선점 vs 비선점

스케줄링 방식은 크게 두 가지로 나뉜다

| 방식 | 설명 |
|---|---|
| **비선점 (Non-preemptive)** | 프로세스가 스스로 CPU를 놓을 때까지 계속 실행 |
| **선점 (Preemptive)** | 스케줄러가 강제로 CPU를 빼앗을 수 있음 |

스케줄링 결정이 일어나는 4가지 시점

| 시점 | 방식 |
|---|---|
| Running → Waiting (I/O 요청 등) | 비선점만 가능 |
| Running → Terminated | 비선점만 가능 |
| Running → Ready (인터럽트 발생) | 선점 또는 비선점 |
| Waiting → Ready (I/O 완료) | 선점 또는 비선점 |

- ℹ **선점 스케줄링은 응답성이 좋지만, 공유 데이터에 대한 동기화 문제가 생길 수 있다**

---

## 디스패처 (Dispatcher)

스케줄러가 "다음 프로세스"를 고르면, 실제로 CPU를 넘겨주는 것은 **디스패처**가 한다

디스패처가 하는 일

- ▶ 현재 프로세스의 컨텍스트 저장 → 다음 프로세스 컨텍스트 복원
- ▶ 커널 모드 → 유저 모드 전환
- ▶ 다음 프로세스의 실행 위치로 점프

- ⚠️ **디스패처는 모든 컨텍스트 스위치마다 호출된다 — 최대한 빨라야 한다**

디스패처가 한 프로세스를 멈추고 다음 프로세스를 시작하는 데 걸리는 시간을
**디스패처 지연(dispatcher latency)** 이라고 한다

---

## 컨텍스트 스위치는 얼마나 자주 일어나는가?

```bash
$ vmstat 1 3         # cs 열이 초당 컨텍스트 스위치 횟수
$ cat /proc/1/status | grep ctxt
voluntary_ctxt_switches:    62   # 자발적 (I/O 요청 등)
nonvoluntary_ctxt_switches:  0   # 강제 (타임 슬라이스 소진 등)
```
