> 4가지 필요 조건 중 하나를 없애면 데드락이 발생하지 않는다

---

## 데드락을 다루는 세 가지 방법

| 방법 | 설명 |
|---|---|
| **무시** | 데드락이 없는 척한다 (UNIX, Windows의 기본 방침) |
| **예방/회피** | 데드락 상태에 절대 진입하지 않도록 한다 |
| **탐지 후 회복** | 발생을 허용하고, 탐지한 뒤 복구한다 |

이번 파일은 **예방(Prevention)** 전략을 다룬다 — 4가지 조건을 각각 제거하는 방법

---

## 조건 1: 상호 배제 제거

- [!] **근본적으로 불가능한 경우가 많다**

뮤텍스 락처럼 본질적으로 공유할 수 없는 자원은 상호 배제를 없앨 수 없다

읽기 전용 파일 같은 경우에는 공유가 가능하지만, 이는 예외적인 경우다

---

## 조건 2: 점유 대기 제거

- ["] **자원을 요청할 때 아무것도 점유하지 않은 상태여야 한다**

두 가지 프로토콜

| 방법 | 설명 | 단점 |
|---|---|---|
| 실행 전 전부 요청 | 시작 전에 필요한 자원을 모두 한꺼번에 요청 | 자원 낭비 — 나중에 쓸 자원을 처음부터 독점 |
| 반납 후 재요청 | 새 자원이 필요하면 현재 자원을 모두 반납하고 다시 요청 | 기아 가능 — 인기 자원 조합을 영원히 못 얻을 수 있음 |

---

## 조건 3: 비선점 제거

- ["] **자원을 갖고 있는 스레드가 새 자원을 즉시 받지 못하면, 현재 점유 중인 자원을 모두 반납한다**

반납된 자원은 다른 스레드에게 할당될 수 있다

이 스레드는 원래 자원과 새 자원 모두 확보될 때까지 대기한다

- [!] **CPU 레지스터, 메모리 공간에는 적용 가능하지만, 프린터나 뮤텍스 같은 자원에는 적용하기 어렵다**

---

## 조건 4: 순환 대기 제거 (현실적으로 가장 유용)

- ["] **모든 자원 타입에 전역 순서(번호)를 매기고, 스레드는 반드시 번호 오름차순으로만 자원을 요청해야 한다**

```
R1=1, R2=2, R3=3, mutex_A=4, mutex_B=5

올바른 순서:  R1 → R2 → mutex_A → mutex_B  (오름차순)
잘못된 순서:  mutex_B → mutex_A             (역순 → 순환 가능)
```

이 규칙을 모든 스레드가 따르면 순환 대기가 구조적으로 불가능해진다

---

## 주의: 동적 락 획득의 한계

- [!] **락 순서를 정해도, 런타임에 동적으로 락을 획득하면 데드락을 보장할 수 없다**

```c
void transaction(Account *from, Account *to, double amount) {
    pthread_mutex_lock(&from->lock);  // from의 번호가 항상 작다는 보장 없음
    pthread_mutex_lock(&to->lock);
    ...
}
// transaction(A, B)와 transaction(B, A)가 동시에 실행되면?
// → A→B 락과 B→A 락이 교차 → 데드락
```

---

## 예방 방법의 공통 단점

- [i] **데드락 예방은 자원 요청 방식을 제한하므로, 자원 활용률 저하와 시스템 처리량 감소를 유발할 수 있다**
