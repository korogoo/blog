## 요청 하나가 서버에서 겪는 일

```
요청 도착
  │
  ├─ [하드웨어] NIC 가 신호를 감지하고 DMA 가 메모리에 복사
  │     -> 04. API 요청 하나가 들어오면 무슨 일이 일어날까?
  │
  ├─ [OS] 인터럽트가 걸리고, CPU 가 스레드를 갈아끼운다
  │     -> 05. CPU는 어떻게 여러 일을 동시에 하나?
  │     -> 06. 프로세스 스위칭이 왜 더 비쌀까?
  │
  ├─ [JVM] 이 메서드가 인터프리터냐 C2 컴파일된 기계어냐
  │     -> 03. 컴파일이 두 번 일어난다고?
  │
  ├─ [JVM] 만든 객체가 Eden 에 쌓인다
  │     -> 04. JVM은 뭘 어디에 저장할까?
  │
  ├─ [Spring] 비즈니스 로직, 트랜잭션 경계
  │
  ├─ [DB] 여기서 또 한 번 TCP 를 타고 나갔다 온다
  │     -> 03. DB랑 어떻게 대화하는 걸까?
  │     -> 04. 다 되거나 다 안 되거나
  │
  ├─ 응답을 메모리에 올려두면 끝 (그 뒤는 OS 와 NIC 의 일)
  │
  ├─ [JVM] Eden 이 차서 GC 가 돈다 -> STW
  │     -> 05. GC는 Heap을 어떻게 정리할까?
  │     -> 06. STW를 어떻게 줄일까?
  │
  └─ [배포] STW 가 길면 헬스체크가 실패하고, 멀쩡한 서버가 재시작된다
        -> 06. 무중단 배포가 무적일까?
```

## 서로 이어지는 지점들

| 이쪽에서 | 저쪽으로 | 무슨 관계 |
|---|---|---|
| JVM warm-up | 배포 전략 | 방금 뜬 서버에 트래픽 100%를 주면 안 되는 이유 |
| GC의 STW | 무중단 배포 | 헬스체크 오탐으로 멀쩡한 서버가 재시작된다 |
| CPU register(SP) | JVM Stack | 컨텍스트 스위칭 때 백업되는 게 그 Stack 위치다 |
| 컨텍스트 스위칭 | 스레드풀 사이즈 | 왜 CPU bound는 코어 수 근처인가 |
| 캐시 계층 | TLB | 자주 쓰는 걸 가까이 두는 같은 발상 |
| DMA | 비동기 | 오래 걸리는 일은 넘기고 끝나면 통보받는다 |
| NIC/OS 응답 송출 | 502 Bad Gateway | 프로세스가 죽으면 응답을 내보낼 주체가 없다 |
| 요청 하나의 여정 | DBMS 접속 | 내 서버도 남의 서버에 TCP 로 붙는 클라이언트다 |
| 디스크가 느린 이유 | WAL | 흩어진 곳에 쓰는 것보다 이어 쓰는 게 싸다 |
| 컨텍스트 스위칭 | 락 대기 | 기다리게 하는 비용을 피하려고 MVCC 가 나왔다 |
| 캐시 계층 | Redis | 자주 쓰는 걸 가까이(메모리) 두는 같은 발상 |

## 아직 안 채운 곳

- **B+Tree** - DB 시리즈에서 이름만 나오고 구조는 못 봤다
- **비동기와 트랜잭션** - 재료는 있고 아직 정리 전
- **OOM 종류별 구분** - Heap / Metaspace / GC Overhead Limit
- **스키마 변경의 하위 호환성** - Expand-Contract
- **실측** - 전부 이론이다, 부하를 걸어서 GC 로그를 직접 떠보는 게 다음 차례다
