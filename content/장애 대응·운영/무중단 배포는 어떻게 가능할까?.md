## 발단

배포는 왜 해야 될까

당연한 소리긴 한데, 많은 사람들이 내 서비스를 사용하게 만들기 위해서다

내 노트북에만 있는 코드는 아무도 못 쓴다

<br/>

여기까지는 쉬웠는데 다음 질문에서 막혔다

> 그럼 지금 많은 사람들이 쓰고 있는 코드를 중간에 어떻게 수정하지...?

<br/>

지금까지 나는 그냥 GitHub Actions 워크플로우 파일을 복붙해서 썼다

푸시하면 알아서 서버에 올라가니까 그 안에서 무슨 일이 일어나는지는 생각을 안 했다

<br/>

스터디 완료 기준을 적어놓고 보니 하나도 답을 못 하겠더라

```
- 배포 중에는 구버전과 신버전이 반드시 공존한다는 게
  왜 모든 배포 전략의 출발점인가
- 무중단 배포에서 502가 뜨는 이유와 막는 순서
  (SIGTERM -> Graceful Shutdown -> Connection Draining)
- 배포 전략 3종(Rolling / Blue-Green / Canary) 차이
  + 롤백 속도 / 리소스 비용 / 버전 공존 시간 3축으로 언제 뭘 쓰는지
- 스키마, 캐시, 직렬화 포맷 변경이 왜 숨은 파괴적 변경인지
```

<br/>

특히 첫 줄이 안 와닿았다

구버전과 신버전이 공존한다는 게 왜 "출발점"씩이나 되나 싶었다

<br/>

일단 제일 옛날 방식부터 따라가 보기로 했다

❓ 프로세스라는 개념이 없던 시절엔 배포를 대체 어떻게 했을까

## 옛날엔 그냥 파일만 덮어썼다고?

## FTP로 파일만 던지면 끝났다

옛날 PHP 시절엔 배포가 진짜 간단했다

FTP(File Transfer Protocol)로 서버 디스크에 파일을 덮어쓰면 끝이었다

```
요청 --> 웹서버 --> 인터프리터 --> 디스크 [ current.php ]

                  (new.php 를 덮어씀)

요청 --> 웹서버 --> 인터프리터 --> 디스크 [ current.php ← 내용이 바뀜 ]
```

요청이 올 때마다 인터프리터가 그 파일을 ==그때그때 읽어서== 실행했으니까

파일 내용이 바뀌면 다음 요청부터 알아서 새 코드가 돌았다

<br/>

재시작이라는 개념 자체가 필요 없었다

요즘 같은 "프로세스가 코드를 메모리에 올려두고 돈다"는 개념이 아니었기 때문이다

---

## 근데 지금은 프로세스로 돈다

`java -jar app.jar`를 하는 순간 프로세스가 뜬다

JVM이 클래스를 메모리에 로드하고 그 상태로 계속 돈다

<br/>

⚠️ **이제 파일 덮어쓰기로는 코드 최신화가 안 된다**

jar 파일을 아무리 새것으로 바꿔놔도 이미 떠 있는 프로세스는 옛날 코드를 들고 있다

```
git pull -> 빌드 -> 프로세스 kill -> restart
```

이 과정을 꼭 거쳐야만 새 코드가 반영된다

---

## 그래서 사람이 직접 들어갔다

**1단계 - SSH 수동 재시작**

사람이 직접 SSH로 서버에 들어가서 위 네 단계를 손으로 친다

<br/>

**2단계 - 스크립트 자동화**

> 이걸 언제 매번 치고 앉아있냐...

아예 스크립트로 작성해서 실행시켜버린다

```bash
#!/bin/bash
git pull
./gradlew build
kill $(cat app.pid)
nohup java -jar build/libs/app.jar &
```

<br/>

**3단계 - CI/CD 자동화**

> 그냥 이 스크립트 실행도 자동으로 하면 안 되나?

```
코드 푸시 -> 빌드 -> 테스트 -> 배포 스크립트 실행
```

이 과정 자체를 자동으로 돌아가게 만든 게 지금 내가 쓰고 있는 GitHub Actions다

---

## 근데 셋 다 같은 문제를 못 풀었다

여기서 좀 허무했다

수동이든 스크립트든 CI/CD든, ==결국 하는 일이 똑같다==

```
kill -> restart
```

편해졌을 뿐이지 문제는 그대로다

<br/>

✨ **FTP만 이 문제가 없었던 이유**

FTP는 애초에 프로세스를 안 죽였다

파일만 바꾸면 됐으니까

<br/>

⚠️ **물론 FTP도 완벽하진 않았다**

파일이 전송되는 중간에 요청이 들어오면 반쯤 덮어써진 파일을 읽게 된다

A 파일은 수정됐는데 관련된 B 파일은 아직 전송 전인 경우도 있다

<br/>

정리하면 이렇다

| 방식 | 프로세스 재시작 | 공백 |
|---|---|---|
| FTP 파일 덮어쓰기 | 없음 | 파일 단위 불일치 |
| SSH 수동 | 있음 | 있음 |
| 스크립트 | 있음 | 있음 |
| CI/CD | 있음 | ==있음== |

❓ kill하고 restart하는 그 사이, 들어온 요청은 어떻게 될까

## 서버를 내렸다 올리면 그 사이 요청은?

## 공백이 생긴다

기존 서버를 kill하고 새 서버를 restart하면 그 사이에 공백이 생긴다

```
기존 서버 [실행중] --kill--> [       공백       ] --restart--> 새 서버 [실행중]
                                   ↑
                        이 사이에 들어온 요청은?
```

<br/>

⚠️ **이 공백에 들어온 요청은 전부 에러다**

프로세스가 없으니까 응답해 줄 주체 자체가 없다

<br/>

이걸 막는 고전적인 방법이 다운타임 공지다

> "OO월 OO일 새벽 3시 ~ 4시 서버 점검이 있습니다"

<br/>

새벽 3시에 배포하고 그 시간엔 사용자가 없기를 기도한다

근데 매번 새로운 배포를 할 때마다 다운타임 공지를 할 수는 없다

<br/>

⚠️ **그러면 배포 주기가 느려진다**

배포가 무서우니까 한 번에 몰아서 하게 되고, 한 번에 몰아서 하니까 더 무서워진다

버그를 하나 고쳐도 다음 정기 배포까지 기다려야 한다

<br/>

내가 원하는 건 반대다

> 배포 자체를 자유롭게, 자주 할 수 있게 만들 순 없을까?

이게 무중단 배포다

---

## 공백을 없애는 방법은 의외로 간단하다

요청을 계속 받아주면 된다

근데 어떻게?

<br/>

✨ **새로운 서버를 미리 띄워두면 되지 않나?**

```
기존 서버 [실행중] ------------- kill
새로운 서버        [실행중] -----------
                    ↑
              먼저 띄워둔다
```

기존 서버가 죽기 전에 새 서버가 먼저 요청을 받을 수 있는 상태가 되면 공백이 없다

당연한 얘기다

---

## 여기서 완료 기준의 첫 줄이 이해됐다

미리 띄우는 순간, 필연적으로 이 구간이 생긴다

```
구버전 [실행중] ══════════╗
신버전        ╔═══════════╩══[실행중]
              ↑ 여기 ↑
        둘 다 살아있는 구간
```

<br/>

✨ **배포 중에는 구버전과 신버전이 반드시 공존한다**

이걸 피할 방법이 없다

<br/>

왜냐면 ==언제 진짜로 이전 버전이 kill될지, 새 버전이 요청을 받을 수 있는 상태가 될지 정확히 알 수가 없기 때문==이다

새 서버가 떴다고 로그에 찍혀도 커넥션 풀이 아직 안 찼을 수 있고, 기존 서버는 처리 중이던 요청이 남아 있을 수 있다

<br/>

그래서 "공존 구간을 없앤다"가 아니라 ==공존 구간을 어떻게 다룰 것인가==가 문제가 된다

- 그 구간을 짧게 할 것인가, 길게 두고 관찰할 것인가
- 그동안 트래픽을 어느 쪽에 얼마나 보낼 것인가
- 두 버전이 같은 DB를 보는데 스키마가 다르면 어쩔 것인가

<br/>

> ==모든 배포 전략은 이 공존 구간을 어떻게 설계하느냐의 차이였다==

전략이 여러 개인 게 아니라, 하나의 문제에 대한 답이 여러 개였던 거다

❓ 그럼 그 답들은 각각 뭐가 다를까

## 그래서 어떤 전략들이 있나?

## 0. 그냥 내렸다 올리기

전략이라고 부르기도 뭐하지만 일단 여기서 출발한다

서버 내리고, 버전 2로 수정하고, 다시 띄운다

```
로드밸런서 --> 서버(v1)
로드밸런서 --> ✗ ERROR      <- 내리는 중
로드밸런서 --> 서버(v2)
```

<br/>

의외로 ==가장 시간이 적게 걸린다==

구조도 제일 단순하고, 서버도 N대만 있으면 된다

<br/>

⚠️ **대신 두 가지가 걸린다**

아주 잠깐이라도 다운타임이 생긴다

그리고 모든 기능이 모든 사용자에게 한 번에 반영돼서 ==테스트 기간을 갖기가 어렵다==

<br/>

지금 바리바리가 이 방식이다

---

## 1. Blue-Green - 미리 띄우고 스위칭

새로운 버전의 서버를 미리 띄워놓고 로드밸런서에서 한 번에 스위칭한다

```
로드밸런서 --> Blue(v1)

로드밸런서 --> Blue(v1)     Green(v2)   <- 미리 띄움, 트래픽은 아직 X
                              ↑
                           준비 완료

로드밸런서 --> Green(v2)    Blue(v1)    <- 스위칭
```

<br/>

✨ **다운타임이 없고 롤백도 쉽다**

문제가 생기면 로드밸런서를 Blue로 되돌리면 끝이다

Blue가 아직 살아있으니까 롤백이 초 단위다

<br/>

⚠️ **대신**

로드밸런서 설정이 그냥 내렸다 올리기보다 복잡하다

그리고 일시적으로 ==서버가 2N대== 뜬다 (비용)

<br/>

그런데 이거 말고 더 걸리는 게 있었다

> 근데 너무 급작스러운 업데이트...

---

## 급작스러운 게 왜 문제야?

한 번에 스위칭하면 두 가지가 터진다

<br/>

**1. 피해 규모**

신버전에 버그가 있으면 ==100%의 트래픽이 동시에 그 버그를 겪는다==

롤백이 아무리 빨라도 그 몇 초 동안 전체 사용자가 맞는다

<br/>

**2. 워밍업이 안 된 상태로 100%를 맞는다**

이게 JVM 공부한 게 딱 연결되는 지점이었다

```
방금 뜬 서버 = 아직 인터프리터로 도는 중
             = C2가 최적화한 기계어가 거의 없음
```

멀쩡한 코드인데도 초반 응답이 느리다

거기에 트래픽 100%를 한 번에 꽂으면 느린 응답이 쌓이고, 스레드가 물리고, 타임아웃이 난다

> 자세한 건 [[03. 컴파일이 두 번 일어난다고?]]

<br/>

**그래서 트래픽을 천천히 늘려야 한다**

---

## 2. Rolling - 하나씩 순차적으로

인스턴스를 한 대씩 교체한다

```
LB --> [Server v1] [Server v1] [Server v1]

LB --> [Server v2] [Server v1] [Server v1]   <- 한 대 교체

LB --> [Server v2] [Server v2] [Server v1]

LB --> [Server v2] [Server v2] [Server v2]
```

<br/>

✨ **서버는 항상 N대로 유지된다**

Blue-Green처럼 2N대가 필요 없다

<br/>

⚠️ **대신 롤백이 느리다**

되돌리려면 또 한 대씩 되돌려야 한다

그리고 구버전과 신버전이 ==섞여 있는 시간이 제일 길다==

같은 사용자가 새로고침할 때마다 다른 버전에 붙을 수 있다

---

## 3. Canary - 5%만 먼저

Rolling이 "몇 대를 바꿀까"라면 Canary는 "몇 퍼센트를 보낼까"다

```
LB --> Server(v1) 100%

LB --> new(v2) 5%   |  Server(v1) 95%
LB --> new(v2) 20%  |  Server(v1) 80%
LB --> new(v2) 50%  |  Server(v1) 50%
LB --> new(v2) 100%
```

<br/>

5%를 보내는 동안 새 서버의 ==에러율과 P99== 같은 지표를 확인한다

문제가 생기면 nginx에서 바로 0:100으로 되돌리면 되니까 피해가 5%에서 끊긴다

<br/>

**몇 퍼센트씩 올릴지, 얼마나 지켜볼지는 상황에 맞게 조절한다**

⚠️ 트래픽이 너무 적으면 5% 모니터링이 별 쓸모가 없다

전체가 하루 100건인데 5%면 5건이다

5건 다 성공했다고 안전하다고 말할 수가 없다

<br/>

바리바리가 딱 이 상태라서, 지금은 Canary를 해도 의미가 없겠구나 싶었다

---

### 💬 P99가 뭐지?

> 요청 누적 카운트의 99% 지점에 있는 요청의 응답 시간

이게 뭔 소리지 싶었다

쉽게 말하면 ==느린 순서로 상위 1%를 뺀 나머지 중 제일 느린 값==이다

평균은 소수의 느린 요청을 가려버리는데, P99는 그걸 잡아낸다

<br/>

**근데 이걸 어떻게 계산하지?**

정직하게 하려면 모든 응답 시간을 정렬해야 한다

요청이 초당 수천 건인데 그걸 다 들고 정렬하는 건 ==리소스가 너무 많이 드는 작업==이다

<br/>

✨ **그래서 미리 버킷을 만들어둔다**

```
A: 0~10ms
B: 10~20ms
C: 20~50ms
D: 50~100ms
E: 100ms 이상
```

응답이 들어올 때마다 해당 버킷에 `count++`만 한다

메모리는 버킷 개수만큼만 쓰고 끝이다

<br/>

**응답 10개로 P90을 찾아보면**

```
A까지 누적: 2건
B까지 누적: 2+4 = 6건
C까지 누적: 6+2 = 8건
D까지 누적: 8+1 = 9건   <- 여기서 9번째(90%)에 도달
```

P90은 버킷 D에 있다

버킷 안은 균등분포라고 가정하고 50~100ms를 잘게 쪼개서 근사값을 낸다

D에 응답이 1개뿐이라면 그냥 100ms로 본다

<br/>

⚠️ **P99는 마지막 버킷에 걸리기 쉽다**

10개 중 9.9번째면 버킷 E인데, E는 상한이 무한대다

그래서 "100ms 이상"으로 추정하거나 하한값 100ms를 근사치로 내놓는다

정확한 값이 아니라 ==일정한 리소스로 얻는 근사값==이라는 걸 알고 봐야 한다

## 3축으로 정리

| | 롤백 속도 | 리소스 비용 | 버전 공존 시간 |
|---|---|---|---|
| 내렸다 올리기 | 느림 (재배포) | N대 | 없음 (대신 다운타임) |
| Blue-Green | ==제일 빠름== | ==2N대== | 짧음 |
| Rolling | 느림 | N대 | ==제일 김== |
| Canary | 빠름 | N + α | 조절 가능 |

<br/>

> 롤백 속도가 중요하면 Blue-Green, 비용이 중요하면 Rolling, 신버전이 불안하면 Canary

<br/>

❓ 그런데 Canary에서 트래픽 비율을 바꾸려면 nginx 설정을 고쳐야 한다

nginx를 reload하면 그 순간엔 요청을 못 받는 거 아닌가

## nginx reload 하면 트래픽을 받을 수 있는 상태인가?

## nginx도 프로세스인데

앞에서 프로세스는 재시작해야 새 코드가 반영된다고 했다

nginx도 프로세스다

그럼 `nginx.conf`를 고치고 반영하려면 nginx를 재시작해야 하고, 그 순간 공백이 생기는 거 아닌가

<br/>

무중단 배포를 하려고 nginx를 쓰는데 nginx 때문에 중단되면 말이 안 된다

---

## master와 worker

nginx는 프로세스가 하나가 아니다

```
       master (관리자)
          |
    ┌─────┼─────┐
 worker worker worker    <- 실제 클라이언트 요청 처리
```

- **master** : 설정 읽기, 워커 관리만 한다 (요청은 안 받는다)
- **worker** : 실제 클라이언트 요청을 처리한다

<br/>

보통 CPU 코어 개수만큼 워커 프로세스를 만든다

<br/>

✨ **여기가 핵심이다**

요청을 처리하는 건 worker지 master가 아니다

그래서 master를 그대로 둔 채 worker만 갈아끼우면 요청은 안 끊긴다

---

## nginx -s reload 하면 무슨 일이 일어날까

```
1. reload         관리자가 master 에게 신호를 보낸다
        ↓
2. 문법 검사       nginx.conf 를 읽고 검사한다
        ↓         문제가 있으면 → 기존 상태를 그대로 유지 (아무 일도 안 일어남)
        ↓
3. 새 워커 fork    master 가 새 설정으로 워커를 fork 한다
        ↓         master 한테 상속받은 리스닝 소켓에서
        ↓         새 연결을 곧바로 받기 시작한다
        ↓
4. 구 워커 종료    새 연결은 안 받고
                  처리 중이던 요청만 끝까지 마무리 (드레이닝)
                  다 끝나면 종료
```

<br/>

**2번이 좋았다**

설정에 오타를 냈어도 죽지 않는다

문법 검사에서 걸리면 기존 워커가 그대로 돌고 있어서 서비스에 영향이 없다

<br/>

**3번이 무중단의 이유다**

새 워커가 fork되자마자 바로 연결을 받는다

리스닝 소켓을 master한테 물려받기 때문에 소켓을 새로 열 필요가 없다

```
구 워커 [처리중] ──드레이닝──> 종료
신 워커        [새 연결 받는 중] ────────>
                ↑
        여기 공백이 없다
```

<br/>

✨ **nginx 자체가 무중단으로 설정을 바꾼다**

그래서 Canary에서 5% -> 20% -> 50%로 비율을 바꿔도 요청이 끊기지 않는다

---

## 여기서 패턴이 하나 보였다

4번을 다시 보면

> 새 연결은 안 받고, 처리 중이던 요청만 끝까지 마무리한다

<br/>

이게 nginx만의 특별한 기능이 아니라 ==프로세스를 안전하게 죽이는 일반적인 방법==이더라

```
1. 새 요청을 더 이상 받지 않는다
2. 처리 중이던 요청은 끝까지 마무리한다
3. 다 끝나면 종료한다
```

<br/>

❓ 그럼 우리 스프링 부트 서버도 이렇게 죽어야 하는 거 아닌가

지금은 그냥 kill하고 있는데, 그러면 무슨 일이 생길까

## 무중단 배포가 무적일까?

## 그건 당연한거고

새 서버를 미리 띄우면 공백이 없다는 얘기를 하고 있었는데, 스터디에서 이 말이 나왔다

> 어셔: "그건 당연한거고"

<br/>

그러니까 로드밸런서 앞단은 안 끊긴다 치고, ==죽는 쪽에서 무슨 일이 벌어지는지==를 봐야 한다는 거였다

기존 서버를 kill하는 순간 그 서버는 놀고 있던 게 아니다

---

## 트랜잭션 중이었다면?

**커밋 전에 죽은 경우**

```
Instance1                    DB
   |--- 트랜잭션 시작 ------->|
   |--- insert -------------->|
   ✗ kill                     |
                        커밋 안 됨 -> 롤백
```

이건 괜찮다

커밋 전이니까 DB가 알아서 롤백한다

지저분한 데이터는 안 남는다

<br/>

**커밋 후, 응답 전에 죽은 경우**

```
Instance1                    DB
   |--- insert -------------->|
   |--- commit -------------->|  ← 저장 완료
   ✗ kill                     |
   (응답을 못 보냄)
```

⚠️ **이게 문제다**

서버에는 저장이 됐는데 사용자한테는 실패로 보인다

롤백도 안 된다 (이미 커밋했으니까)

<br/>

그리고 실패로 보이면 사용자는 뭘 할까

> 다시 누른다

<br/>

포스트가 두 개 생긴다

✨ **그래서 재시도 가능한 API는 멱등성이 필요하다**

무중단 배포를 하려면 배포 설정만 만지는 게 아니라 API 설계까지 봐야 한다는 게 좀 의외였다

---

## 502는 왜 뜰까

kill하면 프로세스가 소켓을 전부 닫아버린다

```
사용자 --> nginx --> Instance1
                        ✗ 소켓이 뚝 끊김
           nginx: "응답 기다리는 중인데... 상대가 사라졌는데요?"
사용자 <-- 502 Bad Gateway
```

<br/>

nginx 입장에서는 업스트림 서버가 갑자기 증발한 거다

돌려줄 응답이 없으니까 자기가 502를 만들어서 내려준다

<br/>

> ==502는 nginx가 뒷단 서버한테 응답을 못 받았을 때 뜬다==

무중단 배포한다고 해놓고 502가 뜨는 건 대부분 이 케이스다

---

## 그럼 어떻게 하면 잘 종료할 수 있을까

순서가 중요하다

<br/>

### 1. 로드밸런서에서 먼저 뺀다

```
        로드밸런서
        /        \
   I1(빼는 중)    I2
   ✗ 새 요청 X    ← 여기서 새 요청 받기
```

⚠️ **이걸 먼저 안 하면 나머지가 다 소용없다**

이미 종료 중인 I1한테 요청이 계속 들어가면, I1에 도달한 그 요청들이 그대로 502가 된다

<br/>

이때 이미 ==새로운 인스턴스가 준비돼 있어야== 한다

I1을 빼는데 받아줄 I2가 없으면 그냥 다운타임이다

<br/>

### 2. SIGTERM을 보낸다

스프링 부트 프로세스에 SIGTERM을 전송한다

```bash
kill -15 <pid>     # SIGTERM - "정리하고 종료해줘"
kill -9  <pid>     # SIGKILL - "지금 당장 죽어"
```

<br/>

### 💬 15는 뭐임

그냥 `kill <pid>`를 치면 기본값이 15, 즉 SIGTERM이다

우리가 흔히 아는 `kill -9`가 SIGKILL이다

<br/>

| | 프로세스가 받나 | 정리할 기회 |
|---|---|---|
| SIGTERM (15) | ==받는다== | 있다 |
| SIGKILL (9) | 못 받는다 (커널이 즉시 제거) | ==없다== |

<br/>

SIGKILL은 프로세스한테 전달조차 안 된다

커널이 그냥 없애버려서 애플리케이션이 뭘 할 수가 없다

`kill -9`로 배포하고 있었다면 위에서 본 502와 커밋 후 종료 문제를 그대로 맞고 있는 거다

<br/>

### 3. Graceful Shutdown

Tomcat이 SIGTERM을 받으면 ==더 이상 새로운 연결을 수락하지 않는다==

⚠️ 연결을 아예 끊는 게 아니다

"더 이상 새 요청을 안 받겠다"는 것이지, 기존에 처리 중이던 요청은 중단시키지 않는다

```
처리 중이던 요청 = DB 트랜잭션 진행 중, 응답 준비 중, ...
```

<br/>

Spring Boot는 설정 한 줄이다

```yaml
server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

<br/>

### 4. Connection Draining

진행 중이던 요청들이 다 끝날 때까지 기다린다

<br/>

**근데 이걸 뭐 평생 기다리나?**

무한 루프에 빠진 요청이 하나 있으면 서버가 영원히 안 죽는다

그래서 유예 시간을 두고 초과하면 강제 종료한다 (위 설정의 30초)

<br/>

⚠️ **강제 종료는 최후의 수단이다**

사실 이게 발동 안 하는 게 정상이다

30초 안에 안 끝나는 요청이 있다면 그건 배포 문제가 아니라 그 API의 문제다

---

## 전체 순서

```
1. 로드밸런서에서 I1 제거      <- 새 요청 차단
2. SIGTERM (kill -15)         <- 정리 신호
3. Graceful Shutdown          <- 새 연결 수락 중단
4. Connection Draining        <- 처리 중이던 요청 마무리
5. (유예 시간 초과 시) 강제 종료 <- 발동 안 하는 게 정상
```

<br/>

앞의 [[05. nginx reload 하면 트래픽을 받을 수 있는 상태인가?]]에서 본 nginx 워커 종료 과정이랑 똑같다

nginx가 특별했던 게 아니라 이게 표준 절차였던 거다

---

## 그리고 JVM 쪽에서 만난 문제가 여기서 또 나온다

GC를 공부할 때 이런 걸 봤다

> STW가 길어지면 헬스체크가 실패해서 멀쩡한 서버가 재시작된다

<br/>

배포 관점에서 보면 이게 더 무섭다

```
Rolling 배포 중 -> 새 인스턴스가 warm-up 중 -> 느림
              -> 트래픽이 남은 인스턴스로 몰림 -> GC 압박
              -> STW 길어짐 -> 헬스체크 실패
              -> 그 인스턴스도 교체 대상이 됨 -> 트래픽이 더 몰림
```

<br/>

⚠️ **배포 중에 연쇄적으로 무너질 수 있다**

그래서 헬스체크 타임아웃은 최악의 STW 시간보다 넉넉해야 하고, 새 인스턴스에 트래픽을 천천히 줘야 한다

> [[06. STW를 어떻게 줄일까?]]에서 본 내용이 여기랑 맞물린다

---

## 그래서 무적은 아니다

무중단 배포는 "설정하면 되는 것"이 아니었다

```
- 트랜잭션 커밋 후 응답 전에 죽으면?    -> API 멱등성 필요
- LB에서 빼는 순서를 안 지키면?         -> 502
- kill -9 로 죽이면?                   -> Graceful Shutdown 자체가 무의미
- STW가 헬스체크보다 길면?              -> 연쇄 재시작
- 구버전과 신버전이 같은 DB를 보면?      -> ???
```

<br/>

❓ 마지막 줄이 아직 안 풀렸다

## 내 기준

## 핵심 흐름

```
[배포의 역사]
FTP 파일 덮어쓰기   -> 프로세스가 없어서 재시작이 필요 없었음
        ↓ 프로세스 시대
SSH 수동 / 스크립트 / CI/CD
        -> 편해졌을 뿐, 셋 다 kill -> restart 는 그대로
        -> 그 사이 공백 = 에러

[공백을 없애려면]
새 버전을 미리 띄운다
        ↓
구버전과 신버전이 반드시 공존한다  <- 모든 배포 전략의 출발점
        ↓
공존 구간을 어떻게 다룰 것인가 = 전략의 차이

[전략]                롤백    비용    공존 시간
내렸다 올리기          느림    N      없음(다운타임)
Blue-Green            빠름    2N     짧음
Rolling               느림    N      김
Canary                빠름    N+α    조절 가능

[죽는 쪽을 잘 죽이는 순서]
1. 로드밸런서에서 제거      <- 안 하면 나머지가 무의미, 502
2. SIGTERM (kill -15)      <- kill -9 는 신호가 전달조차 안 됨
3. Graceful Shutdown       <- 새 연결만 거부, 기존 요청은 유지
4. Connection Draining     <- 처리 중이던 요청 마무리
5. 유예 시간 초과 시 강제 종료 <- 발동 안 하는 게 정상

[nginx reload 도 같은 구조]
master 는 요청을 안 받는다 -> 새 worker fork -> 구 worker 드레이닝
```

---

> ==무중단 배포는 "안 끊기게 하는 기술"이 아니라 "구버전과 신버전이 겹치는 시간을 설계하는 일"이었다==
> 겹치는 걸 없앨 수 없으니, 얼마나 겹칠지와 그동안 뭐가 깨질 수 있는지를 정하는 게 전부다

<br/>

✨ **제일 크게 바뀐 생각**

배포를 인프라 설정 문제로만 봤는데 아니었다

커밋 후 응답 전에 죽으면 사용자가 재시도한다 -> ==API에 멱등성이 있어야 한다==

이건 배포 스크립트가 아니라 내가 짜는 코드의 문제다

<br/>

⚠️ **남는 트레이드오프**

Canary가 제일 안전해 보이지만 바리바리에는 못 쓴다

트래픽이 적어서 5%를 모니터링해봐야 표본이 몇 건 안 되고, 그 몇 건이 다 성공했다고 안전하다고 말할 수가 없다

==좋은 전략이 아니라 트래픽 규모에 맞는 전략을 고르는 것==이 맞다

---

## 바리바리는 지금 어디쯤인가

현재는 그냥 내렸다 올리기다

무중단 배포 조건 중 미충족 항목을 적어봤다

```
[ ] 인스턴스가 1대     -> 애초에 뺄 데가 없음
[ ] 로드밸런서 없음
[ ] Graceful Shutdown 설정 안 됨 (server.shutdown 기본값 immediate)
[ ] 헬스체크 엔드포인트는 있지만 배포 흐름과 연결 안 됨
[✓] 멱등성 - 일부만 (조회는 문제없고, 생성 API는 중복 생성 가능)
```

<br/>

인스턴스가 1대라서 Blue-Green도 Rolling도 지금은 의미가 없다

다만 ==설정 한 줄로 되는 것부터는 해두려고 한다==

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

인스턴스가 1대여도 이건 유효하다

배포 중에 처리되던 요청이 잘려나가는 걸 막아주니까

---

❓ 실전 체크리스트

- 배포했는데 502가 떴다 -> 로드밸런서에서 먼저 뺐는지 본다 (순서가 1번인 이유)
- `kill -9`를 쓰고 있진 않은가 -> 그러면 Graceful Shutdown 설정이 있어도 무의미하다
- 재시도해도 안전한 API인가 -> 커밋 후 응답 전에 죽는 케이스를 가정한다
- 배포 중에 응답이 느려진다 -> 새 인스턴스 warm-up을 의심한다 ([[03. 컴파일이 두 번 일어난다고?]])
- 배포 중에 멀쩡한 인스턴스가 재시작된다 -> 헬스체크 타임아웃 < STW 인지 본다 ([[06. STW를 어떻게 줄일까?]])
- Canary를 도입하려 한다 -> 5%가 통계적으로 의미 있는 트래픽인지 먼저 계산한다
- 드레이닝 유예 시간이 자꾸 초과된다 -> 배포 설정이 아니라 그 API를 의심한다

---

❓ 아직 안 풀린 것

- **스키마 / 캐시 / 직렬화 포맷 변경** - 완료 기준에 있었는데 못 다뤘다  
  구버전과 신버전이 같은 DB를 보는 동안 컬럼을 지우면 구버전이 깨진다  
  Expand-Contract 패턴을 다음에 볼 예정이다
- **웹소켓** - 요청/응답이 짧게 끝나는 HTTP는 드레이닝이 되는데, 연결을 계속 붙들고 있는 웹소켓은 어떻게 드레이닝하는지 모르겠다
- **P99 계산 시점** - 버킷 방식은 이해했는데, 어떤 기간을 기준으로 언제 집계하는지가 안 잡힌다 (10초 롤링? 배포 직후 리셋?)

JVM 쪽에서 시작한 이야기가 결국 여기서 만났다

warm-up도 STW도, 혼자서는 그냥 이론인데 배포와 붙으니까 사고가 됐다
