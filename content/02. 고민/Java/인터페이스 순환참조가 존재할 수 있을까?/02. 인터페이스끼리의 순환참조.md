> 인터페이스끼리의 순환참조는 컴파일 수준에서는 가능하다  
> 
> ==하지만 의미 있는 설계인지는 다른 문제다==

---

## 순환참조란?

A가 B를 의존하고, B가 A를 의존하는 구조다

```
A → B → A (순환)
```

---

## 인터페이스끼리는 가능한가?

```java
public interface A {
    B getB();
}

public interface B {
    A getA();
}
```

컴파일 에러가 나지 않는다

인터페이스는 메서드 시그니처만 선언하기 때문에 서로를 타입으로 참조해도 JVM이 문제없이 로딩한다

인터페이스는 Spring이 직접 Bean으로 만들지 않기 때문에 컴파일에서 문제가 되지 않는다

⚠️  **하지만, 구현체가 만들어질 때 순환이 생기는 것이 문제다**

---

## 클래스 순환참조와의 차이

```java
@Service
class ServiceA {
    @Autowired ServiceB serviceB;
}

@Service
class ServiceB {
    @Autowired ServiceA serviceA;
}
```

Spring이 Bean을 생성할 때 A를 만들려면 B가 필요하고,  

B를 만들려면 A가 필요한 교착 상태가 발생한다

Spring Boot 2.6 이후부터는 기본적으로 순환참조를 금지한다

---

## 의미 있는 설계인가?

인터페이스끼리 순환참조가 생겼다면, 두 인터페이스가 강하게 결합되어 있다는 신호다

❓ **두 개념이 정말 서로를 알아야 하는가?**

❓ **한쪽이 다른 쪽에 일방적으로 의존하도록 방향을 정할 수 없는가?**

❓ **중간에 새로운 추상화를 도입해서 순환을 끊을 수 없는가?**

---

## 핵심

인터페이스끼리의 순환참조는 컴파일러가 막지 않는다

하지만 순환이 생겼다는 것 자체가 설계를 다시 볼 신호다

의존 방향이 한쪽으로 흐르도록 설계를 정리하는 것이 맞다
