## 비교

| 기준      | 대리키             | 복합키             |
| ------- | --------------- | --------------- |
| 구조 단순성  | 단순              | 복잡              |
| 외래키 참조  | 숫자 하나           | 컬럼 여러 개         |
| 변경 안전성  | 비즈니스 값 변경과 무관   | 구성 컬럼 변경 시 영향 큼 |
| ORM 호환성 | 기본 지원           | 별도 설정 필요        |
| 중복 방지   | UNIQUE 제약 별도 필요 | 기본키 자체가 중복 방지   |
| 도메인 표현력 | 의미 없는 id        | 자연스러운 식별        |

---

## 내 기준

```
새 테이블을 만든다
       │
       ▼
이 테이블의 구성 컬럼들이 변경될 가능성이 있는가?
       │
  ┌────┴────┐
 YES        NO
  │          │
  ▼          ▼
대리키 선택  다대다 연결 테이블인가?
            │
       ┌────┴────┐
      YES        NO
       │          │
       ▼          ▼
    복합키 고려  대리키 기본
```

## 실전 기준표

| 상황 | 선택 |
|---|---|
| 일반 엔티티 (Game, Player 등) | 대리키 기본 + UNIQUE 제약 추가 |
| 다대다 연결 테이블 | 복합키 자연스러움 |
| 구성 컬럼이 변경될 가능성이 있다 | 대리키 |
| JPA 사용 | 대리키 강력 권장 |
| 외부 API에 id를 노출한다 | UUID 대리키 고려 |

## ENUM vs VARCHAR + CHECK 제약

피드백에서 함께 나왔던 주제 (이 주제도 고민이 깊어지면 따로 분리할 예정)

|       | ENUM                  | VARCHAR + CHECK          |
| ----- | --------------------- | ------------------------ |
| 장점    | DB 수준 제약, 명확한 허용값     | DB 종속성 없음, 이식성 좋음        |
| 단점    | DB 마이그레이션 필요 (값 추가 시) | 잘못된 값이 들어오면 앱 레벨에서만 막음   |
| 선택 기준 | 값이 고정되고 변경이 없을 때      | 값이 자주 바뀌거나 DB 독립성이 중요할 때 |
