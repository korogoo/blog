> 방어선을 한 겹씩 쌓아가면서  
> 
> ==각 계층이 무엇을 막고 무엇을 못 막는지== 이해하게 됐다

---

## 1단계 : 트랜잭션만

기존에 구현되어 있던 방식이다

서비스 레이어에서 `existsBy`로 검증하고 INSERT한다


⚠️  **동시에 들어온 두 요청이 커밋 전 서로의 상태를 못 보기 때문에 예약 중복을 막지 못한다**

---

## 2단계 : 트랜잭션 + ==DB Unique 제약==

```sql
UNIQUE (res_date, time_id, theme_id)
```

서비스 검증을 동시에 통과해도, INSERT 시점에 하나는 Unique 위반으로 실패한다


⚠️ **DB 예외가 발생한다**

`DataIntegrityViolationException`이 올라오는데,

DB 예외라서 어떤 제약이 깨진 건지 파악하기 어렵고, 비즈니스 예외로 변환하는 처리가 복잡해진다

---

## 3단계 : 트랜잭션 + DB Unique + ==비관적 락==

```sql
SELECT ... FOR UPDATE
```

조회 시점부터 다른 트랜잭션을 블로킹한다

서비스 레이어 `existsBy` 단계에서 이미 대기 또는 예외가 발생하므로, 깨끗한 비즈니스 예외 처리가 가능하다

⚠️ **DB 성능이 급락한다**

락이 걸린 동안 다른 요청이 전부 대기한다

고트래픽 환경이라면 DB 성능이 중요하다

---

## 4단계 : 트랜잭션 + DB Unique + ==낙관적 락==

SELECT는 블로킹 없이 허용한다

실제 INSERT 시점에 version 불일치로 충돌을 감지한다 (`ObjectOptimisticLockingFailureException`)

비관적 락보다 유연하고 성능이 좋다

충돌 시 재시도 또는 409 응답으로 처리한다
