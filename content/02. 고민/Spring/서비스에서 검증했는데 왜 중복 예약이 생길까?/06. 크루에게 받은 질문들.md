## 낙관적 락에 Unique까지 적용하는 이유?

> ==막는 시나리오가 달라서==

둘은 보호하는 대상이 다르다

<br/>

**낙관적 락이 막는 것**

같은 row를 두 트랜잭션이 동시에 수정하는 것

```
Thread A: reservation#1 읽음 (version=0)
Thread B: reservation#1 읽음 (version=0)
Thread A: UPDATE ... WHERE version=0 → 성공, version=1
Thread B: UPDATE ... WHERE version=0 → 0 rows → 충돌 감지
```

<br/>

**Unique 제약이 막는 것**

서로 다른 두 row가 같은 슬롯을 차지하려는 것

```
Thread A: exists(6/1, time1, theme1) → false
Thread B: exists(6/1, time1, theme1) → false
Thread A: INSERT (6/1, time1, theme1) → 성공
Thread B: INSERT (6/1, time1, theme1) → DB가 거절
```

<br/>

낙관적 락은 기존 row의 수정 충돌을 감지하고, Unique 제약은 새 row의 중복 생성을 막는다

보호하는 대상이 다르니 둘 다 필요하다

---

## 동시 수정 충돌 vs 중복 생성 — 본질이 다른가?

> ==패턴이 다르고 해결책도 다르다==

| | 중복 생성 | 동시 수정 충돌 (Lost Update) |
|---|---|---|
| 패턴 | check → (간격) → insert | read → (간격) → write |
| 대상 | 서로 다른 두 row | 같은 row |
| 충돌 결과 | 두 row가 같은 슬롯 차지 | 한 쪽 수정이 조용히 사라짐 |
| 해결책 | DB Unique 제약 | 낙관적 / 비관적 락 |

<br/>

비유하면 이렇다

**중복 생성**: 두 사람이 빈 자리에 동시에 앉으려는 것

**동시 수정 충돌**: 두 사람이 같은 자리에서 동시에 메모를 지우고 자기 글을 쓰는데, 한 쪽 글이 사라지는 것

## 격리 수준을 올려서 해결하면 어떤 문제가?

> 중복 생성을 막으려면 ==SERIALIZABLE까지 올려야== 한다

그러면 네 가지 문제가 생긴다

<br/>

⚠️ **성능 하락**

SERIALIZABLE에서는 SELECT에도 range lock이 걸린다

예약 조회 하나가 다른 트랜잭션의 INSERT를 블로킹하게 되어 처리량이 크게 감소한다

<br/>

⚠️ **데드락 위험 증가**

잠금을 더 넓은 범위에서 더 오래 보유하기 때문에 두 트랜잭션이 서로를 기다리는 상황이 생기기 쉽다

<br/>

⚠️ **범위가 너무 넓다**

날짜+시간+테마가 겹치는 예약 생성을 막겠다는 규칙 하나 때문에 전체 DB 트랜잭션을 직렬화하는 건 과한 해결책이다

Unique 제약은 딱 그 컬럼들만 잠근다
