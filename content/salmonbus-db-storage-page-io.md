DB 삭제를 켰는데도 평가 결과가 더 빨리 쌓였다.

2026년 10월 22일 08:55 KST, Grafana에서 직전 15분을 확인해봤다. `forecast_evaluation_result`에는 초당 약 112건이 들어오고 있었고 삭제는 초당 약 6.2건이었다. 추정 생존 행은 약 8,405만 건. 테이블 10.99GB에 인덱스 7.71GB까지 쓰고 있었다.

처음 든 생각은 단순했다.

```text
생성 속도를 따라잡기 vs 처음부터 덜 쌓이게 하기
```

둘 중 정확도 차이가 별로 없다면 후자가 낫다고 봤다. 그래서 모든 예보를 꼭 평가해야 하는지부터 건드려봤다.

결과만 먼저 말하면 평가를 줄이는 건 실패했다. 저장량은 확 줄었는데 일부 예측이 꽤 크게 틀어졌다. 평가 결과가 그냥 보관용 이력이 아니라 당일 예측을 보정하는 입력이었기 때문이다.

결국 평가가 아니라 **원본 관측에서 다시 읽을 수 있는 중복 정보**를 줄여야 했다.

## DB 삭제는 켰는데, 왜 더 쌓이지?

Salmonbus가 예측 하나를 평가하고 치우는 흐름은 이렇다.

```text
15초마다 차량 관측 저장
→ 차량별 여러 도착 정류장의 잔여석 예측
→ 실제 도착 관측과 연결해 예측 평가
→ 평가 결과를 당일 보정과 승하차 통계에 반영
→ 오래된 상세 결과를 S3에 보관한 뒤 DB에서 삭제
```

차량 하나를 관측하면 앞으로 도착할 여러 정류장의 예측이 같이 만들어진다. 이 관측은 짧은 주기로 반복되고, 같은 차량의 평가 기록도 여러 DB 페이지에 나뉘어 저장된다.

![같은 차량의 평가 기록이 여러 PostgreSQL 페이지에 나뉘어 저장되는 구조](assets/salmonbus-portfolio/01-storage-flow.png)

PostgreSQL은 행 하나를 저장할 때 테이블 페이지만 쓰지 않는다. 기본 키와 보조 인덱스를 갱신하고, 장애 복구와 복제를 위한 WAL도 남긴다. `DELETE`했다고 파일에서 바로 사라지는 것도 아니다. 삭제된 행은 dead tuple로 남고 vacuum이 나중에 재사용할 공간으로 정리한다.

어디서 줄일 수 있을까? 세 군데가 보였다.

1. 오래된 행을 지우는 비용이 큼
2. S3 이관 worker가 한 번에 처리하는 양이 작음
3. 평가 결과 한 행에 원본 관측과 겹치는 값이 반복됨

삭제만 빨라져도 새로 쌓이는 양이 그대로면 언젠가 다시 밀린다. 저장만 줄이면 이미 쌓인 8천만 행은 그대로다. 이관 처리량과 앞으로 쌓을 데이터의 모양을 같이 바꿔야 했다.

## 첫 번째 시도: 날짜 파티션으로 오래된 데이터를 지우기

먼저 오래된 행을 하나씩 지우지 말고 날짜 파티션을 통째로 떼어내면 어떨까 싶었다.

PostgreSQL 18 로컬 컨테이너에 운영과 같은 스키마와 인덱스를 만들고 합성 데이터 60만 행을 넣었다. 그중 오래된 30만 행을 지웠다. CPU 1개, 메모리 512MiB 조건에서 세 번 돌린 중앙값이다.

| 항목                    | `DELETE` | 날짜 파티션 `DROP` |
| ----------------------- | -------: | -----------------: |
| 제거 시간               |  0.162초 |            0.042초 |
| 제거 구간 WAL           |  71.27MB |            0.056MB |
| 이후 vacuum WAL         |  21.28MB |                0MB |
| 제거 후 테이블과 인덱스 | 147.25MB |            73.77MB |

속도만 보면 파티션이 압승이었다. 제거 시간은 약 4배 빨랐고, 제거 구간 WAL은 71.27MB에서 0.056MB로 줄었다.

근데 현재 중복 방지는 `(vehicle_observation_id, target_stop_order)` 유일성에 기대고 있다. 날짜 파티션을 쓰려면 이 키에 파티션 날짜를 넣거나 중복 방지 구조를 따로 만들어야 한다. `evaluation_archive_member`가 예측 원본을 참조하는 외래 키도 같이 손봐야 했다.

그리고 파티션을 떼어내도 S3 업로드가 100행씩 처리되는 문제는 그대로다. 빠른 방법은 맞는데, 지금 문제를 이것 하나로 끝낼 수는 없었다.

## 두 번째 시도: 평가를 덜 하면 되지 않을까?

다음은 처음 생각했던 “덜 쌓기”다. 기존 8개 노선의 2026년 10월 5일 관측을 시간순으로 다시 재생했다.

- 같은 차량은 마지막 평가로부터 60초가 지나면 다시 평가
- 60초 전이라도 정류장이나 방향이 바뀌면 바로 평가
- 승하차 통계에 쓰는 한 정류장 앞 예보는 무조건 평가

평가 등록은 `1,684,742건`에서 `688,694건`으로 59.12% 줄었다. 와, 대박. 평균 좌석 오차도 `3.23619석`에서 `3.24658석`으로 0.01039석만 늘었다.

![모든 예보를 평가한 결과와 평가 간격을 60초로 줄인 결과 비교](assets/salmonbus-portfolio/04-evaluation-sampling-experiment.png)

여기까지만 보면 바로 적용해도 될 것 같았다. 그래도 평균 하나만 보고 끝내기는 찜찜했다. 두 방식의 예측값이 3석 넘게 달라진 사례를 따로 꺼내봤다.

3500번 노선의 08:41 예측이다. 이 버스는 08:55 도착 관측에서 잔여석 23석으로 확인됐다.

| 방식           | 예측 잔여석 | 절대 오차 | 보정 후 만석 확률 |
| -------------- | ----------: | --------: | ----------------: |
| 모든 평가 유지 |     24.37석 |    1.37석 |            26.46% |
| 평가 횟수 축소 |     17.34석 |    5.66석 |            47.67% |

기존 방식은 1.37석 차이였는데 평가를 줄이자 5.66석 차이로 벌어졌다. 평균이 이 값을 가리고 있었다.

왜 이렇게 달라졌을까?

차이는 당일 보정에서 생겼다. 같은 날, 같은 노선, 같은 예측 거리의 정산 표본이 2,800건에서 989건으로 줄었다. 두 방식 모두 실제 만석 관측은 0건이었다. 근데 표본이 적어진 쪽은 “오늘 이 노선은 만석이 아니었다”는 결과를 훨씬 덜 반영했다.

보정 로직은 표본이 50건 이상일 때 움직인다. 표본 몇 개가 확률을 너무 크게 바꾸지 않도록 평균 확률에 200건의 가상 표본도 더한다.

```text
보정에 쓰는 만석 비율
= (실제 만석 건수 + 200 × 기존 평균 만석 확률)
  / (실제 정산 건수 + 200)
```

실제 정산 건수가 줄면 이 200건의 힘이 더 세진다. 평가를 줄인 쪽은 그날 쌓인 “만석 아님”보다 기존 평균을 더 많이 따라갔다. 보정된 만석 확률은 26.46%에서 47.67%로 올라갔고, 예상 잔여석은 내려갔다.

비슷한 사례가 하나만 있었던 것도 아니다. 3석 넘게 달라진 예측 375건 중 332건의 오차가 커졌다. ㄷㄷ

평균 오차는 0.01석 차이였지만 실제 예측 하나씩 보면 얘기가 달랐다. **평가 횟수와 당일 보정 입력을 같이 줄이는 방식은 버렸다.**

## 세 번째 시도: 그래서 평가는 유지하고 저장만 나눴다

평가를 줄이면 안 된다면, 꼭 모든 결과를 같은 크기로 저장해야 할까?

이번에는 평가에는 손대지 않았다. 모든 예보를 원래대로 정산해서 당일 보정과 승하차 통계에 넣고, 저장할 때만 상세 결과와 최소 결과로 나눴다.

아래 결과는 기존처럼 상세하게 남긴다.

- 처음 본 차량이거나 마지막 상세 저장 후 60초가 지난 경우
- 정류장, 방향, 노선 판본, 모델이 바뀐 경우
- 승하차 통계에 쓰는 한 정류장 앞 예측
- 방향을 알 수 없거나 과거 관측을 다시 처리한 경우
- 건너뜀, 도착 미확인, 좌석 정보 없음, 품질 제외처럼 정상 정산이 아닌 경우

그 외 정상 결과는 `forecast_evaluation_compact`에 넣는다. 예측 키, 도착 관측 ID, 실제 잔여석, 정산 시각, 도착 시각과 당시 운행 키만 남겼다. 차량 ID, 도착 정류장, 노선 판본은 원본 관측에서 다시 읽을 수 있으니 또 저장하지 않는다.

![모든 예보를 정산한 뒤 상세 결과와 최소 결과로 저장하는 조건](assets/salmonbus-portfolio/05-evaluation-storage-decision.png)

조회 계약도 그대로 두고 싶었다. 그래서 상세 테이블과 최소 테이블을 `UNION ALL`한 뷰를 만들었다. 기존 코드는 이 뷰에서 같은 형태의 결과를 읽는다.

최소 결과는 도착 관측을 외래 키로 참조한다. 다시 읽어야 할 원본이 먼저 삭제되는 걸 막기 위해서다. 한 정류장 앞 통계는 상세 결과만 읽는 별도 뷰로 뺐다. 통계를 계산할 때마다 최소 결과 전체와 원본 관측을 조인하는 건 또 다른 비용이 되기 때문이다.

같은 차량이 같은 정류장에 있고 15초마다 예측 12개를 만든다면 이렇게 저장된다. 아래 값은 동작을 보여주기 위한 예시다.

| 관측 시각 | 정산 대상 | 상세 저장 | 최소 저장 |
| --------- | --------: | --------: | --------: |
| 10:00:00  |      12개 |      12개 |       0개 |
| 10:00:15  |      12개 |       1개 |      11개 |
| 10:00:30  |      12개 |       1개 |      11개 |
| 10:00:45  |      12개 |       1개 |      11개 |
| 10:01:00  |      12개 |      12개 |       0개 |

합계만 메모리에 들고 있으면 더 작게 만들 수 있다. 근데 worker가 재시작하면 집계 근거를 다시 만들 수 없고, 같은 평가를 두 번 반영했는지도 판단하기 어렵다. 저장량을 더 줄이겠다고 복구와 중복 방지를 포기할 수는 없었다. 그래서 최소 결과는 DB에 남겼다.

## 결과는? 두구두구

같은 관측과 같은 모델을 최종 방식으로 다시 재생했다. 이번에는 모든 정산 결과를 당일 보정과 승하차 통계에 넣고, 상세 저장 여부만 갈랐다.

| 확인한 값                  | 기존 전체 저장 | 상세와 최소 저장 분리 |
| -------------------------- | -------------: | --------------------: |
| 생성한 예측                |    1,684,742건 |           1,684,742건 |
| 확률 분포가 달라진 예측    |           기준 |                   0건 |
| 평균 좌석 오차             |      3.23619석 |             3.23619석 |
| 정상 정산의 상세 저장 대상 |    1,411,497건 |             586,954건 |

확률 분포가 달라진 예측은 0건. 앞에서 17.34석까지 내려갔던 3500번 예측도 다시 24.37석으로 돌아왔다. 정상 정산의 상세 저장 대상은 58.42% 줄었다.

이제야 **예측은 그대로 두고 저장만 줄었다.**

그럼 실제 바이트는 얼마나 줄까? PostgreSQL 18에 모의 데이터 10만 행을 넣어 비교했다.

| 저장 방식                     | 테이블과 인덱스 크기 |
| ----------------------------- | -------------------: |
| 모두 상세 저장                |     27,910,144바이트 |
| 상세 41,584건 + 최소 58,416건 |     20,316,160바이트 |

테이블과 인덱스를 합쳐 27.21% 줄었다. 상세 저장 대상은 58% 줄었는데 바이트는 왜 27%만 줄었을까 싶을 수 있다. 최소 테이블에도 기본 키, 외래 키와 도착 시각 인덱스가 필요해서 행 수와 바이트가 같은 비율로 줄지는 않는다.

## 운영 지표로 이관 병목을 다시 봤다

로컬 재생이 잘 끝났다고 운영 DB가 덜 쌓이는 건 아니다. Grafana의 PostgreSQL 지표와 worker 로그를 같은 시간대로 맞춰봤다.

2026년 10월 22일 08:40부터 08:55 KST까지 worker는 이관 묶음 74번에서 5,304행을 삭제했다. 묶음당 평균 약 71.7행, 최대 100행이었다. 성공한 묶음은 평균 약 5.33초, 95백분위 약 5.63초가 걸렸다. 같은 15분 동안 실패 로그는 3건 있었다.

| Grafana에서 본 값                         | 08:55 KST 기준 |
| ----------------------------------------- | -------------: |
| 평가 결과 입력 속도, 직전 15분 평균       |  약 112.3행/초 |
| 평가 결과 삭제 속도, 직전 15분 평균       |    약 6.2행/초 |
| `forecast_evaluation_result` 추정 생존 행 |  약 8,405만 행 |
| 테이블 크기                               |        10.99GB |
| 인덱스 크기                               |         7.71GB |
| 대기 중인 DB 잠금 연결                    |            0개 |

대기 중인 DB 잠금은 0개였다. 쿼리 하나가 잠겨서 멈춘 게 아니라, 100행을 옮기고 5초 쉬는 속도로는 초당 112건의 입력을 따라갈 수 없었다.

그래서 이관 코드는 기본 500행을 읽고, 4MiB 파일 크기와 SQL 제한 시간 안에서 최대 1,000행까지 처리할 수 있게 바꿨다. 단, 위 Grafana 수치는 운영 worker가 여전히 최대 100행씩 처리하던 때의 기록이다. 500행이라는 설정값을 운영 성과인 것처럼 섞지는 않았다.

운영에서는 삭제량 하나만 보지 않고 아래 값을 같이 본다.

- 평가 결과의 초당 입력과 삭제
- 이관 묶음의 행 수, 처리 시간, 실패 건수
- 상세 테이블과 최소 테이블의 생존 행, 테이블 크기, 인덱스 크기
- WAL 생성량, dead tuple, autovacuum, 잠금 대기

상세 테이블만 줄고 최소 테이블이 같은 속도로 커질 수도 있다. 인덱스와 WAL이 생각보다 커질 수도 있다. 그래서 삭제 속도만 빨라졌다고 끝내면 안 된다.

## 줄인 것은 평가가 아니라 중복 정보였다

처음에는 평가 건수를 59% 줄이면 저장 문제도 같이 풀릴 줄 알았다. 평균 오차 차이도 0.01석이라 꽤 그럴듯했다. 근데 개별 예측을 열어보고 당일 보정까지 따라가니 정확도 입력을 같이 줄이고 있었다.

최종 구조는 `1,684,742건`의 평가를 그대로 처리한다. 달라진 예측 분포는 0건이고, 정상 정산의 상세 저장 대상은 58.42% 줄었다. 모의 데이터 10만 행에서는 테이블과 인덱스가 27.21% 작아졌다.

결국 줄인 건 평가가 아니었다. **다른 원본에서 다시 읽을 수 있는 값만 덜 저장했다.**
