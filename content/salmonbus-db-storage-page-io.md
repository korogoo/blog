연어버스는 버스의 현재 잔여석을 보여주고, 다음 정류장에 도착했을 때 몇 석이 남을지 예측하는 서비스예요.

예측이 맞았는지 확인한 결과를 데이터베이스(DB)에 저장하는데, 오래된 결과를 지우고 있어도 새 결과가 더 빨리 쌓이고 있었어요.

2026년 10월 22일 08:55 KST, 운영 지표를 보는 Grafana에서 직전 15분을 확인했어요. `forecast_evaluation_result` 테이블에는 초당 약 112건이 들어오고 있었고, 삭제는 초당 약 6.2건이었어요. 추정 생존 행은 약 8,405만 건이었고요. 테이블은 10.99GB, 인덱스는 7.71GB를 쓰고 있었어요.

처음에는 두 방법을 생각했어요.

```text
생성 속도를 따라잡기 vs 처음부터 덜 쌓이게 하기
```

예측 정확도가 거의 같다면 처음부터 덜 저장하는 편이 낫겠다고 생각했어요. 그래서 모든 예측을 꼭 평가해야 하는지부터 확인했어요.

결과부터 말하면 평가 횟수를 줄이는 방법은 쓰지 않았어요. 저장량은 크게 줄었지만, 일부 예측이 실제 잔여석에서 더 멀어졌거든요. 평가 결과가 단순한 기록이 아니라 그날의 예측을 보정하는 입력이었기 때문이에요.

결국 평가 자체는 유지하고, **원본 관측에서 다시 읽을 수 있는 중복 정보**를 덜 저장했어요.

## 오래된 결과를 지우는데 왜 더 쌓일까요?

연어버스가 예측 하나를 평가하고 오래된 결과를 치우는 흐름은 이래요.

```text
15초마다 차량 관측 저장
→ 차량별 여러 도착 정류장의 잔여석 예측
→ 실제 도착 관측과 연결해 예측 평가
→ 평가 결과를 당일 보정과 승하차 통계에 반영
→ 오래된 상세 결과를 S3에 보관한 뒤 DB에서 삭제
```

여기서 관측은 외부에서 받은 차량 상태를 시각과 함께 기록하는 일이에요. 차량 하나를 관측하면 앞으로 도착할 여러 정류장의 잔여석 예측이 같이 만들어져요. 관측은 짧은 주기로 반복되고, 같은 차량의 평가 기록도 여러 DB 페이지에 나뉘어 저장돼요.

![같은 차량의 평가 기록이 여러 PostgreSQL 페이지에 나뉘어 저장되는 구조](assets/salmonbus-portfolio/01-storage-flow.png)

PostgreSQL은 데이터를 페이지라는 저장 단위에 나눠 담아요. 행 하나를 저장할 때 테이블 페이지만 쓰지는 않아요. 검색에 쓰는 인덱스도 갱신하고, 장애 복구와 복제를 위한 변경 기록인 WAL도 남겨요.

`DELETE`를 실행해도 파일 크기가 곧바로 줄어들지는 않아요. 삭제된 행은 재사용 가능한 공간으로 정리되기 전까지 남아 있어요. 이 정리를 돕는 PostgreSQL 작업이 vacuum이에요.

줄일 수 있는 곳은 세 군데였어요.

1. 오래된 행을 지우는 비용이 큼
2. S3 이관 worker가 한 번에 처리하는 양이 작음
3. 평가 결과 한 행에 원본 관측과 겹치는 값이 반복됨

삭제만 빨라져도 새로 쌓이는 양이 그대로면 다시 밀려요. 반대로 새로 저장하는 양만 줄이면 이미 쌓인 8천만 행은 그대로고요. 과거 결과를 옮기는 속도와 앞으로 저장할 데이터의 크기를 함께 봐야 했어요.

## 첫 번째 시도: 날짜 파티션으로 오래된 데이터를 지우기

먼저 오래된 행을 하나씩 지우지 말고 날짜별로 나눈 테이블을 통째로 제거하면 어떨까 생각했어요. 이 날짜별 테이블을 파티션이라고 해요.

PostgreSQL 18 로컬 컨테이너에 운영과 같은 테이블 구조와 인덱스를 만들고, 실험용 데이터 60만 행을 넣었어요. 그중 오래된 30만 행을 지웠어요. 아래 값은 CPU 1개, 메모리 512MiB 조건에서 세 번 실행한 결과의 중앙값이에요.

| 항목                    | `DELETE` | 날짜 파티션 `DROP` |
| ----------------------- | -------: | -----------------: |
| 제거 시간               |  0.162초 |            0.042초 |
| 제거 구간 WAL           |  71.27MB |            0.056MB |
| 이후 vacuum WAL         |  21.28MB |                0MB |
| 제거 후 테이블과 인덱스 | 147.25MB |            73.77MB |

속도만 보면 파티션이 더 좋았어요. 제거 시간은 약 4배 짧았고, 제거할 때 생긴 WAL은 71.27MB에서 0.056MB로 줄었어요.

근데 현재는 `(vehicle_observation_id, target_stop_order)` 조합이 유일해야 한다는 규칙으로 같은 평가가 두 번 저장되는 걸 막고 있어요. 날짜 파티션을 쓰려면 이 키에 파티션 날짜를 넣거나 중복 방지 구조를 따로 만들어야 해요. `evaluation_archive_member`가 예측 원본을 가리키는 외래 키도 함께 바꿔야 했어요.

파티션을 제거해도 S3로 과거 결과를 옮기는 작업이 한 번에 최대 100행씩 처리하던 문제는 그대로예요. 삭제에는 유리했지만 이것만으로 적체를 해결할 수는 없었어요.

## 두 번째 시도: 평가를 덜 하면 되지 않을까?

다음은 처음 생각했던 “덜 쌓기”예요. 기존 8개 노선에서 2026년 10월 5일에 받은 관측을 시간순으로 다시 처리했어요.

- 같은 차량은 마지막 평가로부터 60초가 지나면 다시 평가
- 60초 전이라도 정류장이나 방향이 바뀌면 바로 평가
- 승하차 통계에 쓰는 한 정류장 앞 예보는 무조건 평가

평가 등록은 `1,684,742건`에서 `688,694건`으로 59.12% 줄었어요. 평균 좌석 오차도 `3.23619석`에서 `3.24658석`으로 0.01039석만 늘었고요.

![모든 예보를 평가한 결과와 평가 간격을 60초로 줄인 결과 비교](assets/salmonbus-portfolio/04-evaluation-sampling-experiment.png)

여기까지만 보면 적용해도 될 것 같았어요. 그래도 평균만 보면 크게 틀린 예측이 가려질 수 있어요. 두 방식의 예측값이 3석 넘게 달라진 사례를 따로 꺼내봤어요.

3500번 노선의 08:41 예측이에요. 이 버스는 08:55에 도착했을 때 잔여석이 23석으로 관측됐어요.

| 방식           | 예측 잔여석 | 절대 오차 | 보정 후 만석 확률 |
| -------------- | ----------: | --------: | ----------------: |
| 모든 평가 유지 |     24.37석 |    1.37석 |            26.46% |
| 평가 횟수 축소 |     17.34석 |    5.66석 |            47.67% |

모든 평가를 유지했을 때는 실제 잔여석과 1.37석 차이였어요. 평가를 줄이자 5.66석 차이로 벌어졌어요. 평균 오차만 봤다면 놓쳤을 결과예요.

왜 달라졌을까요?

차이는 당일 보정에서 생겼어요. 당일 보정은 그날 확인한 예측 결과로 이후 예측값을 조정하는 일이에요.

같은 날, 같은 노선, 같은 예측 거리에서 쓸 수 있는 평가 결과가 2,800건에서 989건으로 줄었어요. 두 방식 모두 실제 만석 관측은 0건이었어요. 근데 평가를 줄인 쪽은 “오늘 이 노선은 만석이 아니었다”는 결과를 훨씬 덜 반영했어요.

보정 로직은 실제 평가 결과가 50건 이상일 때 움직여요. 결과 몇 건만으로 확률이 크게 바뀌지 않도록 기존 평균 확률에 200건의 가상 표본도 더해요.

```text
보정에 쓰는 만석 비율
= (실제 만석 건수 + 200 × 기존 평균 만석 확률)
  / (실제 정산 건수 + 200)
```

실제 평가 건수가 줄면 가상 표본 200건의 영향이 더 커져요. 평가를 줄인 쪽은 그날 쌓인 “만석 아님”보다 기존 평균을 더 많이 따라갔어요. 보정된 만석 확률은 26.46%에서 47.67%로 올라갔고, 예상 잔여석은 내려갔어요.

이 사례 하나만 그런 것도 아니었어요. 3석 넘게 달라진 예측 375건 중 332건의 오차가 커졌어요.

평균 오차 차이는 약 0.01석이었지만, 개별 예측은 달랐어요. **당일 보정 입력까지 줄이는 방식은 쓰지 않기로 했어요.**

## 세 번째 시도: 평가는 유지하고 저장만 나눴어요

평가를 줄이면 안 된다면, 모든 결과를 꼭 같은 크기로 저장해야 할까요?

이번에는 평가 횟수에 손대지 않았어요. 모든 예측을 원래대로 실제 관측과 비교하고, 그 결과를 당일 보정과 승하차 통계에 넣었어요. 저장할 때만 상세 결과와 최소 결과로 나눴어요.

아래 조건에 해당하는 결과는 기존처럼 상세하게 남겨요.

- 처음 본 차량이거나 마지막 상세 저장 후 60초가 지난 경우
- 정류장, 방향, 노선 판본, 모델이 바뀐 경우
- 승하차 통계에 쓰는 한 정류장 앞 예측
- 방향을 알 수 없거나 과거 관측을 다시 처리한 경우
- 건너뜀, 도착 미확인, 좌석 정보 없음, 품질 제외처럼 정상 정산이 아닌 경우

그 외 정상 결과는 `forecast_evaluation_compact`에 넣어요. 예측을 찾는 키, 도착 관측 ID, 실제 잔여석, 평가 시각, 도착 시각과 당시 운행 키만 남겨요. 차량 ID, 도착 정류장, 노선 정보의 판본은 원본 관측에서 다시 읽을 수 있으니 또 저장하지 않아요.

![모든 예보를 정산한 뒤 상세 결과와 최소 결과로 저장하는 조건](assets/salmonbus-portfolio/05-evaluation-storage-decision.png)

결과를 읽는 기존 코드도 크게 바꾸고 싶지 않았어요. 그래서 상세 테이블과 최소 테이블을 `UNION ALL`로 합쳐 보여주는 뷰를 만들었어요. 뷰는 여러 테이블을 하나의 조회 대상으로 보이게 해줘요. 기존 코드는 이 뷰에서 같은 형태의 결과를 읽어요.

최소 결과는 도착 관측을 외래 키로 가리켜요. 외래 키는 다른 테이블의 원본이 잘못 지워지지 않도록 연결하는 DB 규칙이에요. 다시 읽어야 할 원본이 먼저 삭제되는 걸 막기 위해 넣었어요.

한 정류장 앞 예측의 승하차 통계는 상세 결과만 읽는 별도 뷰로 뺐어요. 통계를 계산할 때마다 최소 결과 전체를 원본 관측과 다시 연결해 읽으면 조회 비용이 늘어나기 때문이에요.

같은 차량이 같은 정류장에 있고 15초마다 예측 12개를 만든다면 아래처럼 저장돼요. 실제 측정값이 아니라 동작을 보여주기 위한 예시예요.

| 관측 시각 | 정산 대상 | 상세 저장 | 최소 저장 |
| --------- | --------: | --------: | --------: |
| 10:00:00  |      12개 |      12개 |       0개 |
| 10:00:15  |      12개 |       1개 |      11개 |
| 10:00:30  |      12개 |       1개 |      11개 |
| 10:00:45  |      12개 |       1개 |      11개 |
| 10:01:00  |      12개 |      12개 |       0개 |

합계만 메모리에 들고 있으면 저장량을 더 줄일 수 있어요. 근데 백그라운드 작업을 하는 worker가 재시작하면 집계 근거를 다시 만들기 어렵고, 같은 평가를 두 번 반영했는지도 판단하기 어려워요. 복구와 중복 방지를 위해 최소 결과는 DB에 남겼어요.

## 저장량과 예측은 얼마나 달라졌을까요?

같은 관측과 같은 예측 모델을 최종 방식으로 다시 처리했어요. 이번에는 모든 평가 결과를 당일 보정과 승하차 통계에 넣고, 상세 저장 여부만 나눴어요.

| 확인한 값                  | 기존 전체 저장 | 상세와 최소 저장 분리 |
| -------------------------- | -------------: | --------------------: |
| 생성한 예측                |    1,684,742건 |           1,684,742건 |
| 확률 분포가 달라진 예측    |           기준 |                   0건 |
| 평균 좌석 오차             |      3.23619석 |             3.23619석 |
| 정상 정산의 상세 저장 대상 |    1,411,497건 |             586,954건 |

확률 분포가 달라진 예측은 0건이었어요. 앞에서 17.34석까지 내려갔던 3500번 예측도 기존과 같은 24.37석이었어요. 정상 평가 중 상세하게 저장할 대상은 58.42% 줄었어요.

이번에는 **예측 결과를 유지하면서 저장할 상세 데이터를 줄였어요.**

그럼 실제 저장 공간은 얼마나 줄까요? PostgreSQL 18에 실험용 데이터 10만 행을 넣어 비교했어요.

| 저장 방식                     | 테이블과 인덱스 크기 |
| ----------------------------- | -------------------: |
| 모두 상세 저장                |     27,910,144바이트 |
| 상세 41,584건 + 최소 58,416건 |     20,316,160바이트 |

테이블과 인덱스를 합쳐 27.21% 줄었어요. 상세 저장 대상은 58% 줄었는데 저장 공간은 왜 27%만 줄었을까요? 최소 테이블에도 기본 키, 외래 키와 도착 시각 인덱스가 필요해서 행 수와 바이트가 같은 비율로 줄지는 않아요.

## 운영 지표에서 확인한 이관 병목

로컬에서 같은 데이터를 다시 처리한 결과가 좋다고 운영 DB도 바로 덜 쌓이는 건 아니에요. Grafana의 PostgreSQL 지표와 worker 로그를 같은 시간대로 맞춰봤어요.

2026년 10월 22일 08:40부터 08:55 KST까지 worker는 이관 작업 74번으로 5,304행을 삭제했어요. 한 번에 평균 약 71.7행, 최대 100행이었어요. 성공한 작업은 평균 약 5.33초가 걸렸고, 95%는 약 5.63초 안에 끝났어요. 같은 15분 동안 실패 로그는 3건 있었어요.

| Grafana에서 본 값                         | 08:55 KST 기준 |
| ----------------------------------------- | -------------: |
| 평가 결과 입력 속도, 직전 15분 평균       |  약 112.3행/초 |
| 평가 결과 삭제 속도, 직전 15분 평균       |    약 6.2행/초 |
| `forecast_evaluation_result` 추정 생존 행 |  약 8,405만 행 |
| 테이블 크기                               |        10.99GB |
| 인덱스 크기                               |         7.71GB |
| 대기 중인 DB 잠금 연결                    |            0개 |

대기 중인 DB 잠금은 0개였어요. 쿼리 하나가 잠겨서 멈춘 게 아니라, 한 번에 최대 100행을 옮기고 다음 작업까지 기다리는 처리 속도로는 초당 약 112건의 입력을 따라갈 수 없었어요.

그래서 이관 코드는 기본 500행을 읽고, 4MiB 파일 크기와 SQL 제한 시간 안에서 최대 1,000행까지 처리할 수 있게 바꿨어요. 위 Grafana 수치는 운영 worker가 여전히 최대 100행씩 처리하던 때의 기록이에요. 새 설정을 적용한 뒤의 운영 삭제 속도로 읽으면 안 돼요.

이관 코드를 바꾼 뒤에도 삭제량만 보면 원인을 놓칠 수 있어요. 저장량을 나눠 줄인 만큼 어느 테이블에 얼마나 쌓이는지, 삭제 과정에서 DB가 쓰는 자원은 어떤지도 함께 볼 지표로 정했어요.

- 평가 결과의 초당 입력과 삭제
- 이관 묶음의 행 수, 처리 시간, 실패 건수
- 상세 테이블과 최소 테이블의 생존 행, 테이블 크기, 인덱스 크기
- WAL 생성량, dead tuple, autovacuum, 잠금 대기

상세 결과가 줄었다는 사실만으로 전체 저장 비용이 줄었다고 판단할 수는 없어요. 최소 테이블과 인덱스에도 공간이 필요하고, 이관 중에는 WAL과 vacuum 비용도 생겨요. 로컬 저장 공간 비교에서 상세 저장 대상은 58.42% 줄었지만 테이블과 인덱스를 합친 크기는 27.21% 줄었던 이유도 여기에 있어요.

## 평가가 아니라 중복 저장을 줄였어요

처음에는 평가 건수를 59% 줄이면 저장 문제도 풀릴 줄 알았어요. 평균 오차 차이도 약 0.01석이어서 괜찮아 보였고요. 근데 개별 예측과 당일 보정 계산을 살펴보니 정확도에 필요한 입력까지 줄이고 있었어요. 3500번 노선의 예측은 실제 잔여석과의 오차가 5.66석까지 커졌어요.

최종 구조로 같은 데이터를 다시 처리했을 때 `1,684,742건`의 평가를 모두 유지했어요. 달라진 예측 분포는 0건이었고, 정상 평가의 상세 저장 대상은 58.42% 줄었어요. 실험용 데이터 10만 행에서는 테이블과 인덱스가 27.21% 작았어요.

**평가 횟수는 지키고, 원본 관측에서 다시 읽을 수 있는 값의 중복 저장을 줄였어요.** 평균 오차만 보고 평가를 줄였다면 이 선택을 하지 못했을 거예요.
