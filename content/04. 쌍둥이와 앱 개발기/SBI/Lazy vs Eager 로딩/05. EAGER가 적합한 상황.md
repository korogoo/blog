## EAGER가 합리적인 세 가지 조건

EAGER를 선택하는 게 자연스러운 케이스는 세 조건이 동시에 맞을 때다

1. **단건 연관** (`@ManyToOne`) 이다
2. 연관 객체가 **항상** 필요하다
3. **`findAll()`로 목록 조회가 없다**

세 조건 중 하나라도 빠지면 LAZY + JOIN FETCH가 더 안전하다

<br/>

## 바리바리 케이스 - 핀 단건 조회

핀 상세 화면에서는 항상 코스 제목과 코스 썸네일이 필요하다

```java
// PinJpaEntity
@ManyToOne(fetch = FetchType.EAGER)  // 항상 코스가 필요하므로
@JoinColumn(name = "course_id", nullable = false)
private CourseJpaEntity course;
```

`pinJpaRepository.findById(pinId)`를 호출하면 JOIN 한 방으로 해결된다

```sql
Hibernate: 
select p1_0.id,p1_0.name,c1_0.id,c1_0.title,c1_0.thumbnail_url
from pin p1_0
left outer join course c1_0 on c1_0.id=p1_0.course_id
where p1_0.id=?
```

LAZY였다면 `pin.getCourse().getTitle()` 호출 시점에 쿼리가 추가로 나갔을 것이다

<br/>

## `@ManyToOne` EAGER인데 findAll이 있으면?

핀 목록을 조회하는 화면이 생기면 얘기가 달라진다

```sql
Hibernate: select p1_0.id,p1_0.name,p1_0.course_id from pin p1_0
Hibernate: select c1_0.id,c1_0.title from course c1_0 where c1_0.id=?
Hibernate: select c1_0.id,c1_0.title from course c1_0 where c1_0.id=?
Hibernate: select c1_0.id,c1_0.title from course c1_0 where c1_0.id=?
-- 핀 수(N)만큼 반복
```

EAGER여도 `findAll`에서는 N+1이 발생한다
이 경우는 LAZY로 바꾸고 JOIN FETCH를 명시하는 게 맞다

<br/>

## 내가 생각해본 기준

✨ **EAGER를 유지하는 판단 기준**

- 해당 엔티티를 조회하는 진입점이 단건(`findById`)뿐이다
- 연관 객체 없이 응답을 만들 수 있는 화면이 없다
- 팀 내에서 "이 연관은 항상 같이 온다"는 암묵적 규칙이 있다

<br/>

✨ **LAZY로 바꾸는 신호**

- 목록 조회 API가 추가됐다
- SQL 로그에서 같은 테이블 SELECT가 반복해서 찍힌다
- 연관 객체가 필요 없는 응답이 생겼다

<br/>

### 💬 결국 EAGER를 써도 되는 상황이 맞긴 한가?

`@ManyToOne` + 단건 조회 전용이라면 EAGER가 오히려 코드를 단순하게 만든다  
JOIN FETCH를 매번 JPQL에 쓰는 것보다 선언 하나로 끝난다  
단, findAll이 생기는 순간 LAZY로 전환해야 한다는 걸 팀이 인지하고 있어야 한다
