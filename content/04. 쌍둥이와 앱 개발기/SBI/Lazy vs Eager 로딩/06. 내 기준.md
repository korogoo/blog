## 판단 흐름

```
연관 객체가 필요한가?
│
├─ 항상 필요 + 단건(@ManyToOne)
│   └─ EAGER 고려 가능 (단, findAll 없을 때만)
│
└─ 가끔 필요 / 컬렉션(@OneToMany)
    │
    ├─ 페이징 없음      -> JOIN FETCH
    ├─ 페이징 있음      -> @BatchSize
    └─ fetch 대상 가변  -> @EntityGraph
```

> EAGER는 "항상 가져온다"가 아니라 "언제 어떻게 가져오는지 JPA에게 맡긴다" - 결과를 예측할 수 없다

<br/>

## 실전 체크리스트

❓ `@OneToMany`에 fetch 타입을 별도로 선언하지 않았는가?
-> LAZY가 기본이다 - 의도한 것이라면 그냥 두면 된다

❓ `findAll()`을 호출하고 연관 컬렉션에 접근하는가?
-> N+1이 발생한다 - JOIN FETCH 또는 @BatchSize를 써야 한다

❓ JPQL을 직접 쓰면서 fetch = EAGER에 의존하고 있는가?
-> JPQL은 fetch 전략을 무시한다 - JOIN FETCH를 명시해야 한다

❓ `@OneToMany`에 EAGER를 설정하고 페이징도 쓰는가?
-> Hibernate가 전체를 메모리에 올린 뒤 자른다 - @BatchSize로 바꿔야 한다

❓ `@ManyToOne`이 EAGER 기본인데 목록 조회가 있는가?
-> N+1을 확인해라 - LAZY + JOIN FETCH 패턴이 안전하다

<br/>

## 남은 한계

@BatchSize는 최적화 수단이지 N+1의 완전한 해결이 아니다
JOIN FETCH가 많아지면 JPQL 관리가 복잡해진다
QueryDSL을 도입하면 동적 fetch 전략을 더 깔끔하게 다룰 수 있다 - 아직 미탐색 영역
