## findById는 정말 JOIN 한 방에 가져오나?

그렇다

`courseJpaRepository.findById(1L)`을 호출하면 JPA가 JOIN 쿼리를 만든다

```sql
Hibernate: select c1_0.id,c1_0.title,c1_0.thumbnail_url,p1_0.course_id,p1_0.id,p1_0.name
           from course c1_0
           left outer join pin p1_0 on c1_0.id=p1_0.course_id
           where c1_0.id=?
```

코스 단건 조회에서는 기대대로 동작했다

<br/>

## findAll은 왜 N+1이 터지나?

근데 목록 조회는 예상과 달랐다

`courseJpaRepository.findAll()`을 호출하면 JPA는 먼저 전체 코스를 조회한다

```sql
Hibernate: select c1_0.id,c1_0.title,c1_0.thumbnail_url from course c1_0
Hibernate: select p1_0.course_id,p1_0.id,p1_0.name from pin p1_0 where p1_0.course_id=?
Hibernate: select p1_0.course_id,p1_0.id,p1_0.name from pin p1_0 where p1_0.course_id=?
Hibernate: select p1_0.course_id,p1_0.id,p1_0.name from pin p1_0 where p1_0.course_id=?
-- 코스 수(N)만큼 반복
```

EAGER이면 처음에 다 가져온다면서,,,왜 JOIN을 안 하는지 이해가 안 됐다

<br/>

✨ **즉시로딩의 '즉시'는 조회 시점의 즉시를 의미한다**

처음에는 즉시 로딩을 "쿼리 한 방으로 즉시 가져온다"는 쿼리 관점으로 생각했다

그런데 쿼리의 개수가 기준이 아니다  
쿼리가 몇 개든, 그 데이터를 쓰든 안 쓰든,  
엔티티를 로드하는 시점에 연관 데이터를 모두 올린다는 의미다

JOIN이냐 추가 SELECT냐는 Hibernate가 상황에 따라 결정한다  
findAll에서는 JOIN 대신 추가 SELECT를 선택하기 때문에 N+1이 발생한다

<br/>

## 그러면 단건 / 컬렉션 반환이 기준인가?

그렇다

`findById`처럼 단건을 반환하는 메서드는 JOIN으로 나가고,  
`findAll`처럼 컬렉션을 반환하는 메서드는 N+1이 발생한다

커스텀 메서드도 동일하다

```sql
-- findByPinsId(1L) → Optional<CourseEntity> (단건) → JOIN
Hibernate: select c1_0.id,c1_0.title from course c1_0
           inner join pin p1_0 on c1_0.id=p1_0.course_id
           where p1_0.id=?

-- findByPinsSequence(3) → List<CourseEntity> (컬렉션) → N+1
Hibernate: select c1_0.id,c1_0.title from course c1_0
           inner join pin p1_0 on c1_0.id=p1_0.course_id
           where p1_0.sequence=?
-- 이후 각 course마다 pin SELECT가 N번 추가로 나간다
```

WHERE 절 조건이 뭔지는 상관없다  
단건을 반환하느냐, 컬렉션을 반환하느냐가 기준이다

<br/>

## JPQL을 쓰면 EAGER가 무시된다

```java
@Query("SELECT c FROM CourseJpaEntity c")
List<CourseJpaEntity> findAllWithJpql();
```

이 JPQL은 fetch = EAGER 설정을 무시하고 코스만 조회한다  
각 코스의 `pins`에 접근할 때 추가 쿼리가 나간다

연관 객체까지 함께 가져오려면 `JOIN FETCH`를 직접 써야 한다

```java
@Query("SELECT c FROM CourseJpaEntity c JOIN FETCH c.pins")
List<CourseJpaEntity> findAllWithPins();
```

<br/>

### 💬 EAGER가 이렇게 예측하기 어려운 거였나?

정리하면 같은 EAGER 설정에서도 세 케이스가 전부 다르다

- 단건 메서드(`findById`, `findByXxx` -> 단건) -> JOIN
- 컬렉션 메서드(`findAll`, `findByXxx` -> List) -> N+1
- JPQL → fetch 전략 무시, JOIN FETCH 직접 명시 필요

Hibernate가 알아서 최적화하기 때문에  
연관관계나 로직이 복잡해질수록 어떤 SQL이 나갈지 예측하기 힘들어진다
