## findById는 정말 JOIN 한 방에 가져오나?

그렇다

`courseJpaRepository.findById(1L)`을 호출하면 JPA가 JOIN 쿼리를 만든다

```sql
SELECT c.*, p.*
FROM course c
LEFT OUTER JOIN pin p ON p.course_id = c.id
WHERE c.id = 1
```

코스 단건 조회에서는 기대대로 동작했다

<br/>

## findAll은 왜 N+1이 터지나?

근데 목록조회는 예상과 달랐다

`courseJpaRepository.findAll()`을 호출하면 JPA는 먼저 전체 코스를 조회한다

```sql
SELECT * FROM course
```

그 다음 각 코스마다 핀 목록을 개별 쿼리로 가져온다

```sql
SELECT * FROM pin WHERE course_id = 1
SELECT * FROM pin WHERE course_id = 2
SELECT * FROM pin WHERE course_id = 3
-- 코스 수(N)만큼 반복
```

EAGER이면 처음에 다 가져온다면서,,,왜 JOIN을 안 하는지 이해가 안 됐다

<br/>

✨ **즉시로딩의 '즉시'는 조회 시점의 즉시를 의미한다**

'처음 쿼리 한 방으로 데이터를 즉시 가져온다' 이런식으로  
처음에는 즉시 로딩을 쿼리 관점에서 생각했다

그런데 쿼리 관점이 아닌 좀 더 넓은 조회 시점으로 봐야한다

쿼리의 개수가 기준이 아닌  
쿼리가 몇개든, 그 데이터를 쓰든 안 쓰든,  
즉시 모든 연관 데이터를 로딩한다는 의미이다

<br/>

💬 **그래서 왜 JOIN 이 아닌 SELECT 일까?**

Hibernate 최적화 로직에 의해 결정된 것이다  
findAll에서는 JOIN 대신 추가 SELECT를 선택하기 때문이다

결과적으로 전체 조회 1번 + 각 코스의 핀 조회 N번 쿼리가 발생한다

<br/>

## 그럼 LAZY 쓰려면 N+1 문제는 안고 가야하나?

⚠️ **JPQL / Native Query는 fetch 전략을 따르지 않는다**

```java
@Query("SELECT c FROM CourseJpaEntity c")
List<CourseJpaEntity> findAllWithJpql();
```

이 JPQL은 fetch = EAGER 설정을 무시하고 코스만 조회한다  
그리고 각 코스의 `pins`에 접근할 때 추가 쿼리가 나간다


즉, 이 방법으로 원하는 쿼리에서 연관 객체까지 함께 가져올 수 있다

```java
// fetch 전략에 의존하지 말고, JPQL에 명시한다
@Query("SELECT c FROM CourseJpaEntity c JOIN FETCH c.pins")
List<CourseJpaEntity> findAllWithPins();
```

<br/>

### 💬 아,, EAGER가 이렇게 예측하기 어려워서 사람들이 기피하는 건가?

위 예시만 해도  

- findById는 JOIN  
- findAll은 N+1  
- JPQL은 fetchType 무시됨

세 가지 케이스에서 전부 다른 SQL이 나간다

hibernate 가 알아서 최적화해서 가져오기 때문에   
연관관계나 로직이 복잡해질수록 어떤 SQL 이 나갈지 예측하기 힘들어진다
