## 연관 객체를 언제 불러오나?

엔티티를 로드하는 순간에 연관 객체도 함께 불러오는 전략이다

`CourseJpaEntity`를 조회하면 JPA가 자동으로 `PinJpaEntity` 목록도 같이 가져온다

```java
@OneToMany(
    mappedBy = "course",
    fetch = FetchType.EAGER  // 명시하면 즉시 로드
)
private List<PinJpaEntity> pins = new ArrayList<>();
```

## `@ManyToOne`은 왜 EAGER가 기본인가?

단건 연관이기 때문이다

`PinJpaEntity`를 가져올 때 `CourseJpaEntity` 하나를 함께 로드하는 건 JOIN 한 번으로 처리 가능하다

LAZY가 기본인 `@OneToMany`와 달리, `@ManyToOne`은 EAGER가 기본이다  
JPA 설계하신 분들이 트레이드오프를 잘 비교해서 한 결정이겠지? 싶다

```java
// PinJpaEntity - 명시적으로 LAZY를 선언했다
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "course_id", nullable = false)
private CourseJpaEntity course;
```

<br/>

---

## `@OneToMany`는 왜 LAZY가 기본인가?

⚠️ **메모리 부하**

EAGER 처럼 매번 컬랙션까지 한 번에 조회하는 것은 메모리에 부하가 있을 수 있다

`CourseJpaEntity` 하나에 핀이 20개 있으면, EAGER는 코스를 불러오는 즉시 핀 20개를 모두 메모리에 올린다  
즉, 코스 목록 100개를 조회하면 핀 2000개가 한꺼번에 올라온다

<br/>

⚠️ **매번 모두 가져오는 건 비효율적**

쓰지 않을 핀 목록까지 무조건 로드하는 것은 비효율적이다  
필요할 때만 딱딱 쿼리를 날릴 수 있게 설계한 것이다

<br/>

---
### 💬 LAZY는 어떻게 동작하나?

실제 접근하기 전까지 프록시 객체로 대체해 둔다

`course.getPins()`를 호출하는 순간 그때서야 SELECT가 나간다

그리고 트랜잭션이 열려 있어야 조회가 가능하다  
트랜잭션 밖에서 접근하면 `LazyInitializationException`이 터진다
