## 왜 파일에 저장하면 안 될까?

## 파일이 뭔데?

> ==파일== : 정보를 담는 단위

파일 하나에는 내용만 들어있는 게 아니다

```
    ┌──────────────┐
    │  attribute   │  형식, 위치, 크기 ...
    ├──────────────┤
    │              │
    │   내용        │
    │              │
    └──────────────┘
```

<br/>

위쪽의 부가 정보를 ==메타데이터==라고 부른다

내가 만든 적 없는데 파일마다 붙어 있는 이유는, 이걸 만드는 게 내가 아니라 OS라서다

---

## 파일 시스템이 뭔데?

> ==파일 시스템== : 보조기억장치를 효과적으로 관리하기 위해 파일과 디렉터리 형태로 저장하고 관리하는 OS 내부 프로그램

우리가 아는 그 폴더 구조가 파일 시스템이다

```
/
├── Documents
│   ├── F1
│   └── F2
├── Downloads
│   ├── F3
│   └── F4
└── Desktop
    ├── F5
    └── F6
```

<br/>

프로그램이 파일을 열면 OS가 그 프로세스에 번호표를 하나 쥐여준다

> ==file descriptor== : 저수준에서 파일을 식별하는 정보

<br/>

여기서 걸리는 게 있었다

파일 시스템도 트리 구조고, 보조기억장치에 저장하고, DB도 트리 구조고 보조기억장치에 저장한다

**똑같은 트리, 똑같은 디스크인데 우리는 왜 파일 시스템을 안 쓰고 DB를 쓰지?**

---

## 게시글을 파일에 저장해보자

`posts.txt` 하나 만들어서 게시글을 넣어봤다

```
posts.txt

post_id=1 title=제목1 조회수=1
post_id=2 title=제목2 조회수=3
...
```

<br/>

돌아가긴 한다

그런데 여기다 `post_id=1 title= 조회수=안녕` 을 써넣어도 아무도 안 막는다

<br/>

> ==무결성== : 데이터가 지켜야 할 규칙, 즉 제약조건을 만족하는지
>
> ==일관성== : 데이터가 항상 무결성 규칙을 만족하는 상태를 유지하는지

<br/>

⚠️ **파일에는 규칙을 걸어둘 자리가 없다**

제목이 비면 안 된다거나 조회수는 숫자여야 한다는 걸 파일 자신은 모른다

지키게 하려면 파일을 읽는 쪽 코드가 매번 검사해야 하는데, 읽는 프로그램이 두 개가 되는 순간 검사도 두 벌이 된다

---

## 여러 명이 동시에 들어오면?

조회수를 1 올리는 일은 세 단계로 쪼개진다

```
open()   파일을 연다
  ↓
write()  조회수를 읽고 +1 해서 다시 쓴다
  ↓
close()  파일을 닫는다
```

<br/>

**이 사이에 다른 요청이 끼어들면 어떻게 막지?**

답은 못 막는다는 것이었다

<br/>

⚠️ **OS에는 순서를 보장한다는 개념 자체가 없다**

프로세스는 순간순간 자기 명령을 수행할 뿐이다

여러 프로세스가 어떤 순서로 끼어들지를 OS가 정해주지 않는다

```
[프로세스 A]              [프로세스 B]
조회수 읽음 (1)
                          조회수 읽음 (1)
2 로 씀
                          2 로 씀

두 명이 봤는데 조회수는 2 다
```

<br/>

그래서 내 코드에서 뭐가 달라지냐면, `synchronized` 를 아무리 걸어도 소용이 없다  
서버를 두 대로 늘리는 순간 서로 다른 프로세스가 되기 때문이다

---

## 파일이 여러 개면?

게시글에 작성자를 붙이려면 `users.txt` 가 하나 더 필요하다

그런데 유저 한 명이 탈퇴하면?

```
users.txt 에서 지운다
  ↓
posts.txt 를 열어서 그 유저의 글을 찾는다
  ↓
comments.txt 도 열어서 찾는다
  ↓
... 하나라도 빠뜨리면 유령 데이터가 남는다
```

<br/>

이 외에도 파일로 버티기 힘든 게 더 있었다

| 문제 | 무슨 뜻이냐면 |
|---|---|
| 중복 저장 | 같은 유저 이름이 파일마다 복사돼 있다 |
| 연관 데이터 변경 | 한 곳을 고치면 나머지를 다 찾아다녀야 한다 |
| 정교한 검색 | "조회수 10 이상인 글"을 찾으려면 처음부터 끝까지 읽어야 한다 |
| 백업과 복구 | 쓰다가 죽으면 어디까지 썼는지 알 방법이 없다 |

---

## 그래서 DB는 뭐가 다른가

똑같이 트리 구조에, 똑같이 보조기억장치에 저장한다

그런데 동시성도 제어해주고, 일관성과 무결성도 보장해주고, 검색도 빠르다

<br/>

✨ **파일이 안 해주던 걸 대신 해주는 프로그램이 붙어 있다**

세 가지가 핵심이었다

```
B+Tree 구조        범위 검색과 정렬된 조회를 위해 설계된 트리
                   (파일 시스템의 트리는 '이름 -> 위치' 검색용이다)

동시성 제어         읽고-고치고-쓰는 동안 다른 요청을 기다리게 하거나
(락 매니저 / MVCC)  아예 버전을 분리해서 처리한다

트랜잭션 로그(WAL)  커밋 전에 "이거 바꿀 거다"를 미리 적어둔다
                   장애가 나도 로그를 재생하거나 롤백할 수 있다
```

<br/>

오호라..되게 좋구나..

❓ 근데 이걸 어떻게 쓰는 건데?

## DB랑 어떻게 대화하는 걸까?

## DBMS가 정확히 뭔데?

> ==DBMS (DataBase Management System)== : 데이터베이스를 관리하기 위한 프로그램

앞에서 본 세 가지(B+Tree, 동시성 제어, WAL)를 실제로 해주는 게 이 프로그램이다

MySQL, PostgreSQL 같은 게 여기 해당한다

<br/>

층으로 그리면 이렇게 된다

```
    Application     내가 짠 서버
        ↓
      DBMS          MySQL
        ↓
       OS
        ↓
    Hardware        디스크
```

<br/>

✨ **DBMS도 결국 하나의 프로세스로 돌아간다**

특별한 무언가가 아니라 그냥 켜져 있는 프로그램이다

이걸 알고 나니 다음 질문이 자동으로 따라왔다

---

## 그럼 어떻게 도달하지?

내 서버가 데이터를 조작하려면 DBMS 프로세스까지 가야 한다

그런데 보통 이 둘은 ==서로 다른 컴퓨터==에서 돌아간다

```
[내 서버 호스트]              [DB 호스트]

  내 서버 프로세스     ?        DBMS 프로세스
```

<br/>

**그럼 네트워크 통신이 필요하겠네, 근데 뭘로?**

일단 어느 컴퓨터인지를 알아야 한다

> 다른 네트워크 간의 통신에는 호스트를 식별하는 주소가 필요하다 -> ==IP==

<br/>

그런데 IP로는 컴퓨터까지밖에 못 간다

패킷의 최종 목적지는 그 컴퓨터에서 돌아가는 프로세스다

> 그래서 ==포트 번호==로 프로세스를 지목한다

<br/>

MySQL을 띄우면 늘 보이던 `3306` 이 이거였다

```
접속 정보    jdbc:mysql://10.0.1.20:3306/mydb
                        └─ IP ─┘ └포트┘
                        어느 컴퓨터  그 안의 어느 프로세스
```

---

## 왜 TCP인가

프로세스를 지목하는 방법은 두 가지다

TCP와 UDP 중에 뭘 골라야 할까

<br/>

**DB한테 우리는 뭘 기대할까?**

아주 정확하고, 유실 없이 안전해야 한다

주문 100건을 보냈는데 3건이 증발하거나 순서가 뒤바뀌면 안 된다

<br/>

✨ **기대하는 성질이 그대로 프로토콜 선택이 된다**

```
쿼리 패킷이 정확한 순서로, 유실 없이 도착해야 한다
                 ↓
              TCP
```

<br/>

### 💬 그럼 HTTP는 왜 안 쓰나?

HTTP도 TCP 위에서 도는 프로토콜이다

다만 요청 하나 보낼 때마다 헤더를 잔뜩 붙이고, 기본적으로 한 번 주고받고 끝나는 구조다

DB는 커넥션을 맺어두고 계속 재사용하는 쪽이 이득이라, 자기 규격을 따로 쓴다

커넥션 풀이 하는 일이 이 연결을 미리 만들어두고 빌려주는 것이다

---

## 내가 보낸 SELECT는 어떻게 나가나

`SELECT * FROM post` 를 실행하면 이런 순서로 흘러간다

```
"SELECT * FROM post"
   ↓ DB 프로토콜 규격에 맞게 바이너리로 인코딩
바이트 덩어리
   ↓ TCP 가 순서와 유실을 책임진다
   ↓ IP 가 어느 호스트로 갈지 라우팅한다
전기 신호로 케이블/와이파이에 실린다
   ↓
DB 호스트 도착 -> 포트 3306 -> DBMS 프로세스
```

<br/>

TCP/IP 모델의 4계층이 각각 어디를 맡는지도 여기서 맞춰졌다

| 계층 | 여기서 하는 일 |
|---|---|
| 애플리케이션 | 쿼리를 DB 규격 바이트로 만든다 |
| 전송 | 포트로 프로세스를 지목하고, 순서와 유실을 책임진다 |
| 인터넷 | IP로 어느 호스트로 갈지 라우팅한다 |
| 링크 | 실제 전기 신호로 실어 보낸다 |

---

## 그래서 쿼리가 뭐냐면

이렇게 DBMS한테 보내는 요청 자체를 ==Query(질의)==라고 부른다

그리고 그 대표적인 규격이 SQL이다

<br/>

✨ **내 서버는 DBMS의 클라이언트다**

브라우저가 내 서버한테 요청을 보내는 것과 똑같은 구조가 한 층 더 있었던 거다

```
브라우저  ──요청──>  내 서버  ──쿼리──>  DBMS
(클라이언트)        (서버)              (서버)
                   (클라이언트)
```

<br/>

그래서 내 코드에서 뭐가 달라지냐면, DB가 느린 이유를 나눠서 볼 수 있게 된다

쿼리 자체가 느린 건지, 커넥션을 못 얻어서 기다리는 건지, 네트워크를 건너느라 느린 건지가 다른 문제다

<br/>

❓ 이제 대화하는 법은 알았다  
그런데 조회수 올리다 중간에 죽으면 어떻게 되는 거지?

## 다 되거나 다 안 되거나

## 트랜잭션이 뭔데?

> ==트랜잭션== : 데이터베이스의 논리적 상호작용의 단위

말이 어려운데, 계좌 이체를 보면 바로 이해된다

```
A 계좌에서 1만원 뺀다
      ↓
B 계좌에 1만원 넣는다
```

<br/>

**여기 화살표 위치에서 서버가 죽으면?**

돈이 세상에서 사라진다

<br/>

이 두 줄은 따로따로 의미가 없고 ==같이 성공하거나 같이 실패해야 하는 한 덩어리==다

그 덩어리를 트랜잭션이라고 부른다

---

## 왜 필요한데?

일부만 반영된 어중간한 상태를 막기 위해서다

```
[트랜잭션 없음]              [트랜잭션 있음]

A 에서 뺌                    BEGIN
   ✗ 죽음                    A 에서 뺌
                                ✗ 죽음
돈이 사라진 채로 남는다        ROLLBACK
                             아무 일도 없던 상태로 돌아간다
```

<br/>

그래서 내 코드에서 뭐가 달라지냐면, `@Transactional` 을 어디에 붙일지가 "메서드 하나"가 아니라 "같이 성공해야 하는 범위"의 문제가 된다

---

## 트랜잭션의 네 가지 성질

이 성질들을 묶어서 ==ACID==라고 부른다

<br/>

**원자성 (Atomicity)**

하나의 트랜잭션 결과가 모두 성공하거나 모두 실패하는 성질

더 이상 쪼갤 수 없다는 뜻에서 원자다

<br/>

**일관성 (Consistency)**

트랜잭션 전후로 데이터베이스가 일관된 상태, 즉 무결성을 유지하는 성질

[[02. 왜 파일에 저장하면 안 될까?|파일에서 못 지키던 그 무결성]]이 여기서 보장된다

<br/>

**격리성 (Isolation)**

여러 트랜잭션이 서로 간섭하지 않도록 보장하는 성질

<br/>

**지속성 (Durability)**

성공한 트랜잭션의 결과가 영구적으로 반영되는 성질

<br/>

| 성질 | 한 줄로 |
|---|---|
| Atomicity | 다 되거나 다 안 되거나 |
| Consistency | 규칙은 언제나 지켜진다 |
| Isolation | 남의 작업이 안 보인다 |
| Durability | 성공했다고 했으면 안 사라진다 |

## 동시에 들어오면 어떻게 막나

격리성을 실제로 지키는 방법이 두 가지였다

<br/>

**락 매니저**

읽고-고치고-쓰는 동안 다른 요청이 들어오면 기다리게 한다

```
[트랜잭션 A]              [트랜잭션 B]
락 획득
조회수 읽음 (1)
                          락 대기 ......
2 로 씀
락 반납
                          락 획득
                          조회수 읽음 (2)
                          3 으로 씀
```

<br/>

**MVCC (Multi-Version Concurrency Control)**

기다리게 하는 대신 ==버전을 분리한다==

읽으려는 쪽에는 고치기 전의 버전을 그대로 보여준다

<br/>

✨ **읽기가 쓰기를 막지 않는다**

조회 하나 때문에 수정이 줄 서서 기다리는 상황이 없어진다

MySQL이 조회가 많은 서비스에서 버티는 이유가 여기 있었다

## 커밋 전에 죽으면?

지속성을 지키는 장치가 ==WAL (Write Ahead Log)==이다

이름 그대로 미리 쓰는 로그다

```
"이거 바꿀 거다" 를 로그에 먼저 적는다
      ↓
실제 데이터를 고친다
      ↓ ✗ 여기서 죽어도
로그가 남아 있으니 재생하거나 롤백할 수 있다
```

<br/>

⚠️ **디스크에 두 번 쓰는 셈인데 왜 이게 빠른가**

실제 데이터는 여기저기 흩어진 위치에 써야 하고, 로그는 뒤에 이어 붙이기만 하면 된다

디스크는 흩어진 곳을 찾아다니는 것보다 한 줄로 이어 쓰는 걸 훨씬 잘한다

<br/>

이건 저장장치 쪽 이야기라 여기서는 이 정도로 남겨둔다

## 표로 저장하고 키로 잇는다

## R이 뭔데?

우리가 쓰는 MySQL은 정확히는 RDBMS다

> ==RDBMS (Relational DBMS)== : 데이터를 행과 열로 구성된 테이블 형태로 묶고, 테이블 간의 관계를 키로 연결해서 관리하는 DBMS

<br/>

관계는 세 종류다

```
1:1    유저 - 유저상세정보
1:N    유저 - 게시글          (유저 한 명이 글 여러 개)
N:N    게시글 - 태그          (글도 여러 개, 태그도 여러 개)
```

<br/>

그리고 이 관계를 실제로 잇는 물건이 키다

---

## 키가 제일 중요하다

내 생각엔 이게 제일 중요하다

조회랑 직관적으로 연결되기 때문이다

```
post 테이블                    user 테이블

post_id  title   user_id       user_id  name
   1     제목1      7    ───>      7     코로구
   2     제목2      7    ───>
                    └─ 이 값 하나로 두 표가 이어진다
```

<br/>

표를 나눠 놓고도 하나처럼 쓸 수 있는 이유가 이 연결이다

## 키 여섯 개

이름이 비슷해서 계속 헷갈렸는데, 두 가지 성질로 갈린다

> ==유일성== : 그 값으로 레코드 하나가 특정된다
>
> ==최소성== : 하나라도 빼면 유일성이 깨진다

<br/>

| 키 | 뭐냐면 |
|---|---|
| 후보 키 | 한 레코드를 식별하기 위한 최소 집합 (==유일성 + 최소성==) |
| 복합 키 | 두 필드 이상으로 구성된 후보 키 |
| 슈퍼 키 | 후보 키에서 최소성을 없앤 키 |
| 기본 키 (PK) | 한 레코드를 식별하도록 선정된 키, 테이블당 하나 |
| 외래 키 (FK) | 다른 테이블의 PK |
| 대체 키 | PK가 아닌 후보 키 |

<br/>

`(학번)` 만으로 학생이 특정되면 후보 키다

여기에 `(학번, 이름)` 처럼 필요 없는 걸 붙이면 유일성은 남지만 최소성이 깨져서 슈퍼 키가 된다

<br/>

후보 키가 여러 개일 때 그중 하나를 골라 PK로 삼고, 안 뽑힌 나머지가 대체 키다

<br/>

inner        양쪽에 다 있는 것만

right outer  오른쪽은 다 살리고, 왼쪽은 있으면 붙인다

post          user           inner join 결과

## 표를 안 쓰는 DB도 있다

## Not Only SQL

NoSQL이라고 하면 SQL을 안 쓴다는 뜻인 줄 알았다

원래는 맞는 말이었다

<br/>

처음엔 키-값 저장소에 전용 API로 데이터를 다뤘으니 SQL이 낄 자리가 없었다

그런데 쓰다 보니 조인이 필요하고, 집계가 필요하고, 서브쿼리가 필요해졌다

<br/>

✨ **그래서 이름의 뜻이 바뀌었다**

```
No SQL          ->    Not Only SQL
SQL 안 쓴다            SQL만 쓰는 건 아니다
```

점점 SQL과 비슷한 쿼리 기능을 갖추기 시작했다

---

## RDBMS랑 뭐가 다른가

두 가지가 갈린다

<br/>

**스키마**

> ==스키마== : 컬럼과 타입 등의 정의

```
RDBMS   스키마가 있다
        name 은 문자열, age 는 숫자라고 미리 정해두고
        어기면 못 넣는다

NoSQL   스키마가 유연하거나 아예 없다
        어떤 레코드엔 age 가 있고 어떤 레코드엔 없어도 된다
```

<br/>

**같이 볼 데이터를 어떻게 두느냐**

```
RDBMS   나눠서 저장하고, 볼 때 조인해서 합친다

NoSQL   같이 조회할 것들을 아예 한 덩어리로 저장해버린다
        -> 합칠 필요가 없으니 꺼낼 때 빠르다
```

<br/>

그래서 내 코드에서 뭐가 달라지냐면, "NoSQL은 조회가 빠르다"가 마법이 아니라 ==미리 합쳐뒀기 때문==이라는 게 된다

대신 그 덩어리에 같은 데이터가 여기저기 복사돼 들어간다

## 핵심 흐름

```
[왜 파일이 아니라 DB인가]
파일 시스템도 트리 구조에 보조기억장치를 쓴다

   B+Tree        범위 검색과 정렬된 조회용 트리
   락 / MVCC     기다리게 하거나 버전을 나눈다
   WAL           바꾸기 전에 미리 적어둔다

[DB 랑 대화하는 법]
DBMS 도 하나의 프로세스다
   ↓ IP 로 호스트를 찾고

   -> 내 서버는 DBMS 의 클라이언트다

[트랜잭션]
논리적 상호작용의 단위 = 같이 성공하거나 같이 실패해야 하는 덩어리
A  다 되거나 다 안 되거나
C  규칙은 언제나 지켜진다

D  성공했으면 안 사라진다      <- WAL

[표로 저장한다는 것]
관계 1:1 / 1:N / N:N 를 키로 잇는다
후보 키 = 유일성 + 최소성
   최소성을 빼면 슈퍼 키
   두 필드 이상이면 복합 키
   후보 키 중 하나를 뽑으면 PK, 안 뽑히면 대체 키
   다른 표의 PK 를 가져오면 FK

[빠르게 꺼내는 법]
서브쿼리   depth 깊어지면 읽기도 실행도 부담
조인       inner / left outer / right outer / full outer
뷰         조회 목적, 권한 분리에 쓸 수 있다
인덱스     clustered   리프에 실제 모든 컬럼
           secondary   리프에 PK 값 -> 한 번 더 찾아 들어간다

[NoSQL]
Not Only SQL, 원래는 진짜로 SQL 을 안 썼다
스키마가 유연하고, 같이 볼 것을 한 덩어리로 저장한다
   -> "조회가 빠르다" 는 미리 합쳐뒀다는 뜻이다
RDBMS  무결성 일관성 > 성능 유연성
NoSQL  성능 유연성 > 트랜잭션 ACID
```

---

> ==DB 의 기능은 전부 "파일로는 안 되는 것"의 목록이었다==
> 무결성도, 트랜잭션도, 인덱스도, 각각 따로 외울 개념이 아니라 파일 하나에서 출발한 답이었다

<br/>

✨ **모호하게 말하던 세 문장에 이유가 생겼다**

"어디서 조회하든 데이터가 서로 같아야 해서" -> 파일은 규칙을 걸어둘 자리가 없고, 검사하는 코드가 여러 벌이 된다

"조회를 빨리하려고 조인을~ 인덱스를~" -> 나눠서 저장했으니 합칠 방법이 필요하고, 처음부터 끝까지 읽지 않으려면 색인이 필요하다

"NoSQL은 조회가 빨라서" -> 빠른 게 아니라 미리 합쳐둔 거다, 대신 같은 데이터가 여기저기 복사된다

<br/>

✨ **DB가 특별한 물건이 아니라는 게 제일 컸다**

그냥 켜져 있는 프로세스 하나고, TCP로 연결해서 바이트를 주고받는다

이걸 알고 나니 "DB가 느리다"를 쿼리가 느린 건지, 커넥션을 기다리는 건지, 네트워크를 건너느라 느린 건지로 나눠서 볼 수 있게 됐다

<br/>

⚠️ **그래도 아직 고를 줄은 모른다**

RDBMS와 NoSQL 중에 뭘 쓸지는 성질로는 설명이 되는데, 실제 프로젝트에서 "이 데이터는 어느 쪽" 을 자신 있게 못 정하겠다

이건 개념이 아니라 겪어봐야 하는 영역인 것 같다

---

❓ 실전 체크리스트

- 조회수 같은 카운터가 어긋난다 -> 읽고-고치고-쓰는 사이에 끼어든 요청이 있는지 본다, `synchronized` 는 서버가 두 대면 소용없다
- 유령 데이터가 남는다 -> FK 없이 애플리케이션 코드로만 관계를 맞추고 있는 건 아닌지 본다
- 일부만 반영된 상태가 남았다 -> 같이 성공해야 할 범위가 한 트랜잭션 안에 있는지 본다
- DB 가 느리다 -> 쿼리 / 커넥션 대기 / 네트워크 중 어디인지부터 나눈다
- 세컨더리 인덱스를 걸었는데 기대만큼 안 빠르다 -> 리프에 PK 만 있어서 한 번 더 찾아 들어간다는 걸 떠올린다
- 캐시를 NoSQL 로 뺀다 -> 원본은 어디에 있는지, 날아가도 되는 데이터인지 먼저 정한다

---

❓ 아직 안 풀린 것

- **B+Tree 의 실제 모양** - 범위 검색을 위해 설계된 트리라는 것까지만 봤다, 내부 노드와 리프 노드가 왜 그렇게 나뉘는지는 아직 안 봤다
- **트리도 그래프의 일종 아닌가** - MySQL 도 B+Tree 를 쓰는데 Graph DB 를 따로 두는 이유가 뭔지 아직 안 잡힌다
- **격리성의 단계** - "남의 작업이 안 보인다" 가 전부 아니면 전무가 아니라 수준이 나뉜다고 들었는데 거기까지는 안 갔다
- **WAL 이 실제로 얼마나 이득인가** - 이어 쓰기가 빠르다는 것까지는 알겠는데 숫자로는 본 적이 없다
