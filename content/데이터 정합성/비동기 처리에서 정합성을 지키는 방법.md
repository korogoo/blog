## ThreadLocal은 어떻게 스레드마다 다른 값을 주나?

`ThreadLocal` 객체(예: `resources`) 자체는 앱 전체에 딱 하나 공유된다
근데 그 객체는 데이터를 자기 안에 저장하지 않는다

실제 저장소는 `Thread` 객체 안의 `threadLocals` 필드다
그래서 `get()`을 호출하면 이렇게 동작한다

```java
public T get() {
    return get(Thread.currentThread());   // 항상 "지금 실행 중인 스레드"로 라우팅됨
}
```

호출하는 스레드가 누구냐에 따라 서로 다른(물리적으로 별개인) 저장소를 보게 된다
공유되는 건 "열쇠(객체)"뿐이고, 그 열쇠가 여는 "저장소"는 스레드마다 완전히 분리돼 있다

<br/>

### 💬 2단계 맵 구조?

```
Thread 객체
 └─ threadLocals (JDK 내부 필드)
      key = resources(ThreadLocal 인스턴스) → value = Spring이 만든 HashMap  (1단계)
                                                    └─ key = EntityManagerFactory → value = EntityManagerHolder  (2단계)
```

1단계는 JDK가 관리 (이 스레드가 쓰는 모든 ThreadLocal 변수를 담음: 트랜잭션, MDC, 보안 컨텍스트 등)
2단계는 Spring이 `bindResource()`에서 직접 만든 Map (실제 리소스 매핑)

<br/>

## 왜 @Async는 트랜잭션을 이어받지 못하나?

트랜잭션을 시작하면(`JpaTransactionManager.doBegin()`) 마지막에 이 한 줄이 실행된다

```java
if (txObject.isNewEntityManagerHolder()) {
    TransactionSynchronizationManager.bindResource(emf, txObject.getEntityManagerHolder());
}
```

이 바인딩은 "지금 이 코드를 실행 중인 스레드"에게만 이루어진다
`@Async`로 새 스레드(풀에서 꺼낸 스레드)가 실행을 이어받으면, 그 스레드는 완전히 비어있는 자기만의 `threadLocals`를 갖고 시작한다
그래서 호출자 스레드가 바인딩해둔 `EntityManagerHolder`(= 영속성 컨텍스트)를 볼 방법이 없다
`@Transactional`이 붙어 있어도 "이어받는" 게 아니라 "새로 시작"하는 것처럼 동작한다

<br/>

## 왜 커밋 전 데이터를 못 보나?

ThreadLocal 분리만으로는 "왜 새 트랜잭션이 열리는지"까지만 설명된다
"그 새 트랜잭션이 왜 데이터를 못 보는지"는 DB 격리성(Isolation) 때문이다

Thread-2가 새로 연 트랜잭션도 결국 트랜잭션이라, DB의 일반 규칙을 따른다
커밋 안 된 변경사항은 다른 트랜잭션에게 안 보인다 (dirty read 방지)

```
ThreadLocal 분리 → Thread-2가 독립된 새 트랜잭션을 열 수밖에 없음
        +
DB 격리성 → 새 트랜잭션은 다른 트랜잭션의 미커밋 데이터를 볼 수 없음
        =
"커밋 전 데이터를 못 본다"
```

<br/>

### 💬 실제 실패 타임라인

```java
@Transactional
public void placeOrder(OrderCommand cmd) {
    Order order = orderRepository.save(new Order(cmd));   // 미커밋 INSERT
    notificationService.sendAsync(order.getId());          // @Async 호출, 기다리지 않음
}                                                            // 메서드 종료 시점에 커밋

@Async
public void sendAsync(Long orderId) {
    Order order = orderRepository.findById(orderId)         // 새 스레드, 새 트랜잭션
        .orElseThrow();                                       // 미커밋이라 못 찾음 -> 예외
}
```

Thread-1이 커밋하기 전에 Thread-2가 이미 실패해버린다

## AOP 프록시 - 왜, 어떻게

AOP = Aspect-Oriented Programming (관점 지향 프로그래밍)

**왜**: 트랜잭션 관리, 비동기 처리 같은 공통 로직(횡단 관심사)이 비즈니스 로직과 뒤섞이는(tangling) 것과, 그게 모든 메서드마다 중복되는(scattering) 것을 막기 위해

**어떻게**: 원본 메서드를 직접 호출하는 대신, 그 앞을 가로막는 대리인(프록시)을 세운다

```
JDK 동적 프록시 - 인터페이스를 구현한 프록시 (런타임 생성)
CGLIB 프록시   - 클래스를 상속한 프록시 (Spring Boot 기본값)
```

Spring이 빈을 등록할 때, `@Async`/`@Transactional`이 붙은 빈은 원본 대신 프록시를 컨테이너에 넣는다
그래서 주입받는 건 항상 프록시다

<br/>

### 💬 self-invocation 함정?

```java
@Service
public class OrderService {
    public void placeOrder(OrderCommand cmd) {
        this.sendAsync(order.getId());   // 같은 클래스 안에서 직접 호출
    }

    @Async
    public void sendAsync(Long orderId) { ... }
}
```

`this.sendAsync()`는 프록시를 안 거치고 원본 객체가 자기 자신을 직접 호출하는 거라 `@Async`가 동작 안 한다
그래서 `@Async` 메서드는 보통 별도 클래스(별도 빈)로 분리한다

<br/>

## Aspect가 정확히 뭔가

- Concern(관심사): 프로그램이 처리해야 할 기능 하나
- 핵심 관심사: 그 모듈이 존재하는 본질적 이유 (예: "주문 저장")
- 횡단 관심사(cross-cutting concern): 트랜잭션/로깅/보안처럼 여러 모듈에 공통으로 걸쳐있는 관심사
- **Aspect**: 관심사 자체를 뜻하는 말이 아니라, 횡단 관심사 하나를 뽑아내서 만든 독립된 모듈 그 자체

왜 "aspect(측면)"라는 이름인가 - OOP는 클래스 계층이라는 한 축으로만 시스템을 나누는데, 횡단 관심사는 그 축을 안 따라간다
AOP는 "이 시스템을 바라보는 또 다른 축(측면)이 있다"고 보고, 그 축으로도 모듈화할 방법을 준 것이다

<br/>

### 💬 tangling / scattering 어원?

- **tangling(엉킴)**: 한 모듈 "안에서" 여러 관심사의 코드가 뒤섞여 구분이 안 되는 상태 (실이 엉키는 것에서 비유)
- **scattering(흩어짐)**: 하나의 관심사를 구현하는 코드가 여러 모듈에 걸쳐 중복되어 흩어져 있는 상태

```java
public void save(Order order) {
    Connection conn = ...;
    conn.setAutoCommit(false);       // tangling: 핵심 로직과 트랜잭션 로직이 한 메서드 안에서 섞임
    try {
        repository.save(order);
        conn.commit();
    } catch (Exception e) { ... }
}

public void updateStock(...) {
    Connection conn = ...;            // scattering: 위와 같은 코드가 여기 또 중복
    conn.setAutoCommit(false);
    ...
}
```

<br/>

## 왜 그냥 객체(TransactionManager)로 뽑아내면 안 되나

객체로 뽑아내면 "구현 로직"의 중복(scattering)은 해결된다
근데 두 가지가 안 풀린다

1. tangling이 그대로 남음 - `begin()/commit()/rollback()` 호출이 여전히 메서드 안에 있음
2. 호출 자체의 scattering이 그대로 남음 - 트랜잭션 필요한 모든 메서드마다 저 패턴을 직접 써야 함

```java
// Template Method 방식 (순수 OOP로 할 수 있는 최선)
public void save(Order order) {
    transactionTemplate.execute(status -> {
        repository.save(order);   // 여전히 이 호출 하나는 남음
        return null;
    });
}

// AOP 방식
@Transactional
public void save(Order order) {
    repository.save(order);   // 트랜잭션 관련 코드가 하나도 없음
}
```

AOP는 **obliviousness(모른 채로 있음)**라는 성질을 준다 - 대상 코드가 자기가 부가 로직의 적용을 받는지조차 모른 채로 존재할 수 있다
순수 OOP(객체 합성/상속/Template Method)로는 이 성질을 만들 수 없다 - 누군가는 반드시 "나 지금 이거 쓴다"를 코드에 명시해야 하기 때문이다

<br/>

## 컨테이너가 뭔가

Spring의 IoC 컨테이너(`ApplicationContext`)는 "필요한 객체(빈)들을 만들어서 보관하고, 서로 연결해주고, 필요할 때 꺼내주는 저장소"다
내부적으로는 `Map<String, Object>` 구조다 (bean 이름 -> 인스턴스)

<br/>

### 💬 BeanPostProcessor가 뭔가?

빈이 완성되는 시점에 끼어들어서 최종 결과물을 바꿔치기할 수 있는 훅이다

```java
public interface BeanPostProcessor {
    default Object postProcessAfterInitialization(Object bean, String beanName) { return bean; }
}
```

리턴값이 곧 "이 빈의 최종 정체"가 된다 (원본을 그대로 리턴할 수도, 다른 객체로 바꿔서 리턴할 수도 있음)
`AbstractAutoProxyCreator`가 이 훅을 이용해서, 빈의 메서드 중 등록된 Advisor의 Pointcut과 매치되는 게 있으면 원본 대신 프록시를 리턴한다

<br/>

## 프록시가 만들어지고 등록되는 전체 흐름

```
① Spring이 원본 인스턴스 생성 (생성자 + 의존성 주입)
② BeanPostProcessor(AbstractAutoProxyCreator)가 검사
   -> 메서드 중에 @Async, @Transactional 등 Advisor와 매치되는 게 있나?
③ 있으면 프록시 생성
   - 인터페이스 없음 -> 무조건 CGLIB (클래스 상속)
   - 인터페이스 있음 -> proxyTargetClass 설정값에 따라 CGLIB or JDK 동적 프록시
     (Spring Boot 기본값은 true라서 사실상 거의 항상 CGLIB)
④ 컨테이너는 원본이 아니라 프록시를 저장소에 등록
   (컨테이너 Map -> 프록시 -> target 필드로 원본 참조, 2단계 경로)
```

**Advisor** = Pointcut(어떤 메서드에 적용할지 규칙) + Advice(실제 부가 로직 코드)를 묶은 것
`@Async`, `@Transactional` 자체는 Advisor가 아니라, 내장 Advisor의 Pointcut이 찾는 마커일 뿐이다

CGLIB 풀네임 = **Code Generation Library** (바이트코드 직접 조작해서 런타임에 클래스 생성)

<br/>

### 💬 인터셉터 체인이 뭔가?

이 메서드 호출에 적용되는 Advice(인터셉터)들의 순서 있는 리스트다

예: `TransactionInterceptor`(`@Transactional`), `AnnotationAsyncExecutionInterceptor`(`@Async`), `CacheInterceptor`(`@Cacheable`), 커스텀 `@Aspect`

```java
public Object proceed() {
    if (체인에 인터셉터가 더 있으면) {
        다음 인터셉터.invoke(this);   // 이 안에서 또 proceed() 호출
    } else {
        method.invoke(target, args);   // 재귀의 종료 조건 -> 원본이 항상 맨 마지막에 실행됨
    }
}
```

체인(리스트)은 캐싱되어 재사용되지만, `MethodInvocation`(체인을 타고 내려가는 진행 상태를 담은 객체)은 매 호출마다 새로 생성된다 (동시 호출 시 진행 상태가 섞이면 안 되므로)

<br/>

## 프록시 동작 원리 - 일반 Advice vs @Async

```java
// 일반 Advice (예: TransactionInterceptor) - 같은 스레드에서 그대로 진행
public Object invoke(MethodInvocation invocation) {
    beginTransaction();
    Object result = invocation.proceed();   // 바로, 같은 스레드에서 원본 실행
    commitTransaction();
    return result;
}

// @Async (AsyncExecutionInterceptor) - proceed() 자체를 다른 스레드로 떠넘김
public Object invoke(MethodInvocation invocation) {
    Callable<Object> task = () -> invocation.proceed();   // 포장만 하고 지금 실행 안 함
    return doSubmit(task, executor, returnType);           // 스레드풀에 제출
}
```

다른 인터셉터는 `proceed()`를 그 자리에서 직접 호출하는데, `AsyncExecutionInterceptor`만 `proceed()` 호출 자체를 Callable로 포장해서 다른 스레드가 나중에 실행하도록 미룬다
이게 `@Async`가 유일하게 "실행 스레드를 바꾸는" 이유고, 오늘 다룬 ThreadLocal 끊김 문제의 근본 원인이다

<br/>

## @Async 실행 원리 - 어떤 조각들로 이루어져 있나

```java
public interface Runnable { void run(); }                 // 리턴값 없음, 실행할 작업을 담는 캡슐
public interface Callable<V> { V call() throws Exception; } // 리턴값 있음

public interface Executor { void execute(Runnable command); }         // 즉시 리턴, 결과 추적 불가
public interface ExecutorService extends Executor {
    <T> Future<T> submit(Callable<T> task);                            // Future를 즉시 리턴
}

public interface Future<V> { V get(); }   // 미래에 결과가 채워질 그릇
```

프록시가 실제 로직을 Callable로 포장해서 이미 만들어진 ThreadPool(Executor)에 제출한다
매번 `new Thread()`를 만드는 게 아니라, 풀 안의 워커 스레드 중 하나가 꺼내서 실행한다

리턴 타입에 따라 분기:
- `void` -> `execute()`처럼 즉시 null 리턴, fire-and-forget (예외는 `AsyncUncaughtExceptionHandler`가 로그만 남김)
- `Future`/`CompletableFuture` -> `submit()`처럼 Future 객체를 즉시 리턴, 나중에 `.get()`이나 콜백으로 결과 확인

`AsyncUncaughtExceptionHandler`로 예외 처리 창구는 통일되지만, "그 창구에서 뭘 할지(로깅만? 재시도? 알림?)"는 여전히 직접 정책을 정해야 한다

<br/>

## 동기/비동기, 블로킹/논블로킹은 다른 축이다

- 블로킹/논블로킹 = 이 호출 하나가 지금 이 순간 나를 멈추게 하는가
- 동기/비동기 = 완료 여부를 확인하고 처리하는 책임이 계속 나한테 있는가, 남에게 넘어갔는가

```java
// 동기 + 블로킹 - 응답 올 때까지 멈춤, 내가 직접 처리
String result = restTemplate.getForObject(url, String.class);

// 동기 + 논블로킹 - 안 멈추지만, 내가 스스로 반복 확인(폴링)해야 함
while (true) {
    int n = channel.read(buffer);
    if (n > 0) break;
}

// 비동기 + 블로킹 - 위임(안 멈춤)과 결과 요청(멈춤)이 시간차를 둔 별개의 순간
Future<Order> future = executor.submit(task);   // 순간 1: 비동기, 안 멈춤
Order order = future.get();                      // 순간 2: 블로킹, 멈춤

// 비동기 + 논블로킹 - 위임하고 완전히 손 뗌, 완료는 콜백이 알아서
### notificationService.sendAsync(orderId);
```

`@Async`는 "비동기 + 논블로킹"에 해당한다

<br/>

### 💬 @Async로 외부 API를 부르면 블로킹이 사라지나?

아니다 `@Async`는 블로킹을 없애는 게 아니라 다른 스레드로 떠넘길 뿐이다

```java
@Async
public void callExternalApi() {
    String result = restTemplate.getForObject(url, String.class);  // 워커 스레드는 여전히 블로킹+동기
    process(result);
}
```

메인 스레드 입장에서는 논블로킹+비동기처럼 보이지만, 실제로 일하는 워커 스레드는 응답 올 때까지 멈춰있다
그래서 외부 API 응답이 느려지면 워커 스레드가 계속 쌓여서 풀이 바닥날 수 있다 (-> ThreadPool 사이즈 공식으로 이어짐)

진짜로 블로킹 자체를 없애려면 `WebClient` 같은 리액티브/논블로킹 HTTP 클라이언트가 필요하다

<br/>

## ThreadPool - 왜 미리 만들어두나

스레드 생성은 비싸다 (OS 스택 메모리 할당 + 커널 시스템콜)
매번 새로 만들고 죽이는 대신, 미리 만들어서 재사용한다

```
while (true) {
    task = 큐에서 작업 하나 꺼냄 (없으면 대기)
    task 실행
    // 안 죽고 다시 대기
}
```

<br/>

### 💬 ThreadPoolExecutor 동작 순서?

```
요청 들어옴
  -> ① core 스레드에 여유 있나 -> 있으면 새 스레드 생성해서 실행
  -> ② (없으면) 큐에 자리 있나 -> 있으면 큐에 쌓음
  -> ③ (큐도 꽉 찼으면) max까지 늘릴 수 있나 -> 그제서야 추가 스레드 생성
  -> ④ (max도 다 찼으면) RejectedExecutionHandler 실행
```

함정: 무제한 큐를 쓰면 큐가 절대 안 차니까 ③이 발동을 안 해서 max 설정이 죽은 설정이 된다

<br/>

## CPU-bound vs I/O-bound 사이즈 공식

```
스레드 수 = CPU 코어 수 × (1 + 대기시간 / 계산시간)
```

- **CPU bound** (연산 위주, 대기시간 ≈ 0): 스레드 수 ≈ 코어 수 (+1)
- **I/O bound** (외부 API, DB 응답 대기 위주): 코어 수보다 훨씬 많이

⚠️ **주의**: `(1 + 대기시간/계산시간)`은 "코어 1개당 필요한 스레드 수"일 뿐이다 (중간값)
여기에 실제 코어 개수를 곱한 최종 결과가 `corePoolSize`로 써야 할 값이다 (core/max로 나뉘는 게 아님)

```
예시: 코어 4개, 계산 50ms + 응답대기 450ms
  1 + 450/50 = 10  (코어 1개당 필요한 스레드 수, 중간값일 뿐)
  4 × 10 = 40       (실제 corePoolSize로 쓸 값)
```

`maxPoolSize`는 이 공식과 별개의 결정이다 - "평소 예상 부하(공식 결과)를 넘는 반짝 몰림을 얼마나 더 흡수할지"를 트래픽 패턴 보고 별도로 정함 (보통 core보다 1.5~2배 정도)

<br/>

## 큐가 필요한 이유, 사이즈 정하는 법

큐 = "잠깐의 부하 폭증을 스레드 추가 생성 없이 버텨주는 완충 장치"
무제한 큐는 OOM 위험 + max 무의미화로 이어져서, 유한 크기로 제한한다 (배압/backpressure)

⚠️ **실제 함정**: Spring `ThreadPoolTaskExecutor`는 `queueCapacity`를 명시 안 하면 기본값이 `Integer.MAX_VALUE`다
21억이면 사실상 무제한 큐라서, `maxPoolSize`를 아무리 설정해도 죽은 설정이 되고 OOM으로 터질 수 있다 - 반드시 직접 지정해야 함

**사이즈 공식 (Little's Law)**

```
큐 사이즈 ≈ 처리량(초당 처리 가능한 작업 수) × 허용 가능한 최대 대기 시간(초)
```

`허용 가능한 최대 대기 시간`은 공식으로 안 나온다 - "이 작업이 늦어져도 되는 한계"를 먼저 정책으로 정해야 하는 값

```
예시 (위 40스레드 이어서):
  스레드 1개가 작업 1개 처리하는 데 500ms(50+450) 걸림 -> 초당 2개 처리 가능
  40개 스레드 -> 처리량 = 40 × 2 = 80개/초
  허용 대기시간 3초로 정했다면 -> 큐 사이즈 = 80 × 3 = 240
```

너무 작으면 스레드가 자주 생성돼서 재사용 이점이 줄고, 너무 크면 뒤에 쌓인 작업이 오래 기다리다 처리될 때쯤 이미 의미 없어지기도 한다

<br/>

## Executor 선택 체크리스트

1. CPU bound냐 I/O bound냐 먼저 판단 -> 공식으로 스레드 수 가늠
2. 큐 종류 결정: `SynchronousQueue`(즉시 전달, max 필수) / `LinkedBlockingQueue`(무제한, 위험) / `ArrayBlockingQueue`(유한, 실무 표준)
3. 거부 정책 결정: `AbortPolicy`(예외) / `CallerRunsPolicy`(호출자가 대신 실행) / `DiscardPolicy`(버림)
4. 용도별로 풀 분리 - CPU bound와 I/O bound를 같은 풀에 두면 서로 굶주릴 수 있음(starvation)

```java
@Bean(name = "notificationExecutor")   // I/O bound (외부 API/알림 발송)
public Executor notificationExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(40);        // 코어수 × (1 + 대기/계산) 공식 결과
    executor.setMaxPoolSize(60);         // core 대비 별도 여유분 (버스트 대비)
    executor.setQueueCapacity(240);      // 처리량 × 허용대기시간 (Little's Law)
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}
```

<br/>

### 💬 @Async가 Executor를 고르는 지점?

인터셉터 체인 중 `determineAsyncExecutor(method)`가 담당한다
`@Async("빈이름")` 지정 -> 그 빈 / 없으면 기본 설정 executor / 그것도 없으면 Spring 기본값

⚠️ **함정**: 아무 Executor도 직접 등록 안 하면 기본값은 `SimpleAsyncTaskExecutor`인데, 이건 풀링을 아예 안 하고 매번 `new Thread()`를 만든다
그래서 실무에서는 반드시 `ThreadPoolTaskExecutor`를 직접 빈으로 등록해야 한다

<br/>

## 비동기 처리에서 트랜잭션 경계가 어떻게 달라지는가 (종합)

**한 줄 요약**: 트랜잭션 경계는 스레드에 묶여있는데, 비동기는 실행을 다른 스레드로 옮기기 때문에, 원래 하나였던 트랜잭션 경계가 "호출자 스레드의 트랜잭션"과 "워커 스레드의 트랜잭션(또는 트랜잭션 없음)"으로 쪼개진다

동기일 때: 메서드 호출 경계 = 트랜잭션 경계 (한 스레드, 한 트랜잭션, 같이 성공/롤백)
비동기가 끼면: 실행 스레드가 바뀌면서 트랜잭션 경계도 함께 끊김

이 경계 분리가 만드는 문제 두 가지:
1. **순서 문제** - 워커 스레드가 호출자보다 먼저 실행되면 아직 커밋 안 된 데이터를 못 봄 (DB 격리성)
2. **롤백 전파 문제** - 두 트랜잭션이 완전히 독립적이라, 한쪽이 실패해도 다른 쪽엔 영향이 없음 (이미 커밋된 건 못 되돌림)

각각의 해결책이 아래 `AFTER_COMMIT`(순서 문제), 보상 트랜잭션(롤백 전파 문제)이다

<br/>

## 커밋 전 이벤트 발행 문제 해결 - `@TransactionalEventListener(AFTER_COMMIT)`

### 💬 Spring 이벤트 기본기 (오해 포인트)

`@EventListener`는 기본적으로 **완전히 동기적**이다 "이벤트"라는 이름 때문에 비동기라고 착각하기 쉬움
`publishEvent()` 호출 즉시, 같은 스레드에서 리스너가 바로 실행된다 (그냥 메서드 하나 더 부르는 것과 같음)

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(OrderPlacedEvent event) { ... }
```

`phase` 옵션: `BEFORE_COMMIT`, `AFTER_COMMIT`(기본값), `AFTER_ROLLBACK`, `AFTER_COMPLETION`

### 실제 동작 원리 - 오늘 배운 것과 같은 인프라

`publishEvent()`가 트랜잭션 안에서 호출되면, 즉시 실행 안 하고 콜백만 등록해둠

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    public void afterCommit() {
        handle(event);   // 커밋 성공 직후에만 실행됨
    }
});
```

`TransactionSynchronizationManager`엔 `resources`(Connection/EntityManagerHolder용) 말고 **`synchronizations`라는 또 다른 ThreadLocal 필드**가 있어서, "커밋 후 실행할 콜백 목록"을 스레드별로 저장해둠 - 완전히 같은 구조(ThreadLocal + 스레드별 리스트)를 재사용하는 것

### 코드 예시 - `@Async`랑 같이 써야 진짜 비동기

```java
@Transactional
public void placeOrder(OrderCommand cmd) {
    orderRepository.save(new Order(cmd));
    eventPublisher.publishEvent(new OrderPlacedEvent(order.getId()));   // 즉시 실행 안 됨, 콜백만 등록
}   // 여기서 진짜 커밋 -> 그 직후 콜백 실행됨

@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(OrderPlacedEvent event) {
    orderRepository.findById(event.getOrderId())...   // 이제 안전 - 이미 커밋된 뒤니까
}
```

⚠️ `@TransactionalEventListener` 혼자서는 스레드를 안 바꾼다 (여전히 커밋한 스레드에서 실행) - 별도 스레드에서 실행하려면 `@Async`를 같이 붙여야 함

### 💬 스레드는 정확히 언제 반납되나?

"커밋되자마자 자동 반납"이 아니라, Thread-1 자신이 "이 작업 Thread-2한테 넘긴다"는 제출 작업까지 마친 다음에 반납된다

```
Thread-1: commit 성공 -> triggerAfterCommit() -> handle() 호출 시도
    -> handle()에 @Async 있어서 프록시가 가로챔 -> executor.submit(task) -> 즉시 리턴
Thread-1: 이제 자유로워짐 -> 원래 있던 풀(예: 톰캣 요청 스레드풀)로 반납
Thread-2(워커): 나중에 큐에서 꺼내 진짜 handle() 로직 실행
```

### 💬 외부 API 연동도 AFTER_COMMIT으로 해결되나?

부분적으로만: "언제 부를지(순서)"는 해결되지만, 여전히 남는 문제:
1. 외부 API 호출 자체의 신뢰성(Timeout/Retry/CircuitBreaker) - 별개 문제, 그대로 필요
2. 로컬은 이미 커밋됐는데 외부 API가 실패하면? -> 롤백 불가 -> **보상 트랜잭션** 필요
3. `AFTER_COMMIT` 콜백 자체가 메모리에만 있어서, 커밋 후 콜백 실행 전에 서버가 죽으면 유실됨 -> **Outbox Pattern** 필요

<br/>

## 비동기 실패 시 보상 트랜잭션

**정의**: DB가 자동으로 되돌려주는 게 아니라, 이미 성공한 이전 단계의 효과를 지우기 위해 **별도의 새로운 작업**을 명시적으로 실행하는 것 (기술적 rollback이 아니라 의미적으로 반대 효과를 내는 새 트랜잭션)

```java
@Async
public void addPointAsync(Long orderId, Long userId) {
    try {
        pointService.addPoint(userId, amount);
    } catch (Exception e) {
        orderService.cancelOrder(orderId);   // ★ 보상 트랜잭션 - 완전히 새로운 별개 트랜잭션
    }
}
```

**실무에서는 계층적으로 쌓음**

```
1단계: 즉시 재시도 (일시적 장애 대응)
    -> 그래도 실패하면
2단계: 보상 트랜잭션 실행 (되돌리기/취소)
    -> 보상 트랜잭션 자체도 실패하면 (드묾)
3단계: Dead Letter Queue + 사람에게 알림
```

⚠️ 보상 트랜잭션도 **멱등성**이 있어야 함 (재시도 중 중복 실행될 수 있으므로)

### 💬 Saga Pattern?

"여러 로컬 트랜잭션을 연쇄로 묶고, 중간 실패 시 보상 트랜잭션으로 앞 단계들을 되돌리는" 방식의 정식 이름
분산된 여러 서비스에 걸친 작업을, 진짜 분산 트랜잭션 없이 일관성 있게 처리하는 표준 해법

<br/>

## Outbox Pattern

**해결하려는 문제 (Dual Write Problem)**: "비즈니스 데이터 저장"과 "이벤트 발행"이 서로 다른 두 시스템(DB, 메시지 브로커)에 걸쳐 있어서, 이 둘을 원자적으로 묶을 방법이 없음

**해법**: 이벤트를 메시지 브로커로 직접 보내는 대신, **같은 로컬 DB, 같은 트랜잭션 안**에 있는 Outbox 테이블에 기록. 그럼 DB의 ACID 보장이 그대로 적용돼서 둘 다 같이 커밋되거나 같이 롤백됨

```java
@Transactional
public void placeOrder(OrderCommand cmd) {
    Order order = orderRepository.save(new Order(cmd));                           // (1) 비즈니스 데이터
    outboxRepository.save(new OutboxEvent("OrderPlaced", order.getId(), payload)); // (2) 같은 트랜잭션!
}   // (1), (2) 하나의 커밋으로 원자적으로 묶임

@Scheduled(fixedDelay = 1000)   // 별도 릴레이 프로세스
public void relayOutboxEvents() {
    List<OutboxEvent> pending = outboxRepository.findUnpublished();
    for (OutboxEvent event : pending) {
        kafkaTemplate.send(event.getTopic(), event.getPayload());   // 실제 발행
        event.markPublished();
    }
}
```

**왜 안전한가 - 앞선 문제들을 흡수**

- 순서 문제 해결: 이벤트가 Outbox에 존재한다는 것 자체가 이미 로컬 트랜잭션이 커밋됐다는 뜻
- 유실 문제 해결: `AFTER_COMMIT` 콜백은 메모리뿐이라 유실 가능했는데, Outbox는 DB에 영속화되어 앱 재시작돼도 안전 (at-least-once 보장)

⚠️ 발행 과정에서 크래시 나면 같은 이벤트가 두 번 발행될 수 있음 -> 컨슈머도 여전히 **멱등성** 필요

### 💬 Outbox도 트랜잭션 커넥션을 오래 들고 있어야 하는 거 아닌가?

Outbox가 새로 만드는 요구사항이 아니라, **원래 `@Transactional`이 항상 이렇게 동작**함 - `outboxRepository.save()`도 그냥 평범한 JPA save라서, `resources.get()`으로 이미 (1)번에서 바인딩해둔 같은 커넥션을 그대로 씀

오히려 Outbox가 잘 설계된 이유: 트랜잭션 안엔 딱 두 개의 빠른 INSERT만 넣고, **진짜 느리고 불안정한 부분(Kafka 전송, 외부 API)은 트랜잭션 밖 별도 릴레이 프로세스로 빼놓음** -> 트랜잭션을 오히려 짧게 유지

### 💬 그럼 진짜 실행(컨슈머 처리)까지 원자적으로 묶이나?

아니다 - **발행까지만 원자적**이고, 그 이후(Kafka 전송, 컨슈머의 실제 처리)는 완전히 다른 프로세스/시스템이라 원자성 밖

```
비즈니스 데이터 변경 + "발행하겠다"는 기록   ← 여기까지만 원자적
                |  (여기서부터 원자성 밖)
                v
   Kafka 전송 -> 컨슈머 소비 -> 실제 비즈니스 효과
```

나머지는 이미 배운 도구들이 나눠서 감당: 컨슈머 실패 시 재시도 -> 그래도 안 되면 보상 트랜잭션, 중복 배달은 멱등성으로 방어. 완전한 분산 원자성(2PC)은 실무에서 어렵거나 불가능해서, 대신 각 구간을 로컬 트랜잭션으로 짧게 끊고 실패 구간만 재시도/보상으로 메꾸는 것 (Saga의 본질)

## 이벤트 기반(ApplicationEventPublisher) vs 메시지 큐(Kafka) 선택 기준

| 기준 | `ApplicationEventPublisher` (인프로세스) | Kafka (메시지 큐) |
|---|---|---|
| 소비자 위치 | 같은 프로세스 (같은 JVM) | 다른 서비스/프로세스 |
| 내구성 | 없음 - 앱이 죽으면 같이 사라짐 | 있음 - 디스크 영속, 리텐션 기간 재처리 가능 |
| 결합도 | 느슨하지만 여전히 같은 배포 단위 | 완전히 독립적 배포/스케일링 |
| 순서/재처리 | 기본 없음 | 파티션 단위 순서 보장 + 재처리 가능 |
| 운영 비용 | 거의 없음 | 브로커 클러스터 운영/모니터링 필요 |

**선택 질문들**

1. 소비자가 같은 프로세스 안인가, 다른 서비스인가? -> 다른 서비스면 메시지 큐 필수
2. 컨슈머가 지금 안 떠 있어도 나중에 놓친 이벤트를 따라잡아야 하나? -> 그래야 하면 Kafka
3. 컨슈머가 앞으로 늘어나거나 독립적으로 배포/스케일링돼야 하나? -> 그렇다면 Kafka
4. 지금 요구사항이 브로커 운영 비용을 정당화하나? -> 아니면 YAGNI, 인프로세스로 시작

Outbox 릴레이 프로세스가 "실제로 뭘 호출하느냐"가 이 선택의 실전 적용:
```java
eventPublisher.publishEvent(event);   // 인프로세스로 충분하면
kafkaTemplate.send(topic, event);      // 다른 서비스가 구독해야 하면
```

## 오늘 다 다졌다

- @Async 원리 (Spring AOP + ThreadPool)
- ThreadPool 사이즈 공식 (CPU/IO bound, Little's Law 큐 사이즈)
- 비동기 처리에서 트랜잭션 경계가 어떻게 달라지는지
- 커밋 전 이벤트 발행 문제 + `AFTER_COMMIT`
- 비동기 실패 시 보상 트랜잭션 (+ Saga Pattern)
- Outbox Pattern
- 이벤트 기반 vs 메시지 큐 선택 기준
