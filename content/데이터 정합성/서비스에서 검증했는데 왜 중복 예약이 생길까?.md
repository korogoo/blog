## 발단

이번 미션 요구사항에서 '같은 날짜, 같은 시간, 같은 테마로는 예약할 수 없다' 가 있었다

크루들과 이 예약 중복 방지를 어떻게 구현할까에 대해서 토론했다

<br/>

나는 당연히 트랜잭션을 걸면 알아서 중복이 잘 처리될 것이라고 일차원적으로 생각했다

그런데 동키가 '다중 서버', '레이스 컨디션' 등등 처음 들어보는 단어와 함께 중복 방지가 완전 보장되지 않는다고 한다

트랜잭션을 걸었는데도 왜 중복 저장이 되는걸까? 궁금해졌다

---

### 전제 상황

(솔직히 지금 구현 중인 미션 수준에서는 대충대충 해도 사실상 문제가 되지 않는다)

충분한 고민을 위해서 아래처럼 극악의 상황을 가정하고 생각한다

- 티켓팅 수준의 고트래픽
- 단, DB는 단일 서버

---

### 무슨 일이 일어날 수 있을까?

서버 A와 B가 동시에 요청을 처리하는 상황을 가정한다

```
서버 A: SELECT → 없음 확인 → INSERT 준비
서버 B: SELECT → 없음 확인 → INSERT 준비
서버 A: INSERT 성공
서버 B: INSERT 성공 ← 중복 저장!
```

서비스 레이어에서 `existsBy`로 검증을 했는데도 둘 다 통과한다

---

### 왜 통과됐을까?

> 두 트랜잭션은 ==커밋 전 서로의 상태를 볼 수 없다==

기본 격리 수준인 `READ COMMITTED`에서는  
A가 INSERT를 커밋하기 전까지 B의 SELECT에 그 데이터가 보이지 않는다

B는 A가 이미 예약을 잡고 있다는 걸 모른 채 검증을 통과한다

---

---

## 어떻게 막을 수 있을까?

> 문제 상황을 하나씩 해결해가면서
> 
> ==각 계층이 무엇을 막고 무엇을 못 막는지== 이해하게 됐다

---

### 1단계 : ==트랜잭션==

기존에 구현되어 있던 방식이다

서비스 레이어에서 `existsBy`로 검증하고 INSERT한다


⚠️  **동시에 들어온 두 요청이 커밋 전 서로의 상태를 못 보기 때문에 예약 중복을 막지 못한다**

---

### 2단계 : 트랜잭션 + ==DB Unique 제약==

```sql
UNIQUE (res_date, time_id, theme_id)
```

서비스 검증을 동시에 통과해도, INSERT 시점에 하나는 Unique 위반으로 실패한다


⚠️ **DB 예외가 발생한다**

`DataIntegrityViolationException`이 올라오는데,

DB 예외라서 어떤 제약이 깨진 건지 파악하기 어렵고, 비즈니스 예외로 변환하는 처리가 복잡해진다

---

### 3단계 : 트랜잭션 + DB Unique + ==비관적 락==

```sql
SELECT ... FOR UPDATE
```

조회 시점부터 다른 트랜잭션을 블로킹한다

서비스 레이어 `existsBy` 단계에서 이미 대기 또는 예외가 발생하므로, 깨끗한 비즈니스 예외 처리가 가능하다

⚠️ **DB 성능이 급락한다**

락이 걸린 동안 다른 요청이 전부 대기한다

고트래픽 환경이라면 DB 성능이 중요하다

---

### 4단계 : 트랜잭션 + DB Unique + ==낙관적 락==

SELECT는 블로킹 없이 허용한다

실제 UPDATE 시점에 version 불일치로 충돌을 감지한다 (`ObjectOptimisticLockingFailureException`)

비관적 락보다 유연하고 성능이 좋다

충돌 시 재시도 또는 409 응답으로 처리한다

---

---

## 서버가 여러 대면 락도 여러 개일까?

낙관적 락이 단일 서버에서 동작한다는 건 알겠는데,

서버가 여러 대면 락도 서버마다 따로 생기는 게 아닐까 싶었다

---

### 락은 어디서 거는 걸까?

> ==락이 걸리는 위치는 DB에 있다==

```
서버 A ────┐
          ▼
서버 B ──► 단일 DB (락 매니저가 여기 있음)
```

서버가 몇 대든 모두 같은 DB 락 매니저에 요청한다

서버 대수는 변수가 아니다

---

### 그럼 언제 다중 서버가 문제가 되나?

락이 DB 바깥에 있을 때다

```java
synchronized (this) { ... }  // JVM 내 락
```

`synchronized`는 JVM 안에서만 유효하다

서버가 두 대면 각자 자기 JVM에서 락을 잡으므로 서로를 막지 못한다

이 경우엔 Redis 같은 분산 락이 필요하다

---

### 정리

| 락의 위치                  | 다중 서버에서 유효한가? |
| ---------------------- | ------------- |
| DB 락 (비관적 / 낙관적)       | O             |
| JVM 락 (`synchronized`) | X             |
| Redis 분산 락             | O             |

---

---

## INSERT에는 왜 낙관적 락이 안 될까?

낙관적 락을 설명할 때 다 UPDATE 만 설명하던데,,

낙관적 락으로 INSERT 중복은 못 막는 건가? 궁금했다

`@Version`을 엔티티에 달면 되는 거 아닌가?

---

### 낙관적 락의 원리

✨ **`@Version`은 UPDATE 시점에 충돌을 감지한다**

```sql
UPDATE reservation
SET version = 1
WHERE id = ? AND version = 0
```

> 내가 읽은 그 행이 그대로인지 ==원자적으로 확인==하는 것이다

version이 바뀌어 있으면 누군가 먼저 수정한 것이므로 충돌로 처리한다

---

### INSERT에 적용하면?

INSERT는 비교할 기존 행 자체가 없다

```
서버 A: INSERT → id=100, version=0 생성
서버 B: INSERT → id=101, version=0 생성  ← ⚠️ 다른 행이라 충돌 없음
```

두 서버가 각자 새 행을 만들었기 때문에 version 체크가 일어나지 않는다

---

### 정리

> `@Version`은 ==UPDATE 충돌 감지용==이다  
> 
> INSERT 중복 방지는 Unique 제약이 최후의 방어 방법이다

---

## 내 기준

### 결론 요약

| 방식       | 중복 방지 | 예외 처리 | 성능  | 다중 서버 |
| -------- | ----- | ----- | --- | ----- |
| 트랜잭션만    | X     | -     | O   | X     |
| + Unique | O     | 복잡    | O   | O     |
| + 비관적 락  | O     | 깔끔    | X   | O     |
| + 낙관적 락  | O     | 깔끔    | O   | O     |

---

### 실전 판단 흐름

```
동시성 문제가 발생했다
        │
        ▼
DB Unique 제약이 있는가?
        │
   ┌────┴──────────┐
  없음             있음
   │                │
   ▼                ▼
먼저 추가        예외 처리가 복잡한가?
                    │
               ┌────┴──────────┐
              아니오            예
               │                │
               ▼                ▼
          Unique만으로    낙관적 락 추가
          충분             (성능 유지)
```

---

### 실전 체크리스트

❓ **서비스 레이어 검증만 믿고 있지 않은가?**

READ COMMITTED 환경에서 동시 요청은 둘 다 통과한다

DB Unique 제약이 최후 방어선이다

<br/>

❓ **비관적 락을 선택하려 하는가?**

고트래픽 환경에서는 모든 요청이 직렬화된다

낙관적 락으로 충돌을 감지하고 409로 응답하는 방식이 더 적합하다

<br/>

❓ **서버가 여러 대라서 락이 의미 없다고 생각하는가?**

락이 DB 안에 있으면 서버 대수는 무관하다

`synchronized` 같은 JVM 락을 쓸 때만 다중 서버를 고려해야 한다

---

## 크루에게 받은 질문들

### 낙관적 락에 Unique까지 적용하는 이유?

> ==막는 시나리오가 달라서==

둘은 보호하는 대상이 다르다

<br/>

**낙관적 락이 막는 것**

같은 row를 두 트랜잭션이 동시에 수정하는 것

```
Thread A: reservation#1 읽음 (version=0)
Thread B: reservation#1 읽음 (version=0)
Thread A: UPDATE ... WHERE version=0 → 성공, version=1
Thread B: UPDATE ... WHERE version=0 → 0 rows → 충돌 감지
```

<br/>

**Unique 제약이 막는 것**

서로 다른 두 row가 같은 슬롯을 차지하려는 것

```
Thread A: exists(6/1, time1, theme1) → false
Thread B: exists(6/1, time1, theme1) → false
Thread A: INSERT (6/1, time1, theme1) → 성공
Thread B: INSERT (6/1, time1, theme1) → DB가 거절
```

<br/>

낙관적 락은 기존 row의 수정 충돌을 감지하고, Unique 제약은 새 row의 중복 생성을 막는다

보호하는 대상이 다르니 둘 다 필요하다

---

### 동시 수정 충돌 vs 중복 생성 — 본질이 다른가?

> ==패턴이 다르고 해결책도 다르다==

| | 중복 생성 | 동시 수정 충돌 (Lost Update) |
|---|---|---|
| 패턴 | check → (간격) → insert | read → (간격) → write |
| 대상 | 서로 다른 두 row | 같은 row |
| 충돌 결과 | 두 row가 같은 슬롯 차지 | 한 쪽 수정이 조용히 사라짐 |
| 해결책 | DB Unique 제약 | 낙관적 / 비관적 락 |

<br/>

비유하면 이렇다

**중복 생성**: 두 사람이 빈 자리에 동시에 앉으려는 것

**동시 수정 충돌**: 두 사람이 같은 자리에서 동시에 메모를 지우고 자기 글을 쓰는데, 한 쪽 글이 사라지는 것

---

### 격리 수준을 올려서 해결하면 어떤 문제가?

> 중복 생성을 막으려면 ==SERIALIZABLE까지 올려야== 한다

그러면 네 가지 문제가 생긴다

<br/>

⚠️ **성능 하락**

SERIALIZABLE에서는 SELECT에도 range lock이 걸린다

예약 조회 하나가 다른 트랜잭션의 INSERT를 블로킹하게 되어 처리량이 크게 감소한다

<br/>

⚠️ **데드락 위험 증가**

잠금을 더 넓은 범위에서 더 오래 보유하기 때문에 두 트랜잭션이 서로를 기다리는 상황이 생기기 쉽다

<br/>

⚠️ **범위가 너무 넓다**

날짜+시간+테마가 겹치는 예약 생성을 막겠다는 규칙 하나 때문에 전체 DB 트랜잭션을 직렬화하는 건 과한 해결책이다

Unique 제약은 딱 그 컬럼들만 잠근다
