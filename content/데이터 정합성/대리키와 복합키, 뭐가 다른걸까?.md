## 대리키(Surrogate Key)

> 대리키는 ==비즈니스와 무관하게 DB가 부여하는 식별자==다  
> 
> `AUTO_INCREMENT`, `SEQUENCE`, `UUID` 등이 여기에 해당한다

---

### 개념

```sql
CREATE TABLE game (
    id      BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 대리키
    name    VARCHAR(50) NOT NULL,
    status  VARCHAR(20) NOT NULL
);
```

`id`는 게임의 도메인적 의미가 없다

DB가 자동으로 부여하는 식별자다

---

### 장점

✨ **단순한 조인**

외래키로 참조할 때 숫자 하나(`game_id`)만 있으면 된다

<br/>

✨ **변경에 안전**

비즈니스 값(이름, 상태 등)이 바뀌어도 식별자가 바뀌지 않는다

복합키는 구성 컬럼이 바뀌면 FK를 참조하는 모든 곳도 바꿔야 한다

<br/>

✨ **단순한 인덱스**

숫자 단일 컬럼 인덱스는 복합 인덱스보다 빠르다

<br/>

✨ **ORM 친화적**

JPA 등 대부분의 ORM이 단일 대리키를 기본으로 설계되어 있다

---

### 단점

✨ **자연키와 분리되어 중복 위험**

`name` 같은 자연키가 유니크해야 한다면 별도 UNIQUE 제약이 필요하다

```sql
CREATE TABLE game (
    id    BIGINT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(50) NOT NULL UNIQUE,  -- 별도 유니크 제약 필요
    ...
);
```

<br/>

✨ **의미 없는 ID 노출**

API에서 `id=3`을 외부에 노출하면 순서 추측 등 보안 이슈가 생길 수 있다  

하지만, 이 경우 ==UUID 대리키==로 대응 가능하다


```sql
id UUID DEFAULT gen_random_uuid() PRIMARY KEY
```


순서를 예측할 수 없어 외부 노출에 유리하지만,

인덱스 성능이 낮고 저장 공간이 크다는 단점이 있다

## 복합키(Composite Key)

> 복합키는 ==두 개 이상의 컬럼을 조합해서 만드는 기본키==다  
> 
> 비즈니스 의미가 있는 컬럼들이 함께 식별자 역할을 한다

---

### 개념

```sql
CREATE TABLE game_piece (
    game_id   BIGINT NOT NULL,
    position  VARCHAR(10) NOT NULL,
    piece_type VARCHAR(20) NOT NULL,
    PRIMARY KEY (game_id, position)  -- 복합키
);
```

`game_id + position` 조합이 하나의 행을 유일하게 식별한다

---

### 장점

✨ **자연스러운 식별**

도메인에서 이미 의미 있는 컬럼들이 식별자가 된다

별도 대리키 없이도 자연스럽게 중복을 방지한다

<br/>

✨ **불필요한 컬럼 없음**

의미 없는 `id` 컬럼을 추가하지 않아도 된다

---

### 단점

✨ **외래키 참조가 복잡해진다**

```sql
-- 복합키를 참조하는 테이블은 모든 컬럼을 다 가져야 한다
CREATE TABLE move_history (
    game_id  BIGINT NOT NULL,
    position VARCHAR(10) NOT NULL,
    moved_at TIMESTAMP NOT NULL,
    FOREIGN KEY (game_id, position) REFERENCES game_piece(game_id, position)
);
```

참조하는 테이블이 늘어날수록 FK가 복잡해진다

<br/>

✨ **수정 가능성 문제**

복합키의 구성 컬럼이 비즈니스 값이라면, 그 값이 변경될 때 FK도 함께 수정되어야 한다

예) 포지션 표기 방식이 바뀌면 모든 참조를 수정해야 한다

<br/>

✨ **ORM 설정이 복잡**

JPA에서 복합키를 다루려면 `@EmbeddedId` 또는 `@IdClass`를 써야 한다

```java
@Entity
@IdClass(GamePieceId.class)
public class GamePiece {
    @Id private Long gameId;
    @Id private String position;
}
```

---

### 언제 자연스러운가?

다대다 관계의 연결 테이블에서 복합키가 자연스럽다

```sql
CREATE TABLE player_game (
    player_id BIGINT NOT NULL,
    game_id   BIGINT NOT NULL,
    PRIMARY KEY (player_id, game_id)
);
```

이 경우 `player_id + game_id`가 자연스러운 복합키다

## 내 기준

### 비교

| 기준      | 대리키             | 복합키             |
| ------- | --------------- | --------------- |
| 구조 단순성  | 단순              | 복잡              |
| 외래키 참조  | 숫자 하나           | 컬럼 여러 개         |
| 변경 안전성  | 비즈니스 값 변경과 무관   | 구성 컬럼 변경 시 영향 큼 |
| ORM 호환성 | 기본 지원           | 별도 설정 필요        |
| 중복 방지   | UNIQUE 제약 별도 필요 | 기본키 자체가 중복 방지   |
| 도메인 표현력 | 의미 없는 id        | 자연스러운 식별        |

---

### 내 기준

```
새 테이블을 만든다
       │
       ▼
이 테이블의 구성 컬럼들이 변경될 가능성이 있는가?
       │
  ┌────┴────┐
 YES        NO
  │          │
  ▼          ▼
대리키 선택  다대다 연결 테이블인가?
            │
       ┌────┴────┐
      YES        NO
       │          │
       ▼          ▼
    복합키 고려  대리키 기본
```

---

### 실전 기준표

| 상황 | 선택 |
|---|---|
| 일반 엔티티 (Game, Player 등) | 대리키 기본 + UNIQUE 제약 추가 |
| 다대다 연결 테이블 | 복합키 자연스러움 |
| 구성 컬럼이 변경될 가능성이 있다 | 대리키 |
| JPA 사용 | 대리키 강력 권장 |
| 외부 API에 id를 노출한다 | UUID 대리키 고려 |

### ENUM vs VARCHAR + CHECK 제약

피드백에서 함께 나왔던 주제 (이 주제도 고민이 깊어지면 따로 분리할 예정)

|       | ENUM                  | VARCHAR + CHECK          |
| ----- | --------------------- | ------------------------ |
| 장점    | DB 수준 제약, 명확한 허용값     | DB 종속성 없음, 이식성 좋음        |
| 단점    | DB 마이그레이션 필요 (값 추가 시) | 잘못된 값이 들어오면 앱 레벨에서만 막음   |
| 선택 기준 | 값이 고정되고 변경이 없을 때      | 값이 자주 바뀌거나 DB 독립성이 중요할 때 |
