## 발단

컨트롤러 테스트를 보면 이렇다

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ReservationControllerTest {

    @MockitoBean
    private ReservationService reservationService;
```

컨트롤러 테스트인데 전체 스프링 컨텍스트를 띄우고 있다

서비스 테스트를 보면 이렇다

```java
@Test
void 날짜와_테마아이디로_예약가능한_시간을_조회한다() {
    // ...
    verify(themeRepository, times(1)).findById(anyLong());
    verify(timeRepository, times(1)).findByDateAndThemeId(any(), anyLong());
    verifyNoMoreInteractions(themeRepository, timeRepository, reservationRepository);
}
```

모든 테스트 마지막에 `verifyNoMoreInteractions`가 붙어 있다

두 가지 모두 테스트가 필요 이상으로 구현에 묶여 있다

## 컨트롤러 테스트에 전체 컨텍스트가 필요한가?

## 이 테스트가 검증하려는 게 뭔가?

컨트롤러 테스트의 목적은 하나다

> ==요청을 올바르게 받고, 응답을 올바르게 내보내는가==

서비스는 이미 `@MockitoBean`으로 대체돼 있다

그런데 `@SpringBootTest`로 전체 스프링 컨텍스트를 띄우고 있다

---

## @SpringBootTest vs @WebMvcTest

| | @SpringBootTest | @WebMvcTest |
|---|---|---|
| 올라오는 것 | 전체 스프링 컨텍스트 | MVC 레이어만 |
| 속도 | 느림 | 빠름 |
| 서비스 처리 | @MockitoBean으로 대체 가능 | 반드시 @MockBean 필요 |

`@WebMvcTest`는 컨트롤러 레이어만 올린다

서비스, 레포지토리 빈은 올라오지 않기 때문에 반드시 `@MockBean`으로 주입해야 한다

---

## 어떻게 바꾸나?

```java
// before
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ReservationControllerTest {

    @MockitoBean
    private ReservationService reservationService;

// after
@WebMvcTest(ReservationController.class)
class ReservationControllerTest {

    @MockitoBean
    private ReservationService reservationService;
```

서비스를 이미 mock하고 있다면 `@MockitoBean` 코드는 그대로 쓸 수 있다

---

## 왜 바꿔야 하나?

컨트롤러 테스트의 목적이 "요청/응답 검증"이라면 전체 컨텍스트를 올릴 이유가 없다

불필요하게 올라오는 빈이 많아질수록 테스트 실행이 느려지고

실패 원인도 컨트롤러 레이어 밖에서 생길 수 있다

## 모든 테스트에 verifyNoMoreInteractions가 있으면?

## verifyNoMoreInteractions가 하는 일

mock 객체에 더 이상 호출이 없었는지 검증한다

```java
verify(themeRepository, times(1)).findById(anyLong());
verifyNoMoreInteractions(themeRepository, timeRepository, reservationRepository);
```

`themeRepository`, `timeRepository` 외에 다른 호출이 있었다면 테스트가 깨진다

---

## 어떤 상황에서 문제가 생기나?

이 테스트의 이름은 `날짜와_테마아이디로_예약가능한_시간을_조회한다`다

검증하려는 건 **올바른 시간 목록이 반환됐는가**다

그런데 `verifyNoMoreInteractions`에 `reservationRepository`가 들어가 있다

`getAvailableTimes`와 직접 관련 없는 mock까지 감시하고 있는 것이다

```java
verifyNoMoreInteractions(themeRepository, timeRepository, reservationRepository);
//                                                        ↑ 이 테스트 목적과 무관
```

---

## 구체적으로 어떻게 깨지나?

내부를 리팩토링해서 `themeRepository.findById` 대신 다른 방식으로 테마 존재를 확인하도록 바꿨다

반환값도 같고 예외 처리도 같다. 비즈니스 결과는 완전히 동일하다

그런데 테스트가 깨진다

> ==비즈니스 로직이 바뀐 게 아닌데 테스트가 깨진다==

---

## verify 자체가 나쁜 건 아니다

특정 호출이 반드시 일어나야 한다는 의도적인 계약이 있다면 써도 된다

```java
// "테마가 존재하는지 반드시 확인해야 한다"는 계약이 있다면
verify(themeRepository, times(1)).findById(anyLong());
```

문제는 `verifyNoMoreInteractions`를 모든 테스트에 기계적으로 붙이는 것이다

그러면 테스트가 결과가 아니라 구현 흐름을 감시하게 된다

## 내 기준

## 테스트는 리팩토링의 안전망이다

리팩토링의 정의는 하나다

> "결과는 바꾸지 않고 구현을 개선하는 것"

테스트가 구현 세부사항에 결합돼 있으면, 결과는 그대로인데 구현을 바꿀 때마다 테스트도 같이 고쳐야 한다

안전망이 아니라 짐이 된다

---

## 결과 검증 vs 구현 검증

```java
// 결과 검증: 이 기능이 올바른 결과를 내는가?
assertThat(availableTimes).containsExactlyInAnyOrder(time1, time2);

// 구현 검증: 내부적으로 어떤 메서드가 몇 번 호출됐는가?
verifyNoMoreInteractions(reservationRepository);
```

테스트가 보호해야 할 건 결과다

구현 방식은 테스트 모르게 자유롭게 바꿀 수 있어야 한다

---

## 테스트 실패를 믿을 수 없게 된다

구현에 결합된 테스트가 깨졌을 때 두 가지 가능성이 생긴다

1. 비즈니스 로직이 잘못된 것인가
2. 내부 구현을 바꿨는데 테스트가 예전 방식을 기억하고 있는 것인가

구별이 안 된다. 테스트 실패 메시지를 신뢰할 수 없게 된다

---

## 기준

| | 기준 |
|---|---|
| `@WebMvcTest` | 컨트롤러 요청/응답 검증이 목적이라면 전체 컨텍스트 불필요 |
| `verify` | 이 호출이 반드시 일어나야 한다는 의도적 계약이 있을 때만 |
| `verifyNoMoreInteractions` | 해당 테스트 목적과 직접 관련된 mock에만, 기계적으로 붙이지 않는다 |
