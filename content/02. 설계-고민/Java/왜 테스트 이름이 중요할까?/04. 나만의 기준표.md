> "테스트 이름을 어떻게 지을까?" 에 대한 내 답

---

## 핵심 질문

> "이 이름만 보고 어떤 규칙을 검증하는지 알 수 있는가?"

→ **YES** → 좋은 이름  
→ **NO** → 조건 + 결과를 이름에 추가

---

## 이름 구성 기준

```
1. 주어(무엇이): 병, 포, 장기보드, 게임 등
2. 조건(어떤 상황에): 기물이 없을 때, 같은 위치일 때 등
3. 결과(어떻게 되는가): 이동할 수 없다, 예외가 발생한다 등
```

```
병은_앞으로만_이동할_수_있다           ← 행위 규칙
같은_위치로_이동하면_예외가_발생한다    ← 실패 케이스
포는_경로에_기물이_없으면_이동_불가하다 ← 조건 + 결과
```

---

## 금지 패턴

| 패턴 | 이유 |
|---|---|
| `test1` / `test2` | 정보 없음 |
| `정상_케이스` | 정상이 무엇인지 모름 |
| `이동_테스트` | 어떤 이동인지 모름 |
| `실패_테스트` | 무슨 실패인지 모름 |

---

## @DisplayName 사용 기준

| 상황 | 판단 |
|---|---|
| 한글 메서드명으로 충분히 표현된다 | `@DisplayName` 불필요 |
| 더 자세한 설명이 필요하다 | `@DisplayName` 추가 |
| 영어 메서드명 + 한글 설명 | `@DisplayName` 사용 |
| `@DisplayName`이 메서드명과 다르다 | 혼란 — 통일 |

---

## 실전 체크리스트

- ✨ **이름에 "테스트", "케이스", "확인"이 들어가는가?**

이런 단어는 테스트임을 다시 말할 뿐이다. 규칙 내용으로 대체한다

<br/>

- ✨ **이름에 숫자가 들어가는가 (`test1`, `케이스2`)?**

순서가 아닌 규칙/조건으로 구분한다

<br/>

- ✨ **`@DisplayName`에 오탈자가 있는가?**

명세서로서의 신뢰를 잃는다. 꼼꼼히 확인한다

<br/>

- ✨ **실패했을 때 이름만 보고 원인을 추론할 수 있는가?**

그렇지 않다면 이름을 개선한다
