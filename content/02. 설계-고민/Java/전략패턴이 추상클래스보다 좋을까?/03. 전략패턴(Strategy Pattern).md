> 전략 패턴은 ==알고리즘(행위)을 별도 객체로 분리해 런타임에 교체할 수 있게 하는 것==이다

---

## 개념

```java
// 전략 인터페이스
public interface MoveRule {
    List<Position> getMovablePositions(Position from, Board board);
}

// 전략 구현체들
public class StraightMoveRule implements MoveRule { ... }
public class CannonMoveRule implements MoveRule { ... }
public class DiagonalMoveRule implements MoveRule { ... }

// 전략을 사용하는 Piece — 상속 없음
public class Piece {
    private final MoveRule moveRule; // 전략 주입

    public Piece(MoveRule moveRule) {
        this.moveRule = moveRule;
    }

    public List<Position> getMovablePositions(Position from, Board board) {
        return moveRule.getMovablePositions(from, board); // 전략에 위임
    }
}
```

---

## 장점

- ✨ **유연하게 교체 가능하다**

런타임에 다른 전략을 주입하면 행위가 바뀐다

<br/>

- ✨ **다중 구현이 가능하다**

인터페이스 기반이라 여러 전략을 자유롭게 조합할 수 있다

<br/>

- ✨ **새 전략 추가가 쉽다**

`Piece` 클래스를 건드리지 않고 새 `MoveRule` 구현체만 추가한다 (OCP)

<br/>

- ✨ **테스트가 쉽다**

전략 객체를 독립적으로 테스트할 수 있다

---

## 단점

- ✨ **공통 상태 공유가 어렵다**

전략 객체는 보통 무상태(stateless)로 만든다

상태를 공유하려면 파라미터로 전달하거나 별도 설계가 필요하다

<br/>

- ✨ **객체 수가 늘어난다**

전략마다 클래스가 생긴다

단순한 경우 오히려 복잡도가 올라갈 수 있다

---

## 추상 클래스와의 조합

두 방식을 함께 쓸 수도 있다

```java
// Piece에 전략 패턴 적용 (전략 교체 가능)
// 공통 로직이 있는 전략은 추상 클래스로
public abstract class BaseMoveRule implements MoveRule {
    protected boolean isBlocked(Position pos, Board board) { ... }
}

public class StraightMoveRule extends BaseMoveRule {
    @Override
    public List<Position> getMovablePositions(...) {
        // isBlocked() 재사용
    }
}
```
