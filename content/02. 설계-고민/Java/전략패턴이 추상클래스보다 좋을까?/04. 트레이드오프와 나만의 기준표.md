## 비교

| | 추상 클래스 | 전략 패턴 |
|---|---|---|
| 공통 상태 공유 | ✅ 자연스럽다 | ❌ 파라미터 전달 필요 |
| 코드 재사용 | ✅ `protected` 메서드 | ⚠️ 조합으로 해결 |
| 유연성 (교체 가능) | ❌ 상속 구조에 고정 | ✅ 런타임 교체 가능 |
| 다중 구현 | ❌ 단일 상속 | ✅ 인터페이스 다중 구현 |
| OCP 준수 | ⚠️ 새 자식 추가 | ✅ 새 전략 추가 |
| 테스트 용이성 | 보통 | ✅ 전략 독립 테스트 |
| 적합한 상황 | 공통 상태/로직이 많다 | 행위 교체가 중요하다 |

## 마와 상처럼 거의 동일한 경우

추상 클래스로 분리하는 것보다 **생성자 주입**으로 해결하는 편이 나을 수 있다

```java
// ❌ — Ma와 Sang이 거의 같은데 별도 클래스
public class Ma extends DiagonalPiece { ... }
public class Sang extends DiagonalPiece { ... }

// ✅ — 이동 방향 차이를 생성자로 주입
public class DiagonalPiece {
    private final int straightStep;
    private final int diagonalStep;

    public static DiagonalPiece ma() {
        return new DiagonalPiece(1, 1); // 직선 1, 대각 1
    }

    public static DiagonalPiece sang() {
        return new DiagonalPiece(1, 2); // 직선 1, 대각 2
    }
}
```

## 실전 체크리스트

- ✨ **두 클래스가 거의 같은 코드를 갖는가?**

상수값이나 이동 방향 차이라면 생성자 주입으로 통합한다

<br/>

- ✨ **행위가 런타임에 바뀌어야 하는가?**

전략 패턴을 도입한다

<br/>

- ✨ **공통 상태(필드)가 많은가?**

추상 클래스가 더 자연스럽다

<br/>

- ✨ **다중 구현이 필요한가?**

추상 클래스의 단일 상속 한계 → 전략 패턴 + 인터페이스
