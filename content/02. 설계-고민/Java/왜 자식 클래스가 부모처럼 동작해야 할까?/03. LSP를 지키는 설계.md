
> LSP를 지키는 핵심은 ==계층 구조가 "행위의 유사성"에 기반하는 것==이다  
> 코드 재사용이 아닌 행위의 일관성을 위해 상속한다

---

## 패턴 1: Null Object 패턴으로 빈 구현 처리

```java
// ✅ — 빈 기물도 Piece처럼 동작한다
public class EmptyPiece implements Piece {

    @Override
    public List<Position> getMovablePositions(Position from, Board board) {
        return List.of(); // 빈 기물은 이동 가능한 위치가 없다 — 예외 없음
    }

    @Override
    public int getScore() {
        return 0; // 빈 기물은 점수가 없다
    }

    @Override
    public boolean isOwnedBy(Side side) {
        return false; // 빈 기물은 누구의 것도 아니다
    }
}
```

`Piece`를 사용하는 쪽이 null 체크 없이 안전하게 쓸 수 있다

## 패턴 2: 상속보다 인터페이스 분리

서로 다른 계약을 하나의 인터페이스로 묶으면 LSP가 깨진다

```java
// ❌ — 차(Chariot)는 포(Cannon)의 규칙이 필요 없다
public interface CannonRule {
    boolean canJumpOver(List<Piece> path);
}

public class Chariot extends StraightMovePiece implements CannonRule {
    @Override
    public boolean canJumpOver(List<Piece> path) {
        throw new UnsupportedOperationException(); // 차는 이 메서드가 의미 없다
    }
}
```

```java
// ✅ — 포에게만 필요한 규칙은 포만 구현한다
public class Cannon extends StraightMovePiece implements JumpRule {
    @Override
    public boolean canJumpOver(List<Piece> path) {
        return path.size() == 1;
    }
}
// Chariot은 JumpRule 구현 불필요
```

## 상속을 쓸 때 LSP 체크

```
부모 클래스의 모든 메서드를
자식 클래스로 대체해도 동작이 같은가?
         │
    ┌────┴────┐
   YES        NO
    │          │
    ▼          ▼
LSP 준수   ❌ 상속이 잘못된 것
           인터페이스 분리 or 구조 변경 고려
```

---

## 상속 vs 인터페이스

| 상황 | 선택 |
|---|---|
| "~이다(is-a)" 관계 + 행위가 일관됨 | 상속 |
| "~할 수 있다(can-do)" 관계 | 인터페이스 |
| 공통 코드 재사용이 목적 | 컴포지션 고려 |
