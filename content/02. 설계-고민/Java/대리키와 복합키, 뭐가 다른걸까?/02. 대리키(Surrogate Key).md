
> 대리키는 ==비즈니스와 무관하게 DB가 부여하는 식별자==다  
> `AUTO_INCREMENT`, `SEQUENCE`, `UUID` 등이 여기에 해당한다

---

## 개념

```sql
CREATE TABLE game (
    id      BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 대리키
    name    VARCHAR(50) NOT NULL,
    status  VARCHAR(20) NOT NULL
);
```

`id`는 게임의 도메인적 의미가 없다. DB가 자동으로 부여하는 식별자다

---

## 장점

- [I] **단순한 조인**

외래키로 참조할 때 숫자 하나(`game_id`)만 있으면 된다

<br/>

- [I] **변경에 안전**

비즈니스 값(이름, 상태 등)이 바뀌어도 식별자가 바뀌지 않는다

복합키는 구성 컬럼이 바뀌면 FK를 참조하는 모든 곳도 바꿔야 한다

<br/>

- [I] **단순한 인덱스**

숫자 단일 컬럼 인덱스는 복합 인덱스보다 빠르다

<br/>

- [I] **ORM 친화적**

JPA 등 대부분의 ORM이 단일 대리키를 기본으로 설계되어 있다

---

## 단점

- [I] **자연키와 분리되어 중복 위험**

`name` 같은 자연키가 유니크해야 한다면 별도 UNIQUE 제약이 필요하다

```sql
CREATE TABLE game (
    id    BIGINT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(50) NOT NULL UNIQUE,  -- 별도 유니크 제약 필요
    ...
);
```

<br/>

- [I] **의미 없는 ID 노출**

API에서 `id=3`을 외부에 노출하면 순서 추측 등 보안 이슈가 생길 수 있다  

하지만, 이 경우 ==UUID 대리키==로 대응 가능하다


```sql
id UUID DEFAULT gen_random_uuid() PRIMARY KEY
```


순서를 예측할 수 없어 외부 노출에 유리하지만,

인덱스 성능이 낮고 저장 공간이 크다는 단점이 있다
