> ==Tell, Don't Ask==  
> 객체에게 상태를 물어보고 외부에서 결정하지 말고, 객체에게 직접 일을 시켜라

---

## 개념

**Ask(물어보기)**: 값을 꺼내서 외부에서 판단

```java
// Ask — "네 상태가 뭐야? 내가 결정할게."
if (order.getStatus() == Status.PENDING) {
    order.setStatus(Status.PAID);
}
```

**Tell(시키기)**: 객체에게 행위를 명령

```java
// Tell — "결제 처리해."
order.pay();

// Order 안에서
public void pay() {
    if (this.status != Status.PENDING) {
        throw new IllegalStateException("결제는 PENDING 상태에서만 가능합니다.");
    }
    this.status = Status.PAID;
}
```

`pay()` 안에서 상태 검증과 변경이 함께 이루어진다

---

## 왜 Tell이 더 좋은가

- [I] **로직이 객체 안에 모인다**

상태 검증 로직이 `Order` 안에 캡슐화된다

같은 검증이 여러 곳에 흩어지지 않는다

<br/>

- [I] **도메인 의도가 드러난다**

`order.pay()` 는 "주문을 결제한다"는 도메인 의미가 있다

`order.setStatus(Status.PAID)` 는 단순 데이터 조작이다

<br/>

- [I] **변경 범위가 좁아진다**

결제 로직이 바뀌면 `Order.pay()` 하나만 바꾸면 된다

---

## getter가 허용되는 경우

- [I] **DTO, Record — 뷰/레이어 경계에서 값 전달**

```java
// DTO는 값을 전달하는 것이 목적이므로 getter가 자연스럽다
public record GameResponse(String name, String status) {}
```

<br/>

- [I] **도메인 밖에서 표현 계층이 값을 읽을 때**

뷰(View)는 도메인 객체에서 값을 읽어 화면에 표시한다

이 경우 getter를 완전히 없애면 오히려 어색하다

<br/>

- [I] **테스트에서 결과를 검증할 때**

```java
assertThat(piece.getSide()).isEqualTo(Side.HAN);
```

> 핵심: **도메인 모델 안에서는** 최대한 메시지를 보내는 방식을 유지한다
