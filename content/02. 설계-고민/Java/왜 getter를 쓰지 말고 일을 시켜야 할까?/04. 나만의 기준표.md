
> "getter를 써도 될까?" 에 대한 내 답

---

## 핵심 질문

> "값을 꺼낸 뒤 판단을 내가 하고 있는가? 아니면 그 판단도 객체가 할 수 있는가?"

→ 객체가 할 수 있다 → **Tell, Don't Ask**로 바꾼다  
→ 표현을 위해 값이 필요하다 → **getter 허용**

---

## 판단 기준표

| 상황 | getter 사용 |
|---|---|
| 도메인 로직 내 상태 확인 후 분기 | ❌ → Tell, Don't Ask |
| DTO/Record에서 값 전달 | ✅ 자연스럽다 |
| 뷰(출력)에서 값을 읽을 때 | ✅ 허용 |
| 테스트에서 결과 검증 | ✅ 허용 |
| 불변 객체의 값 조회 | ⚠️ 꺼낸 값으로 외부 판단 → ❌ |

---

## getter → Tell 변환 패턴

```
// Before (Ask)
if (obj.getStatus() == X) { obj.setStatus(Y); }

// After (Tell)
obj.changeToY();
```

```
// Before (Ask)
if (piece.getSide() == Side.HAN) { score += piece.getScore(); }

// After (Tell)
score += piece.scoreForSide(Side.HAN); // 혹은
pieces.calculateScoreFor(Side.HAN);   // 일급 컬렉션에 위임
```

## 실전 체크리스트

- [I] **getter 반환값으로 if 분기를 만들고 있는가?**

그 분기 로직을 객체 안으로 옮긴다

<br/>

- [I] **`get~`이 아니어도 내부 값을 반환하는가?**

이름이 아니라 **값을 꺼내서 외부가 판단하는가**가 기준이다

<br/>

- [I] **같은 getter + 판단 로직이 여러 곳에 흩어져 있는가?**

중복 제거 + 객체 안으로 응집시킨다

<br/>

- [I] **record 접근자 대신 별도 getter를 선언했는가?**

record는 자체 접근자를 사용한다 (`game.name()` 방식)
