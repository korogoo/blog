> 세 종류의 엔티티를 항상 분리해야 한다는 것이 아니라  
> ==규모와 복잡도에 맞는 전략을 선택하는 것==이 핵심이다

---

## 전략 1: 통합 (작은 프로젝트)

> JPA 엔티티 = 도메인 엔티티로 사용

```java
@Entity
@Table(name = "member")
public class Member {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    // 간단한 도메인 로직도 여기에
    public boolean hasSameEmail(String other) {
        return this.email.equals(other);
    }
}
```

**선택 기준**
- 비즈니스 로직이 단순하다
- 팀이 작고, 빠른 개발이 우선이다
- 도메인 레이어를 따로 테스트할 이유가 없다

**주의할 점**  
나중에 로직이 복잡해지면 분리 비용이 커진다. 처음부터 도메인 메서드를 최소화해두면 이후 분리가 쉬워진다

---

## 전략 2: 분리 (복잡한 도메인)

> 도메인 엔티티 / JPA 엔티티 / 매퍼를 각각 둔다

```
src/
├── domain/
│   └── member/
│       ├── Member.java          ← 도메인 엔티티
│       ├── MemberId.java
│       ├── Email.java
│       └── MemberRepository.java (인터페이스)
│
└── infrastructure/
    └── member/
        ├── MemberJpaEntity.java ← JPA 엔티티
        ├── MemberJpaRepository.java
        └── MemberMapper.java    ← 변환 담당
```

**선택 기준**
- 비즈니스 규칙이 복잡하고 자주 바뀐다
- 도메인 로직을 DB 없이 단위 테스트해야 한다
- 팀이 크고, 도메인 레이어와 인프라 레이어를 다른 사람이 담당한다

---

## 매퍼 작성 가이드

분리 전략을 쓸 때 매퍼의 위치와 책임이 중요하다

```java
@Component
public class MemberMapper {

    // JPA 엔티티 → 도메인 엔티티
    public Member toDomain(MemberJpaEntity entity) {
        return Member.restore(
            new MemberId(entity.getId()),
            new Email(entity.getEmail()),
            entity.getCreatedAt()
        );
    }

    // 도메인 엔티티 → JPA 엔티티
    public MemberJpaEntity toJpaEntity(Member member) {
        MemberJpaEntity entity = new MemberJpaEntity();
        entity.setEmail(member.getEmail().getValue());
        entity.setCreatedAt(member.getCreatedAt());
        return entity;
    }
}
```

- 매퍼는 인프라 레이어에 둔다. 도메인이 매퍼를 알면 안 된다
- 도메인 엔티티 생성 시 `restore()` 같은 팩토리 메서드를 분리해두면 생성자와 재구성을 구분할 수 있다

```
새 프로젝트를 시작한다
       │
       ▼
도메인 규칙이 복잡하거나 자주 바뀔 것 같은가?
       │
  ┌────┴────┐
 YES        NO
  │          │
  ▼          ▼
분리 전략    도메인 메서드 없이 JPA 엔티티 통합 사용
```

## 실전 기준표

| 상황 | 선택 |
|---|---|
| 미션/토이 프로젝트, 로직 단순 | 통합 (JPA 엔티티 = 도메인 엔티티) |
| 도메인 로직 단위 테스트가 필요 | 분리 |
| DB 없이 도메인을 설명할 수 있어야 한다 | 분리 |
| JPA 기본 생성자가 도메인 불변식을 깨트린다 | 분리 |
| 빠른 프로토타이핑, 이후 리팩터링 예정 | 통합으로 시작 → 복잡해지면 분리 |

---

## 기억할 것

> 분리는 목적이 아니라 수단이다  
> 도메인을 DB로부터 보호해야 할 이유가 생겼을 때 분리한다
