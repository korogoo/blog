> 직접 실험으로 검증한 기준 (→ [[00. 당연한 원칙 직접 검증하기]])

---

## 핵심 질문

> "이 두 코드는 같은 이유로 함께 바뀌는가?"

→ **YES** → 합친다  
→ **NO** → 분리 유지

---

## 결정 흐름

```
비슷하게 생긴 코드를 발견했다
           │
           ▼
요구사항이 변경될 때 이 둘이 실제로 함께 바뀌는가?
           │
      ┌────┴────┐
     YES        NO
      │          │
      ▼          ▼
   합친다     변화 이유가 다르다
              → 분리 유지
```

---

## 합칠 때 vs 분리할 때

| 상황 | 판단 |
|---|---|
| 같은 사실이 여러 곳에 흩어져 있다 (보드 크기 상수 등) | ✅ 합친다 |
| 요구사항이 바뀔 때 항상 함께 수정되는 로직 | ✅ 합친다 |
| 코드 형태는 같지만 변경 이유가 다르다 (Row vs Column) | ❌ 분리 유지 |
| "나중에 달라질 수도 있어서" 분리했다 | ❌ 아직 오지 않은 이유 |
| 합쳤더니 분기/캐스팅이 늘어났다 | ❌ 다른 지식임을 증명 |

---

## 조기 추상화 경고

> 겉보기 유사성만으로 합쳤을 때의 신호:
>
> - 추상화를 유지하기 위해 분기나 캐스팅이 생긴다
> - 요구사항이 변경되기 전에 이미 구조를 바꿔야 한다
> - "이 구조에서는 해당 케이스를 처리하기 어렵다"는 말이 나온다

---

## 실전 체크리스트

- ✨ **이 두 코드가 마지막으로 동시에 수정된 적이 있는가?**

동시에 바뀐 경험이 있다면 같은 지식일 가능성이 높다

<br/>

- ✨ **합쳤을 때 도메인 의도가 더 명확해지는가?**

명확해진다면 합치는 근거가 있다

<br/>

- ✨ **합쳤더니 분기나 if가 더 생기는가?**

다른 지식이라는 신호다. 다시 분리한다

<br/>

- ✨ **테스트 상수와 프로덕션 상수가 같다고 합쳤는가?**

프로덕션 값이 바뀌면 테스트도 자동으로 바뀐다 → 테스트 의미가 없어진다  
두 상수는 같은 지식이 아니다. 분리 유지한다
