> "이 테스트를 단위 테스트로 할까, 통합 테스트로 할까?" 에 대한 내 답

---

## 비교

| | 단위 테스트 | 통합 테스트 |
|---|---|---|
| 속도 | 빠름 (ms) | 느림 (초~분) |
| 범위 | 하나의 클래스/메서드 | 여러 레이어 |
| 외부 의존성 | 없음 (Mock/InMemory) | 있음 (실제 DB 등) |
| 실패 원인 파악 | 명확 | 추적 필요 |
| 목적 | 비즈니스 로직 검증 | 레이어 연동 검증 |

---

## 결정 흐름

```
무엇을 검증하려 하는가?
         │
    ┌────┴────┐
비즈니스 로직  레이어 연동
(계산, 검증)  (DB, 트랜잭션)
    │          │
    ▼          ▼
단위 테스트   통합 테스트
```

---

## 기준표

| 검증 대상 | 테스트 종류 |
|---|---|
| 도메인 규칙 (이동 가능 여부, 점수 계산) | 단위 테스트 |
| Service 비즈니스 로직 (executeMove) | 단위 테스트 + InMemory Repository |
| Repository + 실제 DB 연동 | 통합 테스트 |
| 트랜잭션 롤백 확인 | 통합 테스트 |
| 전체 API 흐름 | 통합 테스트 |

---

## TDD 관점

> TDD로 구현했다면 사용되지 않는 필드가 선언될 수 없다

단위 테스트를 먼저 작성하면

- 실제로 필요한 코드만 구현하게 된다
- 테스트가 없는 코드는 구현되지 않는다
- 불필요한 필드, 메서드가 생기지 않는다

---

## 실전 체크리스트

✨ **비즈니스 로직에 대한 단위 테스트가 없는가?**

DB 없이 Service, Domain 로직을 검증하는 테스트를 추가한다

<br/>

✨ **통합 테스트만 있어서 실패 원인 파악이 어려운가?**

단위 테스트를 분리해서 각 레이어를 독립 검증한다

<br/>

✨ **테스트가 없는 메서드가 있는가?**

왜 테스트가 없는지 고민한다. 테스트하기 어렵다면 설계를 개선한다

<br/>

✨ **사용되지 않는 필드가 있는가?**

TDD로 구현했다면 생기지 않았을 것이다. 제거를 고려한다
