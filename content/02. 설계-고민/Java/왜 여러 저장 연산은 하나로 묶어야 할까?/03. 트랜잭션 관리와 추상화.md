## Connection을 파라미터로 넘기면 생기는 문제

```java
// ❌ — 인터페이스에 JDBC 기술이 드러남
public interface GameRepository {
    void save(Game game, Connection conn); // ← Connection이 인터페이스에 노출
}
```

이 인터페이스는 구현 기술이 JDBC임을 강제한다

나중에 JPA로 바꾸면 `Connection`이 없으므로 인터페이스 자체를 바꿔야 한다

---

## 올바른 추상화: 기술을 숨기는 방법들

### 방법 1: ThreadLocal로 Connection 공유

```java
// TransactionManager
public class TransactionManager {
    private final ThreadLocal<Connection> connectionHolder = new ThreadLocal<>();

    public void execute(Runnable work) {
        try (Connection conn = dataSource.getConnection()) {
            connectionHolder.set(conn);
            conn.setAutoCommit(false);
            work.run();
            conn.commit();
        } catch (Exception e) {
            rollback();
        } finally {
            connectionHolder.remove(); // ← 반드시 정리
        }
    }
}
```

Repository는 `TransactionManager`에서 Connection을 꺼내 사용

인터페이스에는 Connection이 드러나지 않는다

---

### 방법 2: Spring @Transactional (실무 환경)

```java
@Service
public class GameService {

    @Transactional  // ← 트랜잭션 시작/커밋/롤백을 Spring이 관리
    public void createGame(String name, List<Piece> pieces) {
        gameRepository.save(new Game(name));
        pieceRepository.saveAll(pieces);
    }
}
```

Repository는 트랜잭션을 몰라도 된다

---

## ThreadLocal 주의사항

- [I] **멀티스레드 환경에서 스레드마다 독립적인 Connection을 갖는다**

같은 스레드 안에서만 Connection이 공유된다

<br/>

- [I] **트랜잭션 밖에서 호출하면 Connection이 null일 수 있다**

항상 트랜잭션 안에서 사용하도록 강제하거나 null 체크가 필요하다

<br/>

- [I] **`threadLocal.remove()`를 반드시 호출해야 한다**

스레드 풀 환경에서 정리하지 않으면 이전 스레드의 Connection이 남아 있다

## 요약

| 방법 | 장점 | 단점 |
|---|---|---|
| Connection을 파라미터로 | 명시적 | 인터페이스에 기술 노출 |
| ThreadLocal | 인터페이스 깔끔 | 누수 주의, null 처리 필요 |
| Spring @Transactional | 가장 깔끔 | Spring 환경 필요 |
