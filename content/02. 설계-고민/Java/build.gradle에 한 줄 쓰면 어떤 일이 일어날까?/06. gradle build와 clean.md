> build가 의존성을 불러오는 거라고 생각했는데  
> ==build는 컴파일부터 jar 생성까지, clean은 이전 결과물을 지우는 것이다==

---

## gradle build

```bash
./gradlew build
```

소스코드를 컴파일하고, 테스트를 실행하고, 배포 가능한 `.jar` 파일을 만드는 전체 과정이다

- [I] **순서**

  1. 소스코드 컴파일 → `.class` 파일 생성
  2. 테스트 코드 전체 실행
  3. 테스트 통과 시 `.jar` 파일 생성 → `build/libs/`

테스트가 하나라도 실패하면 `.jar` 파일이 만들어지지 않는다

---

## build/ 폴더 구조

`./gradlew build` 실행 후 생성되는 폴더 구조다

```
build/
  classes/       ← 컴파일된 .class 파일
  libs/          ← 최종 .jar 파일
  test-results/  ← 테스트 결과 XML
  reports/       ← 테스트 HTML 리포트
```

---

## .jar가 필요한 때

로컬에서 IntelliJ로 실행할 때는 IntelliJ가 알아서 해줘서 `.jar`가 필요 없다

`.jar`가 필요한 건 **서버에 배포할 때** — IntelliJ가 없는 환경에서 실행해야 하므로

```bash
java -jar myapp.jar   # 서버에서 이렇게 실행
```

## gradle clean

```bash
./gradlew clean
```

`build/` 폴더를 통째로 삭제한다

이전 빌드 결과물을 완전히 지우고 새로 시작하고 싶을 때 쓴다

---

## 증분 빌드 vs clean

Gradle은 평소에 변경된 파일만 재컴파일(증분 빌드)한다

`clean`은 평소엔 불필요하다 — 아래 상황에서만 쓰는 비상 수단이다

```bash
./gradlew clean build
```

| 상황 | 이유 |
|------|------|
| 클래스 이름을 바꾸거나 파일을 삭제했을 때 | stale `.class` 파일이 남을 수 있다 |
| `build.gradle` 자체를 수정했을 때 | 의존성 변경이 반영 안 될 수 있다 |
| "분명히 고쳤는데 반영이 안 돼" 상황 | 증분 빌드가 변경을 감지 못한 것 |
| 원인 모를 컴파일 에러 | 일단 깨끗하게 초기화하고 다시 빌드 |

---

## 실수했던 것

`build`가 의존성을 불러오는 거라고만 알았다

`clean`도 몰라서 `build/` 폴더를 파인더에서 직접 삭제한 적이 있었다. 결과적으로 같지만.

`build/libs/`가 없어서 찾았는데, IntelliJ 실행 버튼만 눌렀고 `./gradlew build`를 직접 안 돌렸기 때문이었다

`.class` 파일을 열었을 때 소스코드처럼 보여서 `.java` 파일인 줄 알았는데,
IntelliJ가 자동으로 디컴파일해서 보여준 것이었다
