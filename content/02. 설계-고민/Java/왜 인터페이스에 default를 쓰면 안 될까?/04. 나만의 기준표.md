> "인터페이스를 어떻게 설계할까?" 에 대한 내 답

---

## 인터페이스 설계 핵심 질문

- [?] **이 메서드는 "무엇을" 하는지를 정의하는가?**

YES → 인터페이스에 포함

NO (어떻게를 강제한다) → 제거 또는 추상 클래스로

<br/>


- [?] **구현체가 바뀌어도 인터페이스는 바뀌지 않아야 하는가?**

YES → 기술 세부사항(Connection 등)을 제거

NO → 인터페이스가 기술에 종속됨

---

## default 사용 기준

| 상황 | 판단 |
|---|---|
| 라이브러리/프레임워크 하위 호환성 | ✅ 사용 목적에 맞음 |
| 공통 편의 메서드 (이미 있는 메서드로 구현 가능) | ⚠️ 신중하게 |
| 비즈니스 로직을 포함 | ❌ 추상 클래스 or 별도 클래스 분리 |
| 도메인 인터페이스 | ❌ 기본적으로 사용 안 함 |

---

## 인터페이스 vs 추상 클래스 선택

| 상황 | 선택 |
|---|---|
| 행위 계약만 정의 | 인터페이스 |
| 공통 상태와 공통 로직이 있다 | 추상 클래스 |
| 다중 구현이 필요하다 | 인터페이스 |
| 상속 계층을 고정하고 싶다 | 추상 클래스 |

---

## 실전 체크리스트

- [I] **인터페이스 메서드 파라미터에 기술 관련 타입이 있는가?**

`Connection`, `Session`, `EntityManager` 등 제거

<br/>

- [I] **인터페이스 메서드 이름이 구현 방식을 강제하는가?**

`validateAndThrow`, `saveWithCommit` 등 행위 기반 이름으로 변경

<br/>

- [I] **`default` 메서드 안에 비즈니스 로직이 있는가?**

추상 클래스로 옮기거나 별도 유틸 클래스로 분리한다

<br/>

- [I] **구현체가 인터페이스의 일부 메서드에서 예외를 던지는가?**

LSP 위반 가능성이 있다

인터페이스 설계를 재검토한다
