> Spring `@Transactional` 은 기본적으로 ==Unchecked Exception 에서만 롤백==한다
> Checked Exception 은 기본적으로 ==롤백하지 않는다==

---

## 기본 동작

```java
@Transactional
public void placeOrder(Order order) throws IOException {
    orderDao.save(order);
    throw new IOException("파일 저장 실패"); // Checked — 롤백 안 됨, 커밋됨!
}

@Transactional
public void placeOrder(Order order) {
    orderDao.save(order);
    throw new IllegalStateException("잘못된 상태"); // Unchecked — 롤백됨
}
```

---

## catch (Exception e) 의 위험성

```java
// 나쁜 예 — PR #303 에서 지적받은 패턴
try {
    T result = task.execute(connection);
    connection.commit();
    return result;
} catch (Exception e) {      // 모든 예외를 잡아버림
    connection.rollback();
    throw e;
}
```

> "회복 가능한 Checked Exception 까지 롤백시킨다" — her0807

회복 가능한 상황인데도 롤백이 일어나 데이터가 날아갈 수 있다

## rollbackFor 옵션

Checked Exception 에도 롤백을 원하면 명시적으로 설정한다

```java
@Transactional(rollbackFor = IOException.class)
public void placeOrder(Order order) throws IOException {
    ...
}
```

---

## 정리

| 예외 종류 | 기본 롤백 여부 |
| --------- | -------------- |
| `RuntimeException` (Unchecked) | O |
| `Error` | O |
| `Exception` (Checked) | X (커밋됨) |
| Checked + `rollbackFor` 설정 | O |

> 아직 Spring 을 쓰기 전이라 직접 경험은 없지만,  
> `catch (Exception e)` 가 왜 위험한지는 이해했다
