> 이제는 ==상황에 맞는 예외를 고를 수 있는 기준==을 갖고 싶다

---

## 기준표

| 상황 | 선택 | 이유 |
| ---- | ---- | ---- |
| 파일, DB, 네트워크 등 외부 환경 오류 | Checked | 호출자가 반드시 인지하고 대응해야 함 |
| 프로그래밍 실수, null, 잘못된 인자 | Unchecked | 사전에 방어했어야 할 상황 |
| 도메인 규칙 위반 | Unchecked | 비즈니스 예외는 대부분 Unchecked 로 |
| JDBC `SQLException` 전파 | Unchecked 래핑 | 상위 레이어가 구현 세부사항을 알 필요 없음 |
| 흐름 분기 판단 | 예외 사용 X | `if` 또는 명시적 메서드로 대체 |

---

## 체크리스트

예외를 던지기 전에 스스로 물어보기

- [ ] 이게 정말 예외적인 상황인가? 아니면 정상 흐름의 분기인가?
- [ ] 호출자가 이 예외를 인지하고 회복할 수 있나? → Checked
- [ ] 회복 불가능하거나 프로그래밍 실수인가? → Unchecked
- [ ] 인프라 예외를 상위 레이어까지 그대로 올리고 있지는 않은가?
- [ ] 예외 이름이 "무슨 문제인지" 명확히 설명하는가?

---

## 현재 나의 결론

이전까지는 그냥 `throw new RuntimeException(...)` 으로 다 때웠다

이제는 ==예외도 설계의 일부==라는 걸 안다

비즈니스 예외는 이름을 명확히 붙이고, 인프라 예외는 레이어 경계에서 변환하고, 흐름 제어에는 예외를 쓰지 않는다

> 이 기준표는 계속 업데이트 예정
