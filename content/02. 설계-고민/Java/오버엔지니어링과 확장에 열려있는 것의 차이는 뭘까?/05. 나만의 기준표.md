> "지금 추상화해야 하는가?" 에 대한 내 답  
> 변경 가능성을 염두에 두되, ==아직 필요하지 않은 추상화는 도입하지 않는다==

---

## 핵심 전제

> "변경 가능하게 만든다"는 것이  
> 인터페이스나 전략 객체를 미리 깔아두는 것과 꼭 같은 의미는 아니다

지금 요구사항에 잘 맞고, 책임이 선명하고, 읽기 좋은 코드가  나중에 바꾸기도 더 쉽다

---
## 실전 판단 흐름

```
새 구조를 설계한다
        │
        ▼
애플리케이션 코드인가, 변경 비용이 큰 영역인가?
        │
   ┌────┴──────────────┐
앱 코드              DB/외부 API/인프라
   │                      │
   ▼                      ▼
단순하게 시작          처음부터 확장 고려
   │
   ▼
비슷한 패턴이 세 번째 등장했는가?
또는 실제 변경 요구가 생겼는가?
   │
   ▼
그때 리팩터링
```

---

## 예외) 추상화를 미리 고려할 때

다음 두 조건 중 하나에 해당하면 다르게 판단한다

- [I] **이후에 반드시 도입될 기능이라는 확신이 있을 때**

확신의 근거: 팀 로드맵, 계약된 요구사항, 업무 특성상 반복되는 패턴

<br/>

- [I] **초기 구조를 잘못 잡으면 변경 비용이 너무 큰 영역일 때**

모든 레이어의 리팩터링 비용이 같지 않다

레이어별 리팩터링 비용을 고려하여 추상화를 도입한다

| 레이어 | 변경 비용 | 기본 전략 |
|---|---|---|
| 애플리케이션 코드 (도메인, 서비스) | 낮음 — IDE 리팩터링, 테스트로 확인 가능 | 단순하게 시작 |
| DB 스키마 | 높음 — 마이그레이션, 데이터 변환, 운영 리스크 | 처음부터 보수적으로 설계 |
| 외부 API 계약 | 높음 — 하위 호환성, 클라이언트 영향 | 변경 여지를 미리 확보 |
| 인프라 구성 | 높음 — 배포, 장애 위험 | 검증 후 변경 |

## 실전 체크리스트

- [I] **"나중에 필요할 것 같아서" 추상화를 도입하려 하는가?**

YAGNI — 실제 요구가 생겼을 때 리팩터링한다  
애플리케이션 코드는 리팩터링 비용이 낮다

<br/>

- [I] **지금 만드는 게 DB 스키마, 외부 API 계약, 인프라 구성인가?**

변경 비용이 높다. 여기서는 처음부터 보수적으로 설계한다

<br/>

- [I] **같은 패턴이 몇 번째 등장했는가?**

세 번째라면 추상화 타이밍이다

<br/>

- [I] **상속 계층이 3단계를 넘거나, 협력 객체가 3~4개 이상인가?**

단순화를 검토한다. 값 주입이나 enum으로 해결되지 않는지 먼저 본다

<br/>

- [I] **책임이 선명하고 읽기 좋은 구조인가?**

이것 자체가 나중에 바꾸기 쉬운 구조의 전제 조건이다
