> 
> 다만 실제로 실무를 보고 다양한 코드를 보면서, 적절한 타협점을 계속 찾아가는 것 같아요. 아무래도 여러 사람이 협업해서 코드를 작성하고 리뷰를 하다 보니, 회사에서 협업할때에는 정교한 다형성보다는 해당 코드가 지는 책임 그리고 해당 코드의 작관성에 대해 더 고민하게 되더라고요.
> 
> 예를 들어 협업을 하면서 코드 확인이 어려워서, 여러 단계의 상속 관계나 지나치게 세부적인 클래스 쪼개기는 지양하게 되었습니다.(기능 확인을 위해 지나치게 많은 클래스를 확인해야 하고, 책임이 분산되어 복잡도가 증가)  
대신 팀에서 다형성을 활용한 예시라면, 공통 모듈에 여러 인터페이스들을 만들어둬서, 공통 기능(예: 암호화, 파일 생성 등)에 대해 사용하는 쪽에서는 인터페이스만 참조하도록 하고 구현체는 필요 및 상황에 따라 여러 개를 만들어 주입해주는 경우도 보았습니다. 이러한 다형성의 적용은 정말 유용하게 잘 쓰고 있는듯 해요. (아무래도 책임이 명확하고, 사용하는 측에서도 편리하니까요)

> `협업하기 좋은 코드` 혹은 `직관적인 코드`는 사람마다 기준이 다를수밖에 없고, 저 역시 제 기준이 정답이라고 생각하지는 않습니다.  
그래서 더 중요한 건, 코로구의 기준을 어떻게 정할지라고 생각해요. 앞으로 페어들과 미션 진행하면서 기준을 잡아가고, 다만 유연하게 기준을 바꿀 수 있는 마음가짐도 함께 가지고 가면 좋겠습니다. 그러면 레벨2 시점쯤에는 지금 하시는 고민에 대해 어느정도 정리가 되어있지 않을까 기대되네요. 💯
