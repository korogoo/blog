## 전체 결정 흐름

```
새 클래스를 만든다
       │
       ▼
이 객체는 "변한다"는 게 도메인적으로 의미 있는가?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ▼        ▼
가변 고려  불변 기본값
   │
   ▼
JPA Entity인가?
   │
   ├── YES → 가변 Entity + 불변 VO 분리 검토
   │
   └── NO  → 상태 머신으로 변경 제어 가능한가?
                   │
               ┌───┴───┐
              YES      NO
               │        │
               ▼        ▼
           가변 OK    불변 강력 권장
```

---

## 불변을 선택하는 기준

아래 중 하나라도 해당하면 **불변 우선 검토**:

| 기준 | 예시 |
|------|------|
| 값 자체가 개념인 경우 | `Money`, `Email`, `Coordinates` |
| 여러 객체/스레드가 공유하는 경우 | 설정값, 공통 코드 |
| 변경 이력이 중요한 경우 | 이벤트 소싱 — 새 상태를 새 객체로 |
| 생성 후 절대 안 바뀌어야 하는 경우 | 주문 생성 시각, 가입 이메일 |
| 팀원이 실수로 바꿀 위험이 있는 경우 | setter 열어두면 여기저기서 건드림 |

## 가변을 유지하는 기준

| 기준             | 예시                              |
| -------------- | ------------------------------- |
| JPA Entity     | Hibernate 요구사항                  |
| 변경이 핵심 도메인 행위  | 주문 상태: PENDING → PAID → SHIPPED |
| 프레임워크가 가변을 요구  | Jackson 역직렬화, Spring Form       |
| 성능 측정 후 불변이 병목 | 단, 드문 경우 이므로 먼저 측정하고 나중에 최적화    |

## VO로 만들 기준

이 두 질문에 모두 YES면 VO를 사용한다

1. 이 데이터에 고유한 ID가 없어도 되는가?
2. 값이 같으면 같은 것으로 취급해도 되는가?

추가로 아래 신호가 있으면 VO로 바꾸는 것을 강하게 고려한다

- 같은 파라미터 묶음이 여러 메서드에 반복해서 등장한다
- 유효성 검사가 여러 군데 흩어져 있다 (중복)
- `String amount`, `String currency` 처럼 의미 없는 원시 타입을 쓴다
- 실수로 파라미터 순서를 바꿔 넣는 버그가 발생한 적 있다

## Record vs 일반 Class 기준

| 상황                            | 선택                                        |
| ----------------------------- | ----------------------------------------- |
| Java 16+, VO/DTO, JPA 무관      | Record 우선                                 |
| Java 11 이하                    | 일반 final class                            |
| JPA Entity 내부 VO (Embeddable) | 일반 final class (`@Embeddable`은 기본 생성자 필요) |
| 상속이 필요한 경우                    | 일반 class                                  |
| 복잡한 생성 로직                     | 일반 class + 정적 팩토리                         |

## 실전 체크리스트 (코드 리뷰 or 설계 시)

✨ **이 객체에 setter가 있는가?**

꼭 필요한가? 없앨 수 있으면 없앤다

<br/>


✨ **이 필드가 단순 String/int인데 특정 형식/범위가 있는가?**

VO로 만들자. 유효성 검사를 한 곳에 모은다

<br/>


✨ **이 객체를 여러 곳에서 참조하는가?**

불변이어야 공유가 안전하다

<br/>


✨ **getter가 List/배열/Date를 반환하는가?**

복사 반환 또는 unmodifiable 래핑한다

<br/>


✨ **Java 16+ 환경이고 새로운 VO를 만드는가?**

Record 먼저 시도한다

<br/>


✨ **JPA Entity에 너무 많은 책임이 있는가?**

VO를 분리하고 Entity는 상태 변화만 담당하게 한다
