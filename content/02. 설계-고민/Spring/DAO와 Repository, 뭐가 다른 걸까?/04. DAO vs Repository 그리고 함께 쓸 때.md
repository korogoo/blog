---

## 비교

| 구분 | DAO | Repository |
|---|---|---|
| 관점 | DB 기술 | 도메인 |
| 단위 | 테이블 | 집계 루트(Aggregate) |
| 이름 | 기술 중심 (`findByIdSQL`) | 도메인 중심 (`findByName`) |
| 추상화 수준 | 낮음 (SQL 노출) | 높음 (SQL 숨김) |
| 테스트 교체 | 어렵다 | 인터페이스로 쉽게 교체 |

---

## 함께 쓸 때의 구조

```
Service
  └── GameRepository (인터페이스)
          └── JdbcGameRepository (구현)
                  ├── GameDao
                  └── PieceDao
```

이 구조에서 역할이 명확하다

- **DAO** → SQL 한 줄씩 실행
- **Repository 구현체** → 여러 DAO를 조합해 도메인 객체 완성
- **Repository 인터페이스** → Service가 바라보는 도메인 계약

---

## 주의할 것

- [I] **인터페이스에 기술 세부사항이 드러나면 안 된다**

```java
// ❌ — Connection을 파라미터로 넣으면 인터페이스가 JDBC에 종속된다
public interface GameRepository {
    void save(Game game, Connection conn);
}
```

```java
// ✅ — 구현 방식은 숨긴다
public interface GameRepository {
    void save(Game game);
}
```

<br/>

- [I] **Repository가 도메인 흐름까지 담당하면 책임 초과다**

저장/조회만 담당하고, 흐름(어떤 순서로 실행하는지)은 Service가 결정한다

<br/>

- [I] **DAO가 Repository를 구현하는 구조가 항상 나쁜 건 아니다**

단, 그 의도를 명확히 설명할 수 있어야 한다  
"DAO가 Repository 인터페이스를 구현해서 Service는 인터페이스에만 의존한다" → 명확  
"그냥 둘 다 만들었다" → 의도가 없는 것
