> Repository는 ==도메인 관점에서 객체를 저장하고 꺼내는 인터페이스==다  
> "무엇을 저장하는가"를 담당하고, "어떻게 저장하는가"는 숨긴다

---

## 개념

Repository는 도메인 모델을 영속화하는 **컬렉션처럼 동작하는 추상화**다

마치 메모리 안에 컬렉션이 있는 것처럼 도메인 언어로 저장/조회를 표현한다

```java
public interface GameRepository {

    void save(Game game);

    Optional<Game> findById(Long id);

    List<Game> findAll();

    Optional<Long> findIdByName(String name);

    void delete(Long id);
}
```

---

## 특징

- [I] **도메인 언어를 쓴다**

`findByPlayerName`, `findAllActive` 등 DB가 아닌 도메인 관점의 이름

<br/>

- [I] **기술을 숨긴다**

호출하는 쪽은 JDBC인지 JPA인지 알 필요 없다

<br/>

- [I] **집계 루트(Aggregate Root) 단위**

테이블 단위가 아니라 도메인 개념 단위로 묶인다

예) `GameRepository` → 게임과 기물을 함께 관리

---

## DAO와 Repository의 관계

DAO가 Repository를 구현하는 구조는 흔하다

```
GameRepository (인터페이스 — 도메인 관점)
       │
       └── JdbcGameRepository (구현체 — DAO 역할, JDBC 기술)
```

```java
public class JdbcGameRepository implements GameRepository {

    private final GameDao gameDao;
    private final PieceDao pieceDao;

    @Override
    public void save(Game game) {
        gameDao.save(game);           // 게임 저장
        pieceDao.saveAll(game.getPieces()); // 기물 저장
    }
}
```

이 구조에서 Repository는 **도메인 계약**을 정의하고,  
DAO는 그 계약을 JDBC로 이행하는 구현체가 된다

---

## 왜 Repository가 따로 필요한가?

Service가 DAO를 직접 참조하면 DB 기술이 바뀔 때 Service도 바뀐다

Repository 인터페이스를 사이에 두면 Service는 인터페이스만 보고, 구현체(DAO)는 언제든 교체할 수 있다

```java
// 테스트에서는 메모리 구현체로 교체 가능
public class InMemoryGameRepository implements GameRepository {
    private final Map<Long, Game> store = new HashMap<>();

    @Override
    public void save(Game game) {
        store.put(game.getId(), game);
    }
}
```
