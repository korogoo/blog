> "DAO를 쓸까, Repository를 쓸까?" 에 대한 내 답

---

## 전체 결정 흐름

```
새 저장소 클래스를 만든다
          │
          ▼
Service가 이 클래스를 직접 참조해도 되는가?
(나중에 구현체를 교체할 가능성이 없는가?)
          │
     ┌────┴────┐
    YES        NO
     │          │
     ▼          ▼
  DAO만        Repository 인터페이스 +
  사용해도 무방  DAO 구현체 구조 권장
```

---

## 기준표

| 상황 | 선택 |
|---|---|
| 소규모 프로젝트, 단일 DB 기술 | DAO만 사용해도 무방 |
| 테스트에서 DB를 Mock으로 교체하고 싶다 | Repository 인터페이스 필요 |
| 여러 DAO를 조합해 도메인 객체 완성이 필요 | Repository 구현체에서 조합 |
| JPA 사용 환경 | JpaRepository 자체가 Repository 역할 |

---

## 함께 쓸 때 역할 분리 원칙

- ✨ **Repository 인터페이스** → 도메인 언어로 정의, 기술 노출 금지

- ✨ **Repository 구현체(DAO 역할)** → SQL/JDBC 사용, 여러 테이블 조합 가능

- ✨ **Service** → Repository 인터페이스만 바라본다, DAO를 직접 알지 않는다

---

## 실전 체크리스트

- ✨ **Repository 인터페이스 메서드 파라미터에 Connection이 있는가?**

있으면 제거한다. 구현 기술이 인터페이스에 드러난 것이다

<br/>

- ✨ **Service가 여러 DAO를 직접 참조하는가?**

Repository를 도입해 조합 책임을 옮긴다

<br/>

- ✨ **DAO와 Repository를 구분 없이 쓰고 있는가?**

역할이 무엇인지 한 문장으로 설명할 수 있어야 한다
