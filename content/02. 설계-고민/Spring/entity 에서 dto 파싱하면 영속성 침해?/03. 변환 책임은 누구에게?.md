> 변환 위치마다 트레이드오프가 있다

---

## Entity에서 변환 (`entity.toDto()`)

```java
public ReservationResponse toDto() {
    return new ReservationResponse(id, name, date);
}
```

- ✨ **장점** — 코드가 간결하고 사용하기 편하다

- ✨ **단점** — Domain이 DTO를 알게 된다. DTO 스펙이 바뀔 때마다 Entity가 바뀐다

---

## Service에서 변환

```java
public ReservationResponse findById(Long id) {
    Reservation reservation = reservationRepository.findById(id);
    return new ReservationResponse(reservation.getId(), reservation.getName(), reservation.getDate());
}
```

- ✨ **장점** — 트랜잭션 안에서 변환하므로 Lazy 문제 없음. Entity가 DTO를 모름

- ✨ **단점** — 필드가 많아지면 변환 코드가 길어진다

---

## 별도 Mapper/Assembler 클래스

```java
public class ReservationMapper {
    public static ReservationResponse toResponse(Reservation reservation) { ... }
}
```

- ✨ **장점** — 변환 책임을 한 곳에 모을 수 있다. Entity도 Service도 서로를 모른다

- ✨ **단점** — 클래스가 늘어나고, 팀 합의가 없으면 일관성이 깨진다
