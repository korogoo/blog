연어버스는 버스의 현재 잔여석을 보여주고, 다음 정류장에 도착했을 때 몇 석이 남을지 예측하는 서비스예요.

기능을 바꿀 때는 GitHub에 PR을 올려요. PR은 바꾸려는 코드를 팀원에게 보여주고, 기존 기능과 정책에 맞는지 검토받는 과정이에요.

저는 PR을 볼 때마다 “이 변경이 지금 정책과 맞나?”를 확인하려고 팀 문서를 적는 도구인 Confluence와 코드를 다시 뒤졌어요.

왜 이런 일이 생겼을까요?

연어버스에서 `수집`은 외부 버스 정보 시스템인 GBIS에 차량 위치와 잔여석을 요청하는 과정이에요.

근데 요청을 보낸 순간부터 수집이라고 부를지, 응답을 데이터베이스(DB)에 저장해야 수집이 끝났다고 볼지 팀원마다 다르게 이해할 수 있었어요. 같은 단어를 쓰면서 서로 다른 동작을 생각하고 있던 거예요.

> **이 글에서 말하는 도메인 정책**
>
> 서비스가 어떤 입력을 받고, 어떤 상태를 거쳐, 어떤 결과를 내야 하는지 정한 기준이에요. 예를 들면 “GBIS가 정상 응답했지만 차량이 없을 때 성공으로 볼 것인가?” 같은 결정이 도메인 정책에 해당해요.

Confluence에는 현재 정책과 검토 중인 제안, 개인 메모가 함께 남아 있었어요. 코드와 문서도 각자 바뀌었고요.

그래서 현재 정책 문서와 PR 코드를 비교하고, 팀이 승인한 변경만 이력과 최종 문서에 반영하는 흐름을 설계했어요.

이 글에서는 문서의 역할을 어떻게 나눴고, PR에서 정책 변경 후보를 어떻게 찾도록 설계했는지 차례대로 설명해볼게요.

## 문서가 늘수록 현재 기준이 흐려졌다

처음에는 필요한 설명을 더 적으면 문제가 풀릴 거라고 생각했어요.

실제로 문서가 늘어나면 설명도 늘어나요. 근데 지금 따라야 할 기준이 어느 문서인지 찾기는 더 어려워졌어요.

![현재 정책, 검토 중인 제안, 개인 메모가 섞여 PR 리뷰어가 기준을 직접 찾아야 하는 구조](assets/salmonbus-portfolio/11-policy-document-state.png)

그래서 문서의 역할부터 나눴어요.

팀이 현재 기준으로 사용할 문서에는 아래 내용만 한 흐름으로 연결했어요.

- 팀에서 사용하는 개념과 목적
- 입력과 출력
- 정상 흐름과 실패 조건
- 지금 유효한 서비스 정책
- 정책을 바꾼 PR과 결정 이유

`수집이 무엇인가?`, `예보는 언제 만들어졌다고 보는가?`처럼 팀에서 답이 달라질 수 있는 질문부터 적었어요.

클래스 이름이나 메서드 설명만 모아놓지는 않았어요. 같은 상황을 봤을 때 같은 판단을 할 수 있는 기준이 필요했기 때문이에요.

아직 합의하지 않은 제안과 개인 메모는 현재 정책 문서에서 뺐어요. 논의 중인 내용이 지금 지켜야 할 규칙처럼 읽히는 일을 막기 위해서예요.

## PR 코드와 현재 문서를 나란히 본다

문서의 역할을 나눴다면, 이제 코드가 바뀔 때 현재 정책과 다른 부분을 찾아야 해요.

사람이 PR마다 모든 문서를 처음부터 다시 읽는 방식은 오래 유지하기 어려워요. 그래서 PR이 올라오면 바뀐 코드와 현재 도메인 문서를 비교하도록 설계했어요.

```text
PR이 올라옴
→ 바뀐 코드 확인
→ 현재 정책 문서와 비교
→ 서로 다르게 보이는 위치와 근거를 정리
→ 팀원이 최종 판단
```

AI는 이 과정에서 비교할 코드와 문서 문장을 좁혀요.

설명용 예시를 하나 들어볼게요.

문서에는 “정상 응답에 차량이 없어도 수집 성공”이라고 적혀 있는데, 새 코드가 같은 응답을 실패로 저장한다고 해볼게요. 이때 서로 다른 문서 문장과 코드 위치를 함께 보여줘요.

여기서 중요한 점이 있어요. AI가 바로 `코드가 틀렸다`고 결론 내리지는 않아요. 팀원이 구현 오류인지, 의도한 정책 변경인지 판단해요.

![PR 코드와 도메인 문서를 비교하고 팀원이 정책 변경 여부를 판단하는 설계](assets/salmonbus-portfolio/10-policy-review-design.png)

기능은 그대로 두고 코드 구조만 정리하는 작업을 리팩터링이라고 해요. 리팩터링까지 정책 변경이라고 알리면 팀원이 검토할 내용이 너무 많아져요.

근거가 부족한 변경이나 아직 팀이 승인하지 않은 제안도 정책으로 확정하면 안 돼요. AI는 비교할 대상을 좁히고, 정책을 바꿀 권한은 팀에 남겨요.

## 코드와 문서가 다를 때 어떻게 판단할까?

코드가 문서와 다르다고 해서 무조건 버그는 아니에요.

코드가 틀렸을 수도 있고, 팀이 정책을 바꾸려는 중일 수도 있어요.

앞에서 본 수집 사례로 이어서 살펴볼게요.

- 차량이 없는 정상 응답을 성공으로 보기로 했다면 코드와 테스트를 수정
- 이제부터 실패로 보기로 했다면 사용자 화면과 재시도 동작까지 함께 검토
- 아직 합의하지 못했다면 현재 정책 문서를 유지

팀이 의도한 변경이라고 승인하고 PR을 병합하면 변경 이력을 남겨요. 병합은 검토를 마친 코드를 실제 코드에 합치는 일이에요.

변경 이력에는 이전 정책과 새 정책, 판단 근거가 된 PR을 연결해요.

최종 도메인 문서에는 지금 유효한 정책만 보여줘요. 과거 판단은 변경 이력에서 찾아요.

PR이 열렸다고 문서를 먼저 바꾸지는 않아요.

리뷰하면서 구현이 달라질 수 있고, PR이 닫힐 수도 있기 때문이에요. 팀이 변경을 승인했고 실제로 병합됐을 때만 최종 문서를 갱신해요.

## 알림에는 결론보다 근거를 담는다

마지막으로 팀원에게 어떤 알림을 보낼지 정했어요.

`정책이 변경됐어요`라는 결론만 보내면 팀원은 결국 PR과 문서를 처음부터 다시 찾아야 해요.

그래서 알림에는 최소한 아래 내용을 담도록 했어요.

- 어떤 정책 문장이 바뀌었는지
- 변경 전과 변경 후 내용
- 근거가 된 코드 위치와 PR
- 누가 검토했고 병합됐는지
- 최종 문서에 반영됐는지

알림을 받은 팀원은 무엇이 바뀌었는지 먼저 보고, 필요할 때 코드와 PR까지 따라갈 수 있어요.

정리하면 최종 문서는 지금 기준을 빠르게 읽는 곳이에요.

변경 이력은 왜 그런 결정을 했는지 다시 찾는 곳이고요. 둘을 나누면 현재 정책을 읽다가 오래된 논의에 막히지 않아요.
