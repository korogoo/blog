## 공통 원칙과 패턴

> B-Tree는 컬럼 원본값 기준으로 정렬된다. 원본값이 변환되거나 시작점을 특정할 수 없으면 인덱스를 못 탄다

---

## 케이스 1 — 함수로 컬럼을 감싸면?

```sql
-- 못 탐: YEAR()가 각 행의 created_at을 변환 → B-Tree 키와 달라짐
WHERE YEAR(created_at) = 2026

-- 탐: 원본값 그대로 비교
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
```

B-Tree에는 `YEAR(created_at)` 결과값이 저장되어 있지 않다

MySQL이 매 행마다 함수를 적용해서 비교해야 한다 -> 시작점 특정 불가 -> Full Scan

<br/>

## 케이스 2 — LIKE 앞에 와일드카드를 쓰면?

```sql
-- 못 탐: 끝이 '진구'인 값의 시작점을 B-Tree에서 찾을 수 없음
WHERE name LIKE '%진구'

-- 탐: '김'으로 시작하는 지점을 찾고 sequential read
WHERE name LIKE '김%'
```

B-Tree는 앞글자 기준으로 정렬되어 있다

`%진구`는 어디서 시작해야 할지 모른다 -> Full Scan

<br/>

## 케이스 3 — 묵시적 형 변환이 일어나면?

방향이 중요하다

```sql
-- member_id BIGINT일 때
WHERE member_id = '1'   -- 상수 '1'이 숫자로 변환 → 컬럼값 변환 없음 → 인덱스 탐

-- phone VARCHAR일 때
WHERE phone = 01012345678   -- 각 행의 phone값이 숫자로 변환 → 원본값 변환 → 인덱스 못 탐
```

⚠️ **컬럼값이 변환되면 인덱스를 못 탄다 — 상수가 변환되는 건 괜찮다**

케이스 1(함수)과 원리가 같다 -> 컬럼값에 변환이 적용되면 B-Tree 키와 달라진다

## 내 기준

> 인덱스 컬럼에 뭔가 적용되면 의심한다. 함수, 형변환, 와일드카드 — 셋 다 B-Tree 원본값을 바꾸거나 시작점을 못 잡게 만든다

---

❓ 실전 체크리스트

- WHERE 절에서 인덱스 컬럼에 함수를 씌우고 있진 않은가
- LIKE 조건이 `%`로 시작하진 않는가
- 컬럼 타입과 비교값 타입이 일치하는가 (특히 VARCHAR 컬럼에 숫자 비교)
- EXPLAIN에서 `type = ALL`이 보이면 위 세 가지를 먼저 의심한다
