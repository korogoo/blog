## 설계 기준 세 가지

> 복합 인덱스 컬럼 순서는 Cardinality, 단독 조회 빈도, 조건 타입 세 가지로 결정한다

---

## 기준 1 — Cardinality 높은 컬럼을 앞에

선택도가 높을수록 초반에 데이터를 많이 걸러낸다

뒤에 오는 컬럼의 탐색 범위가 좁아져 전체 비용이 줄어든다

```sql
-- (member_id, expires_at)
-- member_id로 1건으로 좁히고 -> expires_at range scan
-- (expires_at, member_id)보다 효율적
WHERE member_id = 1 AND expires_at > NOW()
```

<br/>

## 기준 2 — 단독 조회 빈도 높은 컬럼을 앞에

Leftmost Prefix Rule: `(A, B)` 인덱스는 A 단독 조건에도 사용 가능하다

```sql
-- (member_id, expires_at) 인덱스 하나로 두 쿼리를 모두 커버
WHERE member_id = 1                          -- O
WHERE member_id = 1 AND expires_at > NOW()   -- O
WHERE expires_at > NOW()                     -- X
```

<br/>

## 기준 3 — 동등 조건(=)을 범위 조건(>, <, BETWEEN) 앞에

범위 조건 이후 컬럼은 인덱스 효과가 없다

```sql
-- (expires_at, member_id) 순서면
WHERE expires_at > NOW() AND member_id = 1
-- expires_at 범위 결과 안에서 member_id가 정렬되어 있지 않음
-- member_id 조건은 인덱스 못 탐 -> 필터링만 가능
```

✨ **= 조건 먼저, 범위 조건 나중**

## 내 기준

> Cardinality 높은 것 앞에, 단독 조회 잦은 것 앞에, = 조건을 범위 조건 앞에

---

❓ 실전 체크리스트

- 복합 인덱스 설계 전에 실제 쿼리 패턴을 먼저 파악한다
- `=` 조건 컬럼과 `>`, `<`, `BETWEEN` 조건 컬럼이 섞여 있으면 `=` 조건을 앞에 둔다
- 단독으로도 자주 조회되는 컬럼이 있다면 Leftmost에 둬서 인덱스를 재사용한다
- EXPLAIN으로 실제로 인덱스를 타는지, `key_len`으로 복합 인덱스 중 몇 컬럼까지 쓰이는지 확인한다

### 💬 key_len으로 컬럼 사용 범위 파악

```sql
EXPLAIN SELECT * FROM refresh_token WHERE member_id = 1 AND expires_at > NOW();
-- key_len = 16이면 (member_id 8bytes + expires_at 8bytes) 둘 다 사용
-- key_len = 8이면 member_id만 사용
```
