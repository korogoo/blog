## 컴퓨터가 어떻게 생겨 먹었나?

## 부품 네 개

메인보드 위에 올라가는 핵심 부품은 크게 넷이다

```
┌──────────────┐        ┌──────────────┐
│     CPU      │        │ Main Memory  │
│ 읽고 해석하고 │◄──────►│ 실행 중인 것  │
│   실행한다    │        │  (휘발성)     │
└──────┬───────┘        └──────┬───────┘
       │      System Bus       │
       └───────────┬───────────┘
           ┌───────┴────────┐
    ┌──────┴──────┐  ┌──────┴──────┐
    │  Secondary  │  │ I/O Device  │
    │   Storage   │  │ 키보드 모니터 │
    │ 전원 꺼져도  │  │             │
    │  안 사라짐   │  │             │
    └─────────────┘  └─────────────┘
```

- **CPU** (Central Processing Unit) - 읽고, 해석하고, 실행하는 부품
- **Main Memory** - 현재 실행 중인 프로그램을 구성하는 데이터와 명령어를 저장
- **Secondary Storage** - 전원 꺼도 안 사라지는 저장소
- **I/O Device** - 키보드, 마우스, 모니터, 프린터

<br/>

💬 보조기억장치와 입출력장치는 CPU 입장에서 정보를 주고받는 방식이 크게 다르지 않아서 ==주변장치(Peripheral Device)==라고 통칭하기도 한다

<br/>

**Bus** - 컴퓨터 부품들이 정보를 주고받는 통로다

그중 System Bus는 위 핵심 부품들을 연결하는 통로다

---

## CPU 안을 열어보면

CPU도 하나의 덩어리가 아니다

```
┌─────────────────────────┐
│          CPU            │
│  ┌─────┐   ┌─────┐      │
│  │ ALU │   │ CU  │      │
│  └─────┘   └─────┘      │
│  ┌──────────────────┐   │
│  │ register register│   │
│  │ register  ...    │   │
│  └──────────────────┘   │
└─────────────────────────┘
```

<br/>

**ALU (Arithmetic and Logic Unit)**

연산을 수행할 회로로 되어 있는 일종의 계산기다

<br/>

**CU (Control Unit)**

명령어를 해석해서 부품을 작동시키는 제어 신호를 보낸다

```
CPU 명령어 실행 -> 메모리/입출력장치를 향해 제어 신호
```

<br/>

**register**

CPU의 데이터/명령어 처리 중간값을 저장하는 ==임시 저장 장치==다

`a + b`를 계산한다면 a, b, 그리고 결과가 잠깐 여기 머문다

<br/>

✨ **여기서 하나 알았다**

메모리는 "CPU 밖에 있는 것"인 줄만 알았는데, CPU 안에도 저장 공간이 있다

그것도 제일 빠른 게

---

## 그래서 내가 짠 코드가 도는 방식은

```
1. 디스크에 있는 jar 를 메모리로 올린다
2. CPU 의 CU 가 메모리에서 명령어를 하나 읽어온다
3. 해석한다
4. ALU 가 연산한다
5. 중간값은 register 에 둔다
6. 결과를 메모리에 쓴다
7. 2번으로 돌아간다
```

이걸 초당 수십억 번 한다

<br/>

❓ 그런데 여기서 저장 공간이 벌써 세 개 나왔다

register, Main Memory, Secondary Storage

메모리가 왤케 많아...

## 메모리가 왤케 많아

## 계층이 있다

저장 장치를 CPU와의 물리적 거리 순으로 세우면 이렇게 된다

```
        register          SRAM
           ↓
      cache memory        SRAM   (L1 / L2 / L3)
           ↓
      Main Memory         DRAM
           ↓
   Secondary Storage      HDD / SSD

아래로 갈수록 CPU와 물리적 거리가 멀어진다
```

<br/>

| | 속도 | 용량 | 가격 |
|---|---|---|---|
| 위 | ==빠름== | 작음 | ==비쌈== |
| 아래 | 느림 | ==큼== | 쌈 |

<br/>

✨ **한 가지로 다 못 만드니까 섞어 쓴다**

전부 register로 만들면 미친 듯이 빠르지만 돈이 감당이 안 되고 용량도 안 나온다

전부 디스크로 만들면 싸지만 CPU가 놀게 된다

---

## SRAM과 DRAM

이름만 보면 뭐가 다른지 모르겠는데 앞글자가 전부다

<br/>

### 💬 Random Access Memory - 왜 랜덤임?

무작위라는 뜻이 아니다

> ==아무 주소나 순서 상관 없이 똑같은 시간에 접근 가능하다==는 뜻

주소만 알면 어디든 곧바로 점프해서 그 위치로 갈 수 있다

<br/>

테이프처럼 앞에서부터 감아야 하는 방식과 반대다

배열의 인덱스 접근이 O(1)인 게 하드웨어 차원에서 보장되는 이유이기도 하다

---

### DRAM - Dynamic

동적인, 즉 ==시간이 지나면 데이터가 사라지는== 메모리다

캐패시터에 전하를 담아두는 방식인데 전하가 계속 새어나간다

<br/>

**아니 뭐 그러면 데이터가 사라지면 뭐 어케...?**

```
전하를 담아두는 시간 : 대략 64ms
```

그래서 새어나가기 전에 메모리 컨트롤러가 리프레시를 시킨다

<br/>

> ==리프레시== : 모든 셀을 주기적으로 다시 읽어서 다시 채워 넣는 것

```
Memory Controller --refresh--> DRAM   (계속 반복)
```

<br/>

⚠️ **그래서 전원이 꺼지면 다 날아간다**

컴퓨터가 꺼지면 전원 공급이 없으니 리프레시를 할 수 없고, 64ms 안에 데이터가 전부 휘발된다

"메모리는 휘발성"이라는 말을 외우고만 있었는데 이런 이유였다

---

### SRAM - Static

정적인, 즉 ==시간이 지나도 데이터가 사라지지 않는== 메모리다

refresh 없이도 상태를 유지할 수 있다

<br/>

**SRAM은 안 없어지니?**

두 개의 회로가 서로 밀어주면서 상태를 유지하는 방식이다

리프레시가 필요 없으니 그만큼 빠르다

<br/>

⚠️ **근데 얘도 전원이 꺼지면 날아간다**

전원 공급이 없으면 회로가 서로 밀어주던 힘이 없어진다

<br/>

정리하면

| | 유지 방식 | refresh | 속도 | 쓰이는 곳 |
|---|---|---|---|---|
| SRAM | 회로가 서로 밀어줌 | 불필요 | 빠름 | register, cache |
| DRAM | 캐패시터 전하 | ==필요== | 느림 | Main Memory |

둘 다 전원이 끊기면 소실된다

---

## 그럼 전원이 꺼져도 남는 건?

보조기억장치다

<br/>

**SSD (Solid State Drive)**

절연막 안에 전자를 가둬둔다

높은 전압으로 전자를 밀어 넣거나 빼면서 저장/수정/삭제를 한다

```
    ┌─────────┐
    │  절연막  │  <- 전자가 나갈 수 없다
    │  [전자]  │
    └─────────┘
```

<br/>

💬 **단순 궁금 - 절연막이 닳으면?**

닳는 시기가 오면 전자가 새어 나가서 내부 데이터가 깨질 수 있다

SSD에 수명이 있다는 게 이 얘기였다

<br/>

**HDD (Hard Disk Drive)**

자석의 방향을 유지하려는 성질을 이용해서 데이터를 보호한다

바꾸려면 더 강한 자기장으로 자석의 방향을 돌려야 한다

---

## 보조기억장치가 오래 걸리는 이유

여기가 재밌었다

<br/>

DRAM은 그냥 전하를 채우면 되는데, 보조기억장치는 ==절연막이나 자기장이 방해를 한다==

전자를 억지로 밀어 넣거나, 자석 방향을 억지로 돌려야 한다

> 저장/수정/삭제 비용이 더 크고 오래 걸린다

<br/>

✨ **"디스크는 느리다"가 물리적인 이유였다**

전원이 꺼져도 데이터를 지키려면 뭔가가 데이터를 붙잡고 있어야 하는데, 그 붙잡는 힘이 곧 바꿀 때의 저항이 된다

<br/>

빠른 것과 안 사라지는 것은 트레이드오프다

그런데도 쓰는 이유는 ==저렴하고 가성비가 있어서==다

---

## 캐시 메모리는 왜 3층인가

CPU와 Main Memory 사이에도 계층이 또 있다

```
CPU ── L1 ── L2 ── L3 ── Main Memory
      가깝고        멀고
      작고 빠름     크고 느림
```

같은 이유의 반복이다

빠른 건 비싸니까 조금만 두고, 자주 쓰는 것부터 가까이 둔다

<br/>

❓ 여기까지가 정적인 구조다

이제 실제로 요청 하나가 들어오면 이 부품들이 어떻게 움직이는지 보고 싶었다

## API 요청 하나가 들어오면 무슨 일이 일어날까?

## 응답을 내보내는 건 누가 하고 있나

API 요청이 네트워크를 타고 들어왔다

앞에서 본 부품 중에 네트워크를 담당하는 게 없었다

<br/>

**NIC (Network Interface Card)**

네트워크 신호를 받고 내보내는 부품이다

그 안에 PHY(Physical layer)가 있어서 전기/광 신호를 다룬다

---

## 들어오는 길

```
네트워크 신호
    ↓
1. PHY 가 신호를 감지
    ↓
2. 신호를 비트로 변환
    ↓
3. DMA 가 메모리의 링버퍼에 데이터를 써넣는다
    ↓
4. 복사가 다 끝나면 CPU 한테 하드웨어 인터럽트
    ↓
5. CPU 가 내가 짠 코드를 실행
   (읽기 / 비교 / 점프 / 더하기 / 쓰기 연산의 조합)
```

<br/>

### 💬 DMA (Direct Memory Access)

여기서 처음 본 물건이었다

NIC가 받은 데이터를 메모리에 옮겨야 하는데, ==CPU를 안 거치고 직접 옮긴다==

<br/>

만약 CPU가 이 복사를 다 했다면?

```
CPU: 1바이트 읽고 -> 메모리에 쓰고 -> 1바이트 읽고 -> 메모리에 쓰고 ...
```

패킷 하나 받는 동안 CPU가 단순 복사만 하고 앉아 있게 된다

<br/>

✨ **그래서 복사는 DMA한테 맡기고, CPU는 다 끝난 뒤에 인터럽트로 통보받는다**

CPU는 그동안 다른 일을 할 수 있다

이게 하드웨어 레벨의 비동기더라

<br/>

`@Async`로 무거운 작업을 딴 스레드에 넘기고 응답을 먼저 주는 거랑 발상이 같다

"오래 걸리는 일은 딴 놈한테 시키고 끝나면 알려달라고 한다"

---

## 나가는 길

```
6. 응답 데이터 결과를 메모리에 올려둠
    ↓
7. OS 에 내보내달라고 요청
    ↓
8. OS -> DMA 컨트롤러
   "이 메모리 영역을 NIC 로 옮겨라"
    ↓
9. 메모리 영역을 NIC 로 복사
    ↓
10. PHY 가 비트를 전기/광 신호로 변환해서 송출
```

<br/>

⚠️ **내 코드가 직접 네트워크에 뭘 쓰는 게 아니다**

```java
return ResponseEntity.ok(response);
```

이 한 줄이 하는 일은 ==메모리에 결과를 올려두는 것==까지다

거기서부터는 OS와 DMA와 NIC의 일이다

<br/>

앞에서 본 502가 여기서 이해됐다

프로세스가 죽으면 7번을 실행할 주체가 사라진다

메모리에 응답이 준비돼 있어도 내보내달라고 말할 놈이 없다

> [[06. 무중단 배포가 무적일까?]]

## 전체 흐름

```
[NIC] 신호 감지 -> 비트 변환
   ↓ DMA
[Memory] 링버퍼
   ↓ 인터럽트
[CPU] 내 코드 실행 (Spring, JVM)
   ↓
[Memory] 응답 데이터
   ↓ OS -> DMA
[NIC] 비트 -> 신호 송출
```

<br/>

"요청이 서버에 도착한다"는 한 줄 안에 이만큼이 있었다

## CPU는 어떻게 여러 일을 동시에 하나?

## 사실 동시에 안 한다

코어 하나는 한 순간에 명령어 하나만 실행한다

동시에 하는 것처럼 보이는 건 아주 빠르게 번갈아 하기 때문이다

<br/>

그럼 번갈아 할 때 하던 일은 어디에 두고 가나

---

## register에 뭐가 들어있길래

CPU 안의 register(SRAM)에는 이런 게 있다

```
PC (Program Counter) : 다음에 실행할 명령어가 메모리 몇 번지에 있는지
범용 레지스터         : 계산 중인 값들 (a + b 라면 a, b, a+b)
SP (Stack Pointer)   : 함수 호출이 쌓이는 스택의 위치
```

<br/>

✨ **PC와 SP가 핵심이다**

PC는 "지금 어디까지 실행했나"고, SP는 "지금 어느 함수 안에 있나"다

이 둘만 있으면 하던 일을 정확히 이어서 할 수 있다

<br/>

💬 SP를 보고 JVM에서 본 Stack이 떠올랐다

메서드 호출 프레임이 쌓이는 그 Stack의 현재 위치를 CPU가 register 하나로 들고 있는 거였다

> [[04. JVM은 뭘 어디에 저장할까?]]

---

## 컨텍스트 스위칭

```
Thread1 [작업 중]
   |
   | 1. 작업 중
   | 2. Timer 가 X ms 마다 interrupt
   ↓
   | 3. 계산 중이던 값들, 스택 위치 등을 TCB 에 복사
   ↓
   | 4. OS Scheduler 가 다음 스레드 차례를 정함
   ↓
   | 5. Thread2 의 TCB 값들을 register 로 복사
   ↓
   | 6. PC 부터 작업 시작
   ↓
Thread2 [작업 중]
```

<br/>

**TCB (Thread Control Block)**

스레드마다 하나씩 있는 백업 공간이다

CPU register 값들을 여기에 통째로 저장해둔다

<br/>

> ==컨텍스트 스위칭== : CPU register에 있는 값들을 전부 메모리에 백업해두고, 다음 스레드의 백업된 register 값을 다시 CPU에 불러오는 작업

---

## 이 시간 동안 CPU는 논다

⚠️ **여기가 핵심이다**

```
[Th1 작업] [C.S] [Th2 작업] [C.S] [Th1 작업] [C.S] ...
             ↑              ↑             ↑
      이 구간엔 내 코드를 하나도 처리하지 못한다
```

<br/>

컨텍스트 스위칭 자체는 아무 일도 하지 않는다

레지스터 값을 옮기는 순수한 관리 비용이다

<br/>

✨ **"스레드를 무작정 늘리면 안 된다"의 이유가 이거였다**

스레드가 많아지면 스위칭 횟수가 늘고, 실제 일하는 시간의 비중이 줄어든다

<br/>

그동안 스레드풀 사이즈 공식을 그냥 외우고 있었는데, 왜 CPU bound 작업에서 코어 수보다 스레드를 많이 두면 손해인지가 이제 보였다

CPU가 계속 계산할 수 있는 상황인데 굳이 끼어들어서 백업/복원만 하게 만드는 거니까

---

## 언제 발생하나

```
1. time slice(quantum) 를 다 사용했을 때
2. I/O 작업을 해야 할 때
3. 다른 리소스를 기다려야 할 때
4. interrupt 가 걸렸을 때
```

<br/>

4번이 앞에서 본 그거다

DMA가 복사를 끝내고 인터럽트를 걸면, CPU는 하던 걸 TCB에 백업하고 인터럽트 처리로 넘어간다

> [[04. API 요청 하나가 들어오면 무슨 일이 일어날까?]]

<br/>

2번도 눈에 띈다

I/O를 기다리는 동안 CPU를 붙잡고 있는 건 낭비니까 자발적으로 넘긴다

I/O bound 작업에서 스레드를 코어 수보다 많이 둬도 되는 이유다

어차피 기다리는 시간이 대부분이라 CPU가 놀고 있다

---

## 근데 스레드끼리랑 프로세스끼리가 다르다더라

같은 컨텍스트 스위칭인데 프로세스 간 전환이 훨씬 비싸다고 한다

<br/>

```
[스레드 간]
커널 모드로 전환
Th1 의 CPU 상태 저장
Th2 의 CPU 상태 로딩

[프로세스 간]
커널 모드로 전환
Th1 의 CPU 상태 저장
Th2 의 CPU 상태 로딩
MMU 를 P2 의 메모리를 보도록 수정   <- 추가
TLB 비움                          <- 추가
```

<br/>

**공통점**은 커널 모드에서 실행되고 CPU register 상태를 교체한다는 것

**차이점**은 스레드끼리는 메모리 영역을 공유하지만, 서로 다른 프로세스는 독립적인 메모리 영역을 갖는다는 것

<br/>

❓ 그래서 MMU랑 TLB가 뭔데 저게 그렇게 비싼가

## 프로세스 스위칭이 왜 더 비쌀까?

## 프로그램은 가짜 주소를 쓴다

프로세스는 각자 독립적인 메모리 영역을 갖는다

정확히는 각 프로세스가 ==자기만의 가상 주소 공간==을 본다

<br/>

프로세스 A도 0번지부터 시작하고, 프로세스 B도 0번지부터 시작한다

근데 물리 메모리에는 0번지가 하나뿐이다

<br/>

그래서 변환해 줄 놈이 필요하다

---

## MMU와 page table

**MMU (Memory Management Unit)**

가상 주소를 물리 주소로 변환하는 하드웨어 디바이스다

```
1. 가상 주소로 접근
        ↓
2. MMU 가 가상 주소를 쪼갠다
   [ 페이지 번호 | 페이지 내 offset ]
        ↓
3. page table 에서 페이지 번호 -> 프레임 번호 변환
        ↓
4. 프레임 번호 + offset = 물리 주소
```

<br/>

**page table**

가상 페이지 번호와 실제 프레임 번호의 대응표다

프로세스마다 하나씩 있다

<br/>

**page hit / page fault**

```
페이지 번호가 page table 에 있다 -> page hit -> 물리 주소 획득
없다 -> disk 에서 가져와서 page table 에 업데이트
```

없으면 디스크까지 갔다 와야 한다

---

## 근데 이게 매번이다

⚠️ **가상 주소 하나 변환하려고 이 짓거리를 매번 해야 한다**

메모리에 접근할 때마다 page table을 읽는데, page table도 메모리에 있다

메모리 한 번 읽으려고 메모리를 두 번 읽는 셈이다

<br/>

✨ **그래서 TLB를 쓴다**

---

## TLB - MMU의 캐시

**TLB (Translation Lookaside Buffer)**

자주 참조되는 Page Table Entry를 저장하는 하드웨어 캐시다

MMU가 사용하는 SRAM이다

```
가상 주소 접근
      ↓
   [ TLB ]  ── TLB Hit ──> 물리 주소 (끝)
      │
   TLB miss
      ↓
   [ MMU ] -> page table -> 프레임 번호
      ↓
   TLB write (다음을 위해 캐싱)
      ↓
   물리 주소
```

<br/>

앞에서 본 캐시 계층이랑 같은 발상이다

자주 쓰는 걸 가까이 두고, 없을 때만 멀리 간다

> [[03. 메모리가 왤케 많아]]

---

## 그래서 왜 비싼가

이제 답이 나온다

<br/>

**스레드 간 전환**

같은 프로세스니까 ==메모리 영역을 공유한다==

가상 주소 체계가 그대로다

MMU도 TLB도 건드릴 게 없다

```
커널 모드 전환 -> register 저장 -> register 로딩
```

<br/>

**프로세스 간 전환**

프로세스끼리는 메모리 영역을 공유하지 않는다

즉 같은 가상 주소가 ==다른 물리 주소==를 가리킨다

```
커널 모드 전환 -> register 저장 -> register 로딩
-> MMU 가 P2 의 page table 을 보도록 수정
-> TLB 를 비움              <- 여기가 진짜 비싼 부분
```

<br/>

⚠️ **TLB를 비우는 게 왜 문제냐면**

TLB에 남아 있는 건 전부 이전 프로세스의 변환 정보다

그대로 두면 P2가 P1의 메모리를 읽어버린다

그래서 비워야 하는데, 비우고 나면 캐시가 텅 빈 상태로 시작한다

<br/>

> 프로세스가 전환된 이후에는 한동안 계속 ==page table walk==를 하게 된다

캐시 미스가 연달아 나면서 그동안 메모리를 두 번씩 읽는다

<br/>

💬 그래서 아예 반대로, 프로세스 컨텍스트 스위칭할 때 TLB를 통째로 날려버리는 구현도 있다

어차피 다 미스 날 거면 관리 비용이라도 아끼자는 쪽이다

---

## 정리

| | register 교체 | MMU 수정 | TLB flush | 이후 성능 |
|---|---|---|---|---|
| 스레드 간 | O | X | X | 그대로 |
| 프로세스 간 | O | ==O== | ==O== | ==한동안 느림== |

<br/>

✨ **비용이 스위칭 순간에만 있는 게 아니었다**

레지스터 몇 개 옮기는 시간보다, ==그 이후에 캐시가 다시 채워질 때까지의 느려짐==이 더 크다

<br/>

"프로세스보다 스레드가 가볍다"를 그냥 외웠는데, 가벼운 이유가 이거였다

메모리를 공유하니까 주소 변환 캐시를 버릴 필요가 없다

<br/>

❓ 그럼 여기까지 알고 나면 뭐가 달라지나

## 내 기준

## 핵심 흐름

```
[부품]
CPU (ALU 계산 / CU 제어 / register 임시저장)
Main Memory (실행 중인 것, 휘발성)
Secondary Storage (전원 꺼져도 유지)
I/O Device
        └─ 다 System Bus 로 연결

[저장 계층]  CPU와 가까울수록 빠르고 작고 비싸다
register     SRAM   회로가 서로 밀어줌, refresh 불필요
cache L1/L2/L3  SRAM
Main Memory  DRAM   캐패시터 전하, 64ms 마다 refresh 필요
HDD / SSD           자기장 / 절연막 -> 그래서 느리다

[요청 하나의 여정]
NIC(PHY) 신호 감지 -> 비트 변환
   ↓ DMA 가 직접 복사 (CPU 안 거침)
Memory 링버퍼
   ↓ 하드웨어 인터럽트
CPU 가 내 코드 실행
   ↓
Memory 에 응답 올려둠
   ↓ OS -> DMA
NIC -> 신호 송출

[컨텍스트 스위칭]
Timer interrupt -> register 값을 TCB 에 백업
-> Scheduler 가 다음 스레드 선택 -> TCB 를 register 로 복원 -> PC 부터 재개
이 구간엔 내 코드가 하나도 처리되지 않는다

발생 조건: time slice 소진 / I/O / 리소스 대기 / interrupt

[스레드 vs 프로세스]
스레드 간   : register 교체만
프로세스 간 : register 교체 + MMU 수정 + TLB flush
             -> 이후 한동안 page table walk 반복 (진짜 비용은 여기)
```

---

> ==하드웨어의 거의 모든 설계가 "빠른 건 비싸니까 자주 쓰는 것만 가까이 둔다" 하나로 설명됐다==
> register / L1~L3 / Main Memory / Disk 도, MMU 앞의 TLB 도, 전부 같은 문제의 같은 답이었다

<br/>

✨ **외우고 있던 것 세 개가 이유를 갖게 됐다**

"메모리는 휘발성이다" -> 전원이 끊기면 리프레시가 멈춰서 64ms 안에 날아간다

"디스크는 느리다" -> 전원 없이 데이터를 붙잡는 힘이 곧 바꿀 때의 저항이 된다

"프로세스보다 스레드가 가볍다" -> 메모리를 공유해서 주소 변환 캐시를 버릴 필요가 없다

<br/>

✨ **스레드풀 사이즈 공식이 이제 공식이 아니게 됐다**

```
CPU bound  -> 코어 수 근처
I/O bound  -> 더 많이
```

이걸 그냥 외우고 있었는데, 컨텍스트 스위칭 구간엔 CPU가 내 코드를 하나도 처리 못 한다는 걸 보고 나니 당연한 얘기였다

CPU가 계속 계산할 수 있는 상황이면 끼어들기가 손해고, 어차피 I/O를 기다리는 상황이면 놀리느니 넘기는 게 이득이다

<br/>

⚠️ **그래도 아직 숫자를 못 정한다**

원리는 알겠는데 "그래서 우리 서버는 몇으로 둘까"는 여전히 측정 없이는 못 정한다

이건 이론이 아니라 실측의 영역이더라

---

❓ 실전 체크리스트

- 스레드풀을 늘려도 처리량이 안 오른다 -> 컨텍스트 스위칭 비용이 이득을 잡아먹는 구간인지 본다
- CPU 사용률은 높은데 일이 안 된다 -> sys 시간(커널 모드) 비중을 본다, 스위칭 자체가 CPU를 쓴다
- 멀티 프로세스로 띄울지 멀티 스레드로 띄울지 -> 메모리 격리가 꼭 필요한 게 아니면 스레드가 싸다
- I/O 대기가 많은 작업이다 -> 스레드를 코어 수보다 늘려도 된다 (어차피 CPU가 논다)
- 디스크 접근이 병목이다 -> 캐시 계층을 하나 더 두는 게 정석적인 답이다
- 응답이 준비됐는데 사용자한테 안 갔다 -> 내 코드는 메모리에 올려두는 데까지만 한다, 그 뒤는 OS/DMA/NIC다

---

❓ 아직 안 풀린 것

- **프로세스 간 스위칭에서 TCB는 어떻게 되나** - register 값 백업은 TCB에 남는다고 봤는데, 프로세스가 바뀌어도 그 정보가 유효한지(어느 주소 공간 기준인지)가 아직 안 잡힌다
- **캐시 라인과 false sharing** - L1~L3가 있다는 것까지만 봤고, 여러 코어가 같은 캐시 라인을 건드릴 때 생기는 문제는 아직 안 봤다
- **DMA와 zero-copy** - DMA가 CPU를 안 거친다는 건 알았는데, 그럼 커널 버퍼와 유저 버퍼 사이의 복사는 여전히 남는 건지
