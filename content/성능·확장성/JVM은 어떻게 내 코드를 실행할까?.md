## 발단

스터디에서 JVM 주제를 잡았다

처음엔 별 생각이 없었다

`java -jar`로 서버를 띄우고, 힙이 부족하면 `-Xmx`를 늘리고, GC 로그는 문제 생겼을 때만 열어봤다

그런데 완료 기준을 적어놓고 보니 하나도 제대로 답할 수 없었다

```
- JVM 메모리 구조 (Heap / Stack / Metaspace / Code Cache) 각 영역에 뭐가 올라가는지
- GC 동작 원리 - Minor GC / Major GC 차이, Eden -> Survivor -> Old 이동 기준
- GC 알고리즘 비교 (G1GC vs ZGC), Spring Boot 기본값이 G1GC인 이유
- STW(Stop-The-World)가 뭔지, 길어지면 어떤 증상이 나타나는지
- OOM 종류별 원인 구분 (Heap OOM / Metaspace OOM / GC Overhead Limit)
- JIT 컴파일러가 뭔지, Warm-up 시간 동안 성능이 낮은 이유
```

특히 걸린 게 두 개였다

"자바는 컴파일 언어인가 인터프리터 언어인가"에 대답을 못 했고, 새로 뜬 서버에 로드밸런서가 트래픽을 조금씩 흘려보내는 이유를 설명하지 못했다

둘 다 JVM 안에서 벌어지는 일인데 나는 JVM을 그냥 "자바 돌려주는 것"으로만 알고 있었다

❓ JVM은 대체 뭐고, 왜 있어야 하는 걸까

## JVM은 뭐고 왜 필요할까?

## 컴파일은 왜 하나?

CPU는 자바 코드를 못 읽는다

CPU가 이해하는 건 기계어뿐이고, 컴파일은 내가 쓴 언어를 CPU가 이해할 수 있는 언어로 바꾸는 작업이다

<br/>

여기서 갈림길이 생긴다

기계어는 CPU와 OS마다 다르기 때문이다

---

## JVM이 없으면 어떻게 되나?

C 같은 언어는 소스코드를 플랫폼별 기계어로 각각 변환한다

```
              [배포 시점]
소스코드 --compile--> 기계어 --> CPU (Mac)
소스코드 --compile--> 기계어 --> CPU (Windows)
소스코드 --compile--> 기계어 --> CPU (Linux)
```

플랫폼이 늘어날 때마다 그 플랫폼에서 다시 빌드해야 한다

배포 시점에 이미 대상이 정해져 버린다

---

## JVM은 뭘 바꿨나?

✨ **컴파일 결과물을 기계어가 아니라 바이트코드로 만들었다**

```
        [배포 시점]                    [실행 시점]
.java --javac--> 바이트코드(.class) --> JVM --> CPU (Mac)
                        |
                        +------------> JVM --> CPU (Windows)
                        |
                        +------------> JVM --> CPU (Linux)
```

바이트코드는 어떤 CPU의 기계어도 아니다

JVM이라는 가상 머신 하나만을 위한 명령어 집합이다

<br/>

실제로 만들어지는 결과물을 보면 이렇다

```bash
$ javac Hello.java     # Hello.class 생성
$ javap -c Hello       # 바이트코드 열어보기
```

```
public static void main(java.lang.String[]);
  Code:
     0: getstatic     #2   // System.out
     3: ldc           #3   // "hello"
     5: invokevirtual #4   // println
     8: return
```

`getstatic`, `invokevirtual` 같은 명령어는 x86에도 ARM에도 없는 명령어다

JVM만 아는 명령어고, ==바이트코드를 해당 플랫폼의 기계어로 해석하고 실행하는 것==이 JVM의 일이다

<br/>

그래서 빌드는 한 번만 하고, 플랫폼별 차이는 실행 시점에 그 플랫폼의 JVM이 흡수한다

내가 로컬 Mac에서 만든 jar가 리눅스 서버에서 그대로 도는 이유다

---

## 그럼 컴파일이 두 번인가?

여기서 이상해졌다

javac가 이미 컴파일을 했는데, 바이트코드를 기계어로 바꾸는 것도 컴파일이다

```
javac : .java  -> .class      (빌드 시점, 딱 한 번)
JIT   : .class -> 네이티브 기계어  (실행 시점, 계속)
```

❓ 실행하는 내내 컴파일을 계속 한다는 게 무슨 소리일까

## 컴파일이 두 번 일어난다고?

## 왜 처음부터 다 컴파일하지 않나?

JVM이 뜰 때 바이트코드 전체를 기계어로 미리 바꿔두면 편할 것 같았다

그런데 그렇게 하지 않는다

<br/>

⚠️ **컴파일은 공짜가 아니다**

컴파일 자체가 CPU를 쓰고, 결과물인 기계어가 메모리를 차지한다

한 번도 호출되지 않을 메서드까지 전부 컴파일하면 그 비용은 그냥 버려진다

<br/>

그래서 JVM은 일단 ==인터프리터==로 시작한다

바이트코드를 한 줄씩 해석해서 실행하고 버린다

대신 메서드가 호출될 때마다 카운트를 올린다

```
api 요청 -> 인터프리터가 바이트코드 한 줄씩 해석 -> 실행 후 버림
                            |
                         count++
```

---

## 그럼 언제 컴파일하나?

호출 횟수가 임계치(`CompileThreshold`, 기본 수천 회 단위)를 넘으면 그때 판단이 바뀐다

> 이 메서드는 앞으로도 자주 불릴 것이다 -> 기계어로 만들어둘 값어치가 있다

<br/>

JVM은 그 메서드를 통째로 컴파일 큐에 넣는다

```
count <  CompileThreshold  -> 계속 인터프리터
count >= CompileThreshold  -> 컴파일 큐 -> C1 컴파일러
```

컴파일은 별도 스레드에서 돈다

✨ **컴파일이 진행되는 동안 들어온 요청은 계속 인터프리터로 처리된다**

그래서 JIT 컴파일 때문에 요청이 멈추는 일은 없다

---

## C1과 C2는 뭐가 다른가?

컴파일러가 하나가 아니다

```
                          [사용량이 적음]
인터프리터 --임계치--> C1 컴파일러 --계속 자주 사용--> C2 컴파일러
                          |                              |
                          v                              v
                    profiled nmethods            non-profiled nmethods
                          \____________ Code Cache ____________/
```

<br/>

C1은 빠르게 컴파일한다

대신 실행되면서 프로파일링 정보를 계속 수집한다 (어떤 분기를 주로 타는지, 어떤 타입이 주로 들어오는지)

<br/>

C2는 그 실측 데이터를 받아서 공격적으로 다시 컴파일한다

컴파일 자체는 느리지만 결과물이 훨씬 빠르다

```java
public int calc(Shape s) {
    return s.area();   // 인터페이스 호출
}
```

C2는 프로파일링 결과 여기 들어온 게 100% `Circle`이었다면, 가상 호출을 없애고 `Circle.area()` 구현체를 직접 부르거나 아예 인라인해 버린다

<br/>

⚠️ **이건 낙관적 추측이다**

그러다 `Square`가 들어오면 추측이 깨진다

이때는 컴파일된 코드를 버리고 인터프리터로 되돌아간다 (deoptimization)

<br/>

이렇게 만들어진 기계어가 쌓이는 곳이 Code Cache다

C1 결과물은 프로파일링 코드가 박혀 있어서 profiled nmethods, C2 결과물은 그게 없어서 non-profiled nmethods로 구분해 둔다

---

## warm-up이 이거였나?

> ==warm-up== : JVM이 막 시작된 시점부터, 자주 쓰이는 코드 경로들이 JIT에 의해 최적화된 기계어로 다 전환될 때까지의 과도기 구간

이 구간에서 서버는 이런 상태다

```
- 대부분의 코드가 아직 인터프리터로 실행된다
- 뭐가 자주 호출되는지 카운팅 중이다
- C2로 승격된 완전 최적화 코드는 거의 없다
```

<br/>

같은 코드, 같은 서버인데 방금 뜬 서버가 느린 이유가 여기 있다

✨ **로드밸런서가 새로 뜬 인스턴스에 트래픽을 조금씩만 흘려보내는 이유 중 하나다**

(다만 실제 배포에서 이건 커넥션 풀 예열이나 캐시 워밍에 비하면 비중이 작은 편이다)

<br/>

이게 Blue-Green처럼 한 번에 스위칭하는 방식의 약점이기도 하다

-> [[04. 그래서 어떤 전략들이 있나?]]

<br/>

그래서 성능 테스트할 때 처음 몇 초의 응답 시간을 그대로 지표로 쓰면 안 된다

warm-up 구간을 버리고 측정해야 한다

## 자바는 컴파일 언어인가 인터프리터 언어인가

```
javac 로 컴파일한다        -> 컴파일 언어
바이트코드를 해석해 실행한다 -> 인터프리터 언어
JIT 로 다시 컴파일한다      -> 컴파일 언어
```

셋 다 맞다

정확히는 ==컴파일 후 인터프리터로 시작해서, 뜨거운 코드만 다시 컴파일하는 하이브리드==다

❓ 그럼 그렇게 만들어진 기계어랑 객체들은 각각 어디에 저장되는 걸까

## JVM은 뭘 어디에 저장할까?

## 영역이 왜 나뉘어 있나?

JVM 메모리는 크게 네 덩어리다

```
JVM Memory
├── Heap        : new 로 만든 객체
├── Stack       : 메서드 호출 프레임
├── Metaspace   : 클래스 메타데이터
└── Code Cache  : JIT가 만든 기계어
```

나뉜 기준은 두 가지다

==언제 사라지는가==, ==누가 공유하는가==

---

## Stack - 메서드가 끝나면 사라진다

```java
public int sum(int a, int b) {
    int result = a + b;
    return result;
}
```

`a`, `b`, `result`는 Stack에 올라간다

- 메서드 호출 프레임 (지역 변수, 매개변수, 연산 중간값)
- ==스레드마다 하나씩== 따로 갖는다
- LIFO(Last In First Out), 메서드가 끝나면 프레임째로 즉시 사라진다

<br/>

정리해 줄 사람이 필요 없다

호출이 끝나는 순간이 곧 수명이 끝나는 순간이기 때문이다

<br/>

💬 이 Stack의 현재 위치를 CPU는 register 하나(SP)로 들고 있다

컨텍스트 스위칭 때 백업되는 값 중 하나가 그거다

-> [[05. CPU는 어떻게 여러 일을 동시에 하나?]]

---

## Heap - 스코프랑 상관이 없다

```java
public Member create() {
    Member member = new Member("구진");   // 객체는 Heap, member 참조는 Stack
    return member;                        // 메서드는 끝나지만 객체는 안 죽는다
}
```

- `new`로 만든 ==모든 객체==
- ==모든 스레드가 공유==한다
- 함수 호출 스코프와 무관하다

<br/>

✨ **그래서 GC가 필요한 건 Heap이다**

메서드가 끝나도 객체는 남고, 누가 아직 쓰고 있는지는 실행해 봐야만 알 수 있다

---

## Metaspace - 클래스 정보가 산다

- 클래스 메타데이터 (클래스 구조, 메서드 정보, static 필드)
- 모든 스레드가 공유하고, ==Heap 밖 네이티브 메모리==에 별도로 할당된다
- Java 8부터 Heap 밖으로 분리됐다 (그전에는 PermGen)

<br/>

⚠️ **Spring은 이 영역을 많이 쓴다**

리플렉션과 프록시를 많이 쓰기 때문에 로드하는 클래스 수 자체가 많다

`@Transactional` 하나 붙일 때마다 CGLIB 프록시 클래스가 런타임에 생성되고, 그게 다 Metaspace로 간다

<br/>

Heap이 넉넉한데 죽는 경우가 있는데, Metaspace가 따로 터지는 경우다

---

## Code Cache - 기계어가 사는 곳

- JIT(C1/C2)이 바이트코드를 컴파일해서 만든 실제 기계어
- 모든 스레드가 공유한다
- ==실행 가능 권한이 붙은 유일한 메모리 영역==이다

<br/>

다른 영역은 데이터를 담을 뿐이지만, 여기 있는 내용물은 CPU가 그대로 실행한다

Code Cache가 꽉 차면 JIT 컴파일이 멈추고 전부 인터프리터로 돌아간다

터지지는 않는데 갑자기 느려지는 형태로 나타난다

---

## 정리하면

| 영역 | 담기는 것 | 공유 | 정리 방식 |
|------|-----------|------|-----------|
| Stack | 지역 변수, 매개변수 | 스레드별 | 메서드 종료 시 자동 |
| Heap | new로 만든 객체 | 전체 공유 | ==GC== |
| Metaspace | 클래스 메타데이터 | 전체 공유 | 클래스 언로드 시 |
| Code Cache | JIT 컴파일 기계어 | 전체 공유 | 코드 무효화 시 |

<br/>

Heap만 정리 시점이 정해져 있지 않다

❓ 그럼 GC는 안 쓰는 객체를 어떻게 골라낼까

## GC는 Heap을 어떻게 정리할까?

## 안 쓰는 객체를 어떻게 아나?

Heap에는 `new`로 만든 객체가 계속 쌓인다

API가 호출될 때마다 쌓이기만 하면 언젠가 터진다

<br/>

GC는 안 쓰는 객체를 찾아서 치워준다

그런데 "안 쓴다"의 기준이 뭘까

<br/>

✨ **GC Root - 쓰인다/안 쓰인다의 출발점**

메서드 호출 정보가 올라가는 Stack이 대표적인 GC Root다

지금 실행 중인 메서드의 지역 변수가 그 객체를 참조하고 있는가, 거기서 시작한다

```
Stack (GC Root)
  └─ member ──> Member 객체        ✓ mark
                   └─ profile ──> Profile 객체   ✓ mark

                     Order 객체    ✗ 아무도 안 가리킴
```

Root에서 참조를 따라가면서 도달 가능한 객체를 전부 mark한다

그리고 mark가 안 된 객체, 즉 ==GC Root에서 도달할 수 없는 객체==를 메모리에서 지운다

이게 Mark-and-Sweep이다

<br/>

여기서 참조 카운팅과 다른 점이 나온다

```java
a.next = b;
b.next = a;   // 서로 참조 중, 하지만 Root에서 도달 불가
```

서로를 참조하고 있어도 Root에서 못 닿으면 그냥 쓰레기다

순환 참조가 저절로 해결된다

---

## 매번 전부 스캔하면 느리지 않나?

Heap이 4GB면 그 안의 객체를 전부 훑어야 한다

너무 오래 걸린다

<br/>

여기서 GC는 통계에 기댄다

> ==Generational Hypothesis(세대 가설)== : 대부분의 객체는 생성된 지 얼마 안 돼서 죽는다

```java
public List<PostResponse> findAll() {
    List<Post> posts = repository.findAll();        // 응답 만들고 나면 끝
    return posts.stream()
        .map(PostResponse::from)                    // 중간 객체들도 바로 죽음
        .toList();
}
```

요청 하나 처리하면서 만든 객체 대부분은 응답이 나가는 순간 쓸모없어진다

반대로 살아남은 객체(싱글톤 빈, 캐시)는 앞으로도 계속 살아남는다

<br/>

✨ **그럼 새로 만들어진 객체들만 자주 보면 된다**

Heap을 세대로 나누는 이유다

---

## Young Generation에서 벌어지는 일

Young 영역은 Eden 하나와 Survivor 둘로 나뉜다

```
[ Young Generation ]          [ Old Generation ]
Eden   S0   S1
```

<br/>

**1. 새 객체는 Eden에 들어간다**

```
Eden [ new new new new ]   S0 [ ]   S1 [ ]
```

<br/>

**2. Eden이 꽉 차면 Minor GC가 돈다**

Eden에서 살아남은 객체만 비어 있는 Survivor로 ==복사==하고, Eden은 통째로 비운다

살아남은 게 몇 개 없으니 복사할 양도 적다 (Copying GC)

```
Eden [        ]   S0 [ 생존 age=1 ]   S1 [ ]
```

<br/>

**3. 다음 Minor GC부터는 Survivor끼리도 옮긴다**

Eden 생존자 + S0 생존자를 S1로 모으고, Eden과 S0를 비운다

옮겨질 때마다 객체의 age가 1씩 올라간다

```
Eden [ ]   S0 [ ]   S1 [ age=2 ]
     -> 다음 번엔 반대로 S1 -> S0
```

Survivor 둘 중 ==하나는 항상 비어 있다==

복사 대상 공간이 늘 필요하기 때문이고, 복사하면서 자연스럽게 압축까지 된다

<br/>

**4. age가 임계치를 넘으면 Old로 승격된다**

```
age < 15  -> Survivor에 계속 머무름
age >= 15 -> Old Generation 으로 이동
```

(기본값 15, `-XX:MaxTenuringThreshold`)

여러 번의 Minor GC를 버텼다는 건 앞으로도 오래 살 확률이 높다는 뜻이다

Young에서 계속 검사할 이유가 없으니 Old로 보낸다

---

## Minor GC와 Major GC

```
Minor GC : Young 영역만 정리, 자주 발생, 짧게 끝남
Major GC : Old 영역까지 정리, 드물게 발생, 오래 걸림
```

<br/>

Old에는 오래 살아남은 객체들이 있으니 죽은 객체 비율이 낮다

Copying이 비효율적이라 mark 후 정리하고 압축하는 방식을 쓰고, 대상 크기 자체도 크다

그래서 Major GC(Full GC)는 훨씬 오래 걸린다

<br/>

❓ 그런데 정리하려면 애플리케이션을 멈춰야 한다고 한다

왜 멈춰야 하고, 그 시간을 어떻게 줄일까

## STW를 어떻게 줄일까?

## 왜 멈춰야 하나?

GC가 객체를 다른 영역으로 옮기는 작업(evacuation)을 하는 동안, GC 스레드를 제외한 ==애플리케이션의 모든 스레드가 완전히 멈춘다==

이게 Stop-The-World다

<br/>

멈추지 않으면 이런 일이 생긴다

```
GC 스레드 : Order 객체를 mark 중... 아무도 참조 안 하네, 지워야지
App 스레드 : (그 사이) cart.order = new Order()  <- 방금 참조 생김
GC 스레드 : 삭제
```

⚠️ **GC가 보는 객체 그래프가 스캔 도중에 흔들린다**

살아있는 객체가 지워질 수 있다

객체를 옮기는 중이라면 더 심각하다

애플리케이션은 옛날 주소를 들고 있는데 객체는 이미 다른 곳으로 이사 가 버린 상태가 된다

---

## 멈추면 뭐가 문제인가?

STW가 길어지면 이런 증상이 나온다

```
- 사용자 요청 타임아웃 (당연히)
- 헬스체크 응답 지연
```

<br/>

두 번째가 은근히 무섭다

헬스체크에 응답이 없으면 오케스트레이터는 그 인스턴스가 죽었다고 판단한다

⚠️ **GC 중이었을 뿐인데 프로세스를 재시작시켜 버린다**

재시작하면 warm-up부터 다시 시작이고, 그 트래픽이 다른 인스턴스로 몰리면서 거기서도 GC가 터진다

배포 중에 이게 터지면 연쇄적으로 무너진다

-> [[06. 무중단 배포가 무적일까?]]

<br/>

그래서 GC 알고리즘의 역사는 ==STW를 어떻게 줄이고, 어떻게 예측 가능하게 만드느냐==의 역사였다

---

## CMS는 왜 밀려났나?

G1 이전에는 CMS(Concurrent Mark Sweep)를 썼다

이름 그대로 애플리케이션을 멈추지 않고 동시에 mark를 진행하는 게 핵심이었다

<br/>

⚠️ **정리는 하는데 압축을 안 했다**

```
Heap [■□■□□■□■■□□■□]   <- 죽은 객체 자리가 구멍으로 남음
```

메모리는 분명히 남아 있는데 연속된 공간이 없다

큰 배열 하나를 할당하려는 순간 자리가 없어서 Full GC가 터진다

압축을 하려면 결국 길게 멈춰야 했고, 예측이 안 됐다

---

## G1은 뭘 바꿨나?

✨ **Heap을 region이라는 작은 조각으로 나누고, 각 region에 역할을 붙였다 뗐다 한다**

```
Heap [E][E][S][O][E][O][ ][O][E][ ][O][S]
      E = Eden, S = Survivor, O = Old
```

Young과 Old가 물리적으로 붙어 있지 않다

Young GC가 한 바퀴 돌면 기존 E, S region은 통째로 비고, 비어 있는 region에 역할이 다시 부여된다

<br/>

**여기서 두 가지가 해결된다**

작은 region 단위로 옮기니 STW 시간이 짧아지고, 몇 개를 정리할지 고르는 방식이라 ==멈추는 시간을 예측할 수 있다==

`-XX:MaxGCPauseMillis=200`처럼 목표를 주면, G1이 그 시간 안에 처리 가능한 만큼만 region을 고른다

<br/>

**Old가 계속 늘어나면?**

Young GC만 돌면 Old region은 쌓이기만 한다

```
Heap [O][O][O][O][E][O][S][E][O][O]   <- 슬슬 비워야 한다
```

전체 힙 사용량이 45%(`InitiatingHeapOccupancyPercent` 기본값)를 넘으면 G1은 동시 마킹을 시작한다

애플리케이션을 돌리면서 Old region마다 죽은 객체 비율을 조사한다

<br/>

그다음이 이름의 유래다

> Old region 중 ==쓰레기 비율이 가장 높은 것 몇 개==를 골라서 Young region과 함께 청소한다

Garbage First

적은 비용으로 가장 많은 공간을 회수하는 region부터 처리한다

<br/>

그리고 옮기면서 정리하기 때문에 CMS의 단편화 문제도 같이 풀린다

Spring Boot 기본값이 G1인 이유가 이거다

대부분의 웹 애플리케이션은 짧게 죽는 객체가 많고, 응답 시간의 상한을 예측할 수 있는 게 평균 처리량보다 중요하다

---

## ZGC는 어디까지 갔나?

G1도 evacuation 순간에는 멈춘다

아무리 짧아도 힙이 수십 GB로 커지면 그 시간도 무시할 수 없다

<br/>

✨ **ZGC는 살아있는 객체를 옮기는 작업까지 concurrent로 처리한다**

멈추는 걸 아예 없애진 못하지만 힙 크기와 무관하게 ms 이하로 유지한다

<br/>

**어떻게?**

mark 여부와 이사 여부를 객체가 아니라 ==참조 포인터 자체에 상태값으로== 박아 넣는다 (colored pointer)

64비트 주소에서 안 쓰는 비트를 메타데이터로 쓰는 방식이다

<br/>

그리고 참조를 읽을 때마다 Load Barrier를 거치게 한다

```
                 [옛날 region]              [새 region]
요청 --> 옛날 참조로 접근                     복사된 객체
             |                                  ^
             v                                  |
        Load Barrier  --2. 최신 주소 조회-->  Forwarding Table
        (JIT가 심어둠)  <--- 새 주소 반환 ---   (region마다 하나)
             |
        3. 참조의 주소와 mark 상태를 최신으로 업데이트
```

1. 포인터의 상태값이 옛날 상태면 Load Barrier가 끼어든다
2. Forwarding Table에서 최신 주소를 조회한다
3. 참조를 최신 주소로 바꿔 끼우고 그대로 진행한다

애플리케이션 입장에서는 그냥 필드 하나 읽은 것이고, 이사는 그 틈에 조금씩 진행된다

<br/>

### 💬 Load Barrier는 JIT가 심는다

내가 쓴 코드에는 없는 동작이다

JIT가 바이트코드를 기계어로 컴파일할 때 참조를 읽는 지점마다 검사 코드를 끼워 넣는다

앞에서 본 Code Cache의 기계어가 이렇게 GC와 맞물린다

---

## 그럼 왜 ZGC를 안 쓰나?

⚠️ **공짜가 아니다**

```
- 참조를 읽을 때마다 Load Barrier를 거쳐서 CPU 오버헤드가 붙는다
- 옮기는 중인 객체를 동시에 다루려면 메모리 공간이 더 필요하다
```

<br/>

STW를 줄인 대가로 처리량과 메모리를 내줬다

힙이 몇 GB 수준이고 G1의 pause가 이미 목표치 안에 들어온다면, 굳이 그 대가를 낼 이유가 없다

<br/>

> ==힙이 수십 GB 이상이고 p99 지연이 중요하면 ZGC, 그 외에는 G1==

---

❓ 여기까지 오니 남는 질문이 있다

메모리가 결국 터지면 무슨 일이 생길까

## 내 기준

## 핵심 흐름

```
[배포 시점]
.java --javac--> 바이트코드(.class)          한 번만, 플랫폼 무관

[실행 시점]
바이트코드 --> 인터프리터로 시작 (한 줄씩 해석, count++)
                    |
              count >= CompileThreshold
                    v
              C1 컴파일 (빠름, 프로파일링 수집)
                    |
              계속 자주 호출됨
                    v
              C2 컴파일 (느림, 실측 기반 공격적 최적화) --> Code Cache
              추측이 빗나가면 --> 인터프리터로 복귀

[메모리]
Stack      : 스레드별, 메서드 끝나면 즉시 소멸
Heap       : 전체 공유, 수명이 안 정해짐 --> GC 대상
Metaspace  : 클래스 메타데이터, Heap 밖 (Spring이 많이 씀)
Code Cache : JIT 결과 기계어, 실행 권한이 붙은 유일한 영역

[Heap 정리]
GC Root(Stack 등)에서 도달 가능 --> mark
도달 불가 --> sweep
        |
  전부 스캔은 비싸다 --> 세대 가설
        v
Eden --Minor GC--> Survivor(age++) --age 15--> Old

[STW 줄이기]
CMS : concurrent mark, 압축 X --> 단편화
G1  : region 단위 --> pause 예측 가능, 쓰레기 많은 region 우선
ZGC : colored pointer + Load Barrier --> evacuation까지 concurrent
```

---

> ==JVM은 "일단 대충 실행하고, 자주 쓰이는 것만 제대로 최적화한다"는 원칙 하나로 움직인다==
> 컴파일도 그렇고(인터프리터 -> C1 -> C2), GC도 그렇다(전체 스캔 대신 새 객체만 자주)
> 성능 문제를 만나면 "지금 이게 뜨거운 경로로 인정받았나"를 먼저 묻게 됐다

<br/>

✨ **모르는 걸 두 개 설명할 수 있게 됐다**

방금 뜬 서버가 느린 이유 - 아직 인터프리터로 돌고 있어서다

지표를 볼 때 첫 구간을 버려야 하는 이유도 같다

<br/>

⚠️ **하지만 아직 튜닝은 못 한다**

옵션 이름과 기본값은 알게 됐지만, 실제 서비스의 GC 로그를 읽고 어떤 값을 어떻게 조정할지는 해본 적이 없다

숫자를 외운 것과 판단할 수 있는 건 다르다

---

❓ 실전 체크리스트

- 응답이 느리다 -> 방금 배포한 서버인가 (warm-up), 아니면 계속 느린가 (GC)
- Heap은 충분한데 OOM이 났다 -> Metaspace를 의심한다 (Spring 프록시/리플렉션으로 클래스가 계속 늘어나는가)
- 갑자기 전체가 느려졌는데 GC 로그는 깨끗하다 -> Code Cache가 꽉 차서 JIT가 멈췄는지 본다
- 헬스체크 실패로 재시작이 반복된다 -> STW 시간과 헬스체크 타임아웃을 같이 본다
- GC 옵션을 바꾸고 싶다 -> 힙이 수십 GB가 아니고 pause가 목표 안이면 G1을 그대로 둔다
- 성능 측정을 한다 -> warm-up 구간을 버리고 측정한다

---

❓ 아직 안 풀린 것

- **OOM 종류별 구분** - Heap OOM / Metaspace OOM / GC Overhead Limit Exceeded 세 개를 실제 스택트레이스로 구분해 본 적이 없다 (다음 회차 숙제)
- **G1의 내부 단편화** - 외부 단편화는 region 단위 압축으로 풀었는데, region 안쪽에 남는 자투리와 region 크기를 넘는 거대 객체(humongous object)는 어떻게 되는지 아직 모른다
- **GC 로그 읽기** - 이론은 정리했지만 실제 로그 포맷을 보고 원인을 짚어내는 건 별개다

<br/>

바리바리에 부하를 걸어보고 GC 로그를 직접 떠서 이어서 볼 예정이다
