노선을 12개 더 늘릴 예정이었는데, 평가가 끝난 결과도 RDS에 계속 쌓이고 있었습니다. 대기 중인 평가와 완료 이력을 나눠 조회 비용은 줄였지만, 완료 결과를 계속 보관하면 테이블과 인덱스는 다시 커집니다.

그래서 집계가 끝난 과거 평가 결과를 S3로 옮기고 RDS에서 삭제하기로 했습니다.

처음에는 파일 업로드가 성공하면 DB 원본을 지워도 된다고 생각할 수 있습니다. 근데 이 데이터는 과거 통계를 다시 계산할 때 읽고, 이미 끝난 평가가 다시 대기로 등록되는 것도 막고 있었습니다. **보관 위치만 옮기는 작업이 아니라 읽기 경로와 완료 판정까지 같이 바꿔야 했습니다.**

## 어떤 데이터가 어디까지 이동하나

연어버스는 차량 관측을 저장하고, 관측 하나에서 앞쪽 정류장의 좌석을 예보합니다. 차량이 실제로 정류장에 도착하면 예보와 실제 좌석을 비교해 평가 결과를 만듭니다.

이번에 S3로 옮기는 것은 조건을 만족한 완료 평가 결과입니다. 차량 관측과 예보 원본은 RDS에 그대로 남깁니다. 사용자 화면도 S3를 직접 조회하지 않습니다.

![수집, 예보, 정산, 집계, 이관에서 RDS와 S3 사이의 데이터 흐름](assets/salmonbus-portfolio/06-sal175-data-flow.png)

삭제 대상은 다음 조건을 모두 만족해야 합니다.

- 한국 시간 기준 오늘 이전에 평가가 끝남
- 집계가 끝남
- 미처리 작업이나 재집계가 남아 있지 않음
- 도착 시각이 있다면 도착도 오늘 이전임

오늘 자료까지 바로 옮기면 품질 판정이 바뀌었을 때 통계를 다시 계산하는 경로가 복잡해집니다. 그래서 처리 완료 여부와 다시 읽을 가능성을 함께 확인했습니다.

## S3 저장 성공만 믿지 않았다

업로드 요청이 성공했다는 사실만으로는 파일 내용이 DB 원본과 같다고 볼 수 없습니다.

1. 이관할 대상을 짧은 DB 트랜잭션에서 예약
2. 원본과 검증 정보를 S3에 저장
3. 저장한 파일을 다시 내려받음
4. 건수와 SHA-256, 원본, 품질 상태, 소유권을 비교
5. 삭제 직전에 현재 원본과 처리 상태를 다시 확인
6. DB 원본 삭제와 삭제 완료 기록을 같은 트랜잭션으로 커밋

S3 통신을 기다리는 동안 DB 트랜잭션을 열어두지 않았습니다. 검증이나 재확인 중 하나라도 실패하면 원본은 RDS에 남습니다.

![S3 재다운로드 검증과 DB 원본 삭제 전 재확인 흐름](assets/salmonbus-portfolio/07-sal175-safe-deletion.png)

원본 삭제와 완료 기록을 같은 트랜잭션으로 처리한 이유도 같습니다. 삭제만 되고 완료 기록이 남지 않으면 같은 평가가 다시 대기로 등록될 수 있습니다. 반대로 완료 기록만 있고 원본이나 S3 파일이 올바르지 않으면 과거 통계가 빠집니다.

## 삭제한 자료를 다시 읽을 수 있어야 했다

정기 통계 갱신은 새로 들어온 표본만 반영합니다. 과거 품질 판정이 바뀌어 재집계가 필요할 때는 RDS에서 빠진 평가 결과를 S3에서 다시 읽습니다.

RDS에는 어떤 평가를 어느 파일로 옮겼는지, 파일 건수와 해시가 무엇인지 남깁니다. 재집계는 현재 품질 조건에 필요한 키를 먼저 확인한 뒤 RDS와 S3 결과를 합칩니다. 계산한 통계는 다시 RDS에 저장합니다.

![RDS에서 삭제된 완료 결과를 S3에서 읽어 과거 통계를 다시 계산하는 흐름](assets/salmonbus-portfolio/08-sal175-rebuild.png)

파일을 다시 읽을 수 있다고 DB 원본 전체를 복구하는 것은 아닙니다. 통계 계산에 필요한 결과만 읽고, 조회 조건과 진행 위치는 RDS에 유지합니다.

## 스레드를 나눠도 DB 부하가 분리되는 것은 아니다

S3 응답을 기다리는 동안 수집과 실시간 예보가 멈추지 않도록 통계와 이관을 별도 실행 경로로 나눴습니다.

```text
collection 스레드  → 수집
processing 스레드  → 실시간 예보와 평가
calibration 스레드 → 통계와 이관
```

근데 세 작업은 같은 worker JVM, 같은 Hikari 연결 풀, 같은 RDS를 사용합니다. 스레드를 나눴다고 DB 연결과 I/O까지 격리되는 것은 아닙니다.

![수집, 실시간 처리, 통계와 이관의 실행 스레드와 공유 DB 자원](assets/salmonbus-portfolio/09-sal175-scheduling.png)

그래서 SQL 제한 시간은 500ms, 잠금 대기는 100ms, DB 트랜잭션은 2초로 제한했습니다. S3 실패 시에는 원본을 유지하고 60초 뒤 만료된 작업부터 다시 시작하도록 했습니다.

## 어디까지 확인했나

구현에서는 다음 동작을 확인했습니다.

- 파일이 다르면 DB 원본을 삭제하지 않음
- 실패한 작업을 다시 실행할 수 있음
- 일부 자료만 읽은 통계를 게시하지 않음
- 복원한 결과를 다시 삭제하지 않음
- S3에서 읽은 자료와 DB 자료를 합쳐 진행 위치를 저장함
- 삭제와 자동 처리, 스레드 구성 테스트 통과

운영 S3 권한, 실제 삭제량, RDS 부하, EBS 효과는 별도 확인 대상이었습니다. 삭제 후 S3 읽기를 끄거나 구버전으로 단순 롤백하면 과거 통계가 누락될 수 있습니다. 삭제만 멈출 때는 `FORECAST_ARCHIVE_DELETE_ENABLED=false`로 바꾸고 worker를 재시작하도록 운영 경계를 나눴습니다.
